`prepare-source.mjs <restricted-source-directory>` обрабатывает HTML как данные, без исполнения. Сохраняет визуальную разметку, CSS, изображения, анимацию и пятиминутный таймер. Удаляет следы браузерного расширения и сторонние трекеры из экспорта. Отправка в Tilda заменяется существующим мостом HTML → форма платформы. Имя и фамилия раздельные. Форма и все источники маршрутизации настраиваются в существующем конструкторе.

`vendor/tilda-scripts-3.0.min.js` — публичный исходник https://static.tildacdn.com/js/tilda-scripts-3.0.min.js, получен 16.10.2026. При подготовке единственное чтение `window.parent.isPagePreview` заменяется локальным `window.isPagePreview`, поскольку HTML работает в изолированном iframe. Ограничения sandbox не меняются. У таймера предусмотрен локальный запасной объект хранилища; отсчёт не зависит от доступа к данным родительской страницы.

## Путь клиента

1. Лендинг Никиты; кнопки прокручивают к контактной форме.
2. Имя, фамилия, email, телефон; согласие. Каноническое окно регистрации получает введённые контакты.
3. Проверка контактов и шестизначный код на email. В действующей подтверждённой сессии повторный код не нужен. Другой email к открытой сессии не прикрепляется.
4. Сохраняется контакт, заполняются только пустые поля существующей карточки. Пароль и покупки не меняются.
5. Проверяется действующая привязка основного support-бота. Если её нет — клиент подключает бота и нажимает «Старт».
6. «Завершить регистрацию» сохраняет одну регистрацию на человека/форму. Нет вопросов, заказа, платежа или учебных доступов.
7. Переход на отдельную страницу «Спасибо» вебинара.

Данные попадают в существующие `site_form_submissions` и историю контакта. UTM — в существующий механизм journeys. Сервер берёт продукт и тариф из опубликованной формы, проверяет почту/бан/архив/бота и повторно проверяет схему в транзакции. Новый RPC — только тонкая идемпотентная обёртка существующих функций; их определения и ACL не меняются.

## Выпуск

`build-release.mjs [output-file]` создаёт проверяемый `release.sql`. По решению владельца страница «Спасибо» переиспользует существующий блок бонусов анкеты и обе ссылки из CMS; меняется только заголовок новой страницы. Источник защищён хешем, оригинальная анкета не меняется.

1. GitHub PR, тесты, checks, merge.
2. Lovable Cloud: проверка точного SHA; только `20261016074828_webinar_registration_reuse.sql`, развёртывание `site-form-submit`, `broadcast-audience-preview`, `email-mass-broadcast`, `telegram-mass-broadcast`, `process-scheduled-broadcasts`.
3. Скрипт CMS по умолчанию заканчивается `ROLLBACK`: две страницы + выключенный черновик уведомления email/Telegram. Ожидается 3 строки, 0 отправок. Сначала резервная копия и dry-run, затем один утверждённый DO, затем независимый read-back.
4. Сверить защищённые хеши ЦБ21, регистрации/покупки/очередь, CMS, продукт и тариф. Не включать глобальные уведомления эфиров, не запускать существующие очереди.
5. Publish только после PASS. Снимки опубликованных ПК/телефона, контроль CTA и формы. Реальные OTP/контакт/сообщение для теста — с отдельного разрешения.

Сам вебинар создаёт Ирина; новых комнат или правил доступа этот выпуск не создаёт. В существующих рассылках появляется фильтр «Зарегистрировались на вебинар»: только завершённые регистрации выбранной страницы/формы, пересечение с остальными условиями. Предпросмотр, email, Telegram и плановые отправки применяют один фильтр. Ссылку на эфир и время отправки менеджер укажет после создания вебинара. Подготовленный шаблон выключен, фактических отправок при выпуске нет.
