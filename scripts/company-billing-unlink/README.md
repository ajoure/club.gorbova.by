# Безопасная отвязка контакта-плательщика

Статус: подготовка кода и PR. Применение к рабочей базе и сама отвязка
этим PR не разрешены. В миграции нет UUID клиентов или исправления данных.

## Что меняется

Сейчас `crm_company_backfill_billing_cld` при каждом повторе вызывает
`crm_company_link_contact` и восстанавливает удалённую связь плательщика.
Новый административный RPC снимает одну проверенную ошибочную связь,
сохраняет всю строку в закрытой истории и подавляет её повторное создание.
`crm_company_restore_billing_contact` восстанавливает исходную строку с тем
же ID, флагами, метаданными и временем создания.

Для двух целевых зарегистрированных профилей устранено расхождение схемы:
UI уже показывал роль `employee` («Сотрудник»), но CHECK `company_contacts`
её запрещал. Миграция добавляет ровно это значение к прежним шести после
проверки точного исходного CHECK. Она не создаёт профиль, внешнюю персону или
контакт. Само подключение существующих профилей выполняется позже штатным
`crm_company_link_contact`: director и employee, оба без флага плательщика.
Это тип связи CRM, не роль авторизации или доступ к покупкам.

`client_legal_details` и `client_legal_details_company_map` остаются на месте.
Реквизиты сохраняют своего владельца и статус. Документы, черновики,
покупки, платежи, подписки, права и согласия не обновляются и не удаляются.
История исправления и две операции записываются в `crm_activity_log`.
Доменные события уведомлений и внешние сообщения не создаются.

Подавление узкое: конкретные компания, профиль, реквизиты и карта источника,
только `billing_contact`. Другая компания того же профиля и другие профили
не затрагиваются. Намеренная ручная связь другого типа остаётся доступной;
она не создаётся этим исправлением. Если у профиля уже есть другая связь с
этой компанией, unlink откажет, чтобы не выдать частичную отвязку за полную.

## Контракты и блокировки

- `crm_company_unlink_billing_contact(company, profile, cld, expected_contact, reason, initiator_user_id DEFAULT NULL)`:
  authenticated с фактическим `auth.uid()` и ролью `admin`/`super_admin`.
  Обычный пользователь, менеджер и support выполнить его не могут. Существующий
  привилегированный процесс Lovable Cloud может вызвать его как service_role
  только с явным ID администратора-инициатора, проверяемым через has_role_v2.
  Сервис сохраняет собственную идентичность; пользовательские JWT и auth.uid()
  не подменяются. Интерактивный пользователь не может указать другого инициатора.
  В журнале отдельно записываются execution_role и initiator_user_id.
  Та же проверка применяется к восстановлению.
- Проверяются точные ID, владелец реквизитов, назначение billing, тип юрлица,
  активная компания, карта источника, тип/источник/флаг контакта и отсутствие
  других связей этого профиля с компанией. Все проверки и изменения атомарны.
- Первый вызов возвращает `unlinked=1` и `suppression_id`. Точный повтор
  возвращает тот же ID и `unlinked=0, already_unlinked=true`, без нового аудита.
  Несовпавший ожидаемый ID или изменившееся состояние дают ошибку без записей.
- Порядок блокировок: реквизиты → компания → существующий advisory lock
  `crm_company_link_contact:<company>:<profile>:billing_contact` → карта → контакт.
  У worker реквизиты уже заблокированы до upsert; прямой linker сначала
  блокирует компанию. Нельзя переносить advisory lock перед этими блокировками.
- Linker после общей блокировки возвращает NULL для подавленной связи.
  Backfill возвращает `contact_suppressed=true`, `contact_id=null`, оба флага
  `contact_created/contact_reused=false`. Остальной ответ и ACL сохранены.
- Текущий `company-sync-worker/index.ts` принимает успех по `company_id`,
  `writer` и отсутствию ошибки, а не по ненулевому `contact_id` (строки 235–256
  базового SHA). Этот ответ уже соответствует контракту. Изменение и deploy
  Edge Function не нужны. Очередь продолжает отмечать такой replay как done.
- Триггер на `company_contacts` также отклоняет прямую запись подавленной
  связи. Карта с активным подавлением не может сменить компанию/источник:
  слияние такой компании останавливается атомарно до разрешения исправления.
- FK истории сохраняют lineage: удаление реквизитов, карты, компании или
  профиля, на которые ссылается история, будет отклонено, в том числе после
  восстановления. Для будущего удаления/анонимизации нужен отдельный план
  сохранения аудита. Историю нельзя стереть обычной записью Data API.

UI, поиск и `useUnifiedPayments` читают актуальные `company_contacts`,
поэтому снятая связь перестаёт участвовать в их выборе профилей. Строка
реквизитов не переносится другому человеку. Имеющиеся прямые связи заказов
с компанией также сохраняются; их изменение не входит в этот PR.

Установка создаёт только схему/API; контакты автоматически не исправляются.

## Проверки

```sh
PGLITE_MODULE=/path/to/existing/pglite/dist/index.js \
  node scripts/company-billing-unlink/unlink.test.mjs
```

Фикстура загружает настоящие определения таблиц компаний/карт/контактов,
writer-функций, merge и source enqueue. Финансовые таблицы и документы —
минимальные синтетические sentinel-строки с FK на реквизиты и триггерами,
запрещающими любые записи. Это проверка SQL-контрактов, а не копия всей
рабочей схемы. PGlite не доказывает конкуренцию разных серверных сессий.

По умолчанию проверяется upsert, совпавший с рабочей базой. Второй запуск с
`BILLING_UPSERT_VARIANT=documented` проверяет другой допустимый вариант целиком.
Оба запуска проверяют итоговую форму: ровно два существующих зарегистрированных
профиля (director/employee), без администратора, без флагов плательщика,
с идемпотентными повторами и сохранностью бизнес-данных после синхронизации.

GitHub job `concurrency` отдельно запускает пять настоящих гонок на
одноразовом PostgreSQL 17: backfill → unlink, unlink → backfill,
linker → unlink, unlink → linker и managed service unlink → backfill.
Первая транзакция удерживает свои
блокировки; вторая должна дождаться её, обе должны успешно завершиться.
Итог всегда: 0 контактов заданного профиля, 1 активное подавление.

Для ручного повтора **только в пустой одноразовой локальной базе**:

```sh
BILLING_UNLINK_LOCAL_TEST=1 PGHOST=127.0.0.1 PGDATABASE=unlink_fixture \
  PGUSER=postgres PGPORT=5432 bash scripts/company-billing-unlink/concurrency.sh
```

Скрипт не принимает hosted connection string и требует точного локального
имени тестовой базы. Он создаёт синтетические таблицы и роли; существующую
базу для этих тестов использовать нельзя.

## Будущее применение через Lovable Cloud

Требуется отдельное явное разрешение владельца. Сейчас эти шаги не выполнять.

1. Проверить очередь Lovable, отсутствие чужой исполняемой/приостановленной
   команды, SHA и неизменность чужих неопубликованных изменений. После merge
   использовать точный проверенный SHA. Не включать посторонний Publish.
2. Сверить текущие определения, FK, триггеры и ACL с PR. Применить только
   `20261103125859_crm_company_billing_contact_unlink.sql` штатным managed
   механизмом Lovable Cloud. Не использовать legacy Supabase или прямой SQL/CLI
   как обход. Никаких deploy функций или frontend Publish для этого PR.
3. Свежим ограниченным чтением сверить компанию, **profiles.id**, реквизиты,
   карту и точный ID одной ошибочной связи. Ожидается один профильный контакт,
   одна карта источника, одна строка реквизитов. Сохранить приватный baseline
   количества, ID и контрольных сумм реквизитов/документов/черновиков,
   покупок/платежей/подписок/прав/согласий и прямых company-order links.
   Учитывать одновременно profile_id и отличный от него auth user_id.
4. Выполнить один разрешённый вызов нового RPC через штатный механизм
   платформы. Для существующего сервисного процесса Lovable Cloud сначала
   подтвердить service_role, явно указать проверенного администратора-инициатора
   и получить это различие в аудите. Не подменять claims и не извлекать JWT.
   Если платформа не даёт штатный нужный контекст — STOP без SQL обхода.
   Записать возвращённый
   suppression_id; ожидание — `unlinked=1`. При неопределённом ответе сначала
   читать исходный запрос/состояние, затем при необходимости точный повтор.
5. Прочитать компанию и профиль: 0 связей этого профиля, число контактов −1,
   ровно 1 активное подавление с ожидаемым archived contact_id. Все baseline
   реквизиты, их владелец/статус, документы, деньги, права и другие компании
   совпадают. Не запускать рабочий worker для smoke. Не создавать людей,
   заказы, покупки, права, письма, платежи или согласия.
6. Проверить карточки и опубликованный экран компании допустимым браузером,
   сохранить безопасный снимок без персональных и банковских данных.
   После подтверждения установки CHECK с employee подключить целевые два
   существующих зарегистрированных профиля штатным linker: director и employee,
   `_is_billing_contact=false`, `_source=manual`, без карты источника. Имена и
   роли не заменяют проверенные `profiles.id`. Исправление полного/краткого
   имени и района относится к исходной бизнес-задаче и выполняется после
   проверки сохранности. Этот PR не создаёт эти связи автоматически.
   Финальная цель бизнеса остаётся ровно 2 профиля.

Stop: другой ID, лишние связи, merged/archived компания, дрейф кода/схемы,
неожиданный rowcount, ошибка аудита или отличие baseline. Никакого fallback
на `client_legal_details_admin_delete` и никакого переноса владельца реквизитов.

## Восстановление

После отдельного решения вызвать `crm_company_restore_billing_contact` с
сохранённым suppression_id в том же административном контексте. Для service_role
второй аргумент — явно проверенный initiator_user_id администратора. Возвращается
`restored=1`; точный повтор даёт `restored=0`. Вся строка возвращается с прежним
ID. Проверить её и тот же business baseline. Если владелец/карта изменились,
компания неактивна либо появилась другая связь, RPC откажет без перезаписи.
Старый restore не отменяет более новую отвязку. История исправления остаётся.

Не откатывать writer-код при активном подавлении: это убрало бы корректный
replay-контракт. Сначала отдельно решить судьбу каждого активного подавления;
любое последующее изменение схемы проводить новой проверенной миграцией.
