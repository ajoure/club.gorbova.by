# Восстановление двух включённых отраслей исторического ЦБ

DATA-артефакт для одной заранее проверенной покупки: ИП и розница входили в
оплаченный базовый тариф, но отсутствуют в `module_list_mapped`. Это не новая
продажа, платёж, распределение стоимости или выдача другого курса.

В Git хранятся только шаблон, renderer и синтетические тесты. UUID клиента,
наблюдаемые хеши строк, сообщения-доказательства и готовые SQL держать в частном
каталоге доказательств вне Git. Применять только через явно согласованную задачу
канонического Lovable Cloud, после PR/CI и ревизии. Legacy Supabase не подходит.

## Обязательные исходные доказательства

- Единственный активный профиль связан с точным Auth UUID.
- Исходная оплаченная историческая покупка имеет `base_tariff_purchase`;
  первичная переписка подтверждает выбор именно двух включённых отраслей.
- Отдельные дополнительные покупки сохраняются. Новые суммы, валюты, даты,
  платежи, заказы и подписки из переписки не выводятся.
- Текущий BUSINESS: точные UUID подписки/заказа/успешной оплаты 250 BYN,
  отсутствие возврата и конечный оплаченный срок. ИП/розница входят в точное
  действующее `prior_purchase / per_product` правило этого тарифа.
- ИП: единственная истёкшая запись без ручного запрета; розница: запись
  отсутствует. Независимые источники не подменяются и не удаляются.
- Нативно проверены все включённые триггеры четырёх записываемых таблиц и тела
  фактически срабатывающих функций. UPDATE меняет только `purchase_snapshot`:
  колонковые триггеры денег, рефералов, CRM и `meta` на него не подписаны.
  Общие UPDATE-триггеры должны только проверять принадлежность стадии и менять
  `updated_at`; внешние эффекты недопустимы. Хеш `bundle-dependencies.sql`
  фиксирует эти определения, публичные helpers и конфигурацию CRM. Любой дрифт
  останавливает выполнение; автоматически обновлять хеш для прохождения нельзя.

## Вход и порядок

Renderer принимает только перечисленные в нём UUID, исходные MD5/UTC timestamps,
уникальный `repair_key` и 2–8 UUID сообщений-доказательств. Прочие входные поля
отбрасываются. Идентификаторы, ключ и временные метки проходят строгую валидацию.

```sh
node scripts/historical-purchases/render-bundle-repair.mjs /private/reviewed-input.json dry-run /private/bundle-dry.sql
node scripts/historical-purchases/render-bundle-repair.mjs /private/reviewed-input.json execute /private/bundle-execute.sql
```

Результат renderer — SHA-256 точного SQL; готовые файлы создаются с mode `0600`.
Неразмеченный шаблон исполнять нельзя: он останавливается без входа.

1. Managed dry-run работает в `READ ONLY` транзакции: только проверки/хеши,
   без UPDATE/INSERT, ledger, audit, endpoint calls и боевой генерации документов.
   Ожидается: один snapshot, реактивация одного ИП, одна новая розница,
   два ledger и один audit. Ни одного другого изменения.
2. После PASS запускается точный ранее проверенный execute SQL: одна атомарная
   транзакция, CAS полных исходных строк и lock/statement timeout. Меняются только
   snapshot состава и два права. В meta сохраняются остальные ключи, прежняя
   lineage записывается отдельно, новый source — действующий BUSINESS.
   В обоих правах полный `historical_module_product_ids` содержит пару из
   исходного snapshot; новые платежи/заказы/подписки не создаются.
3. ИП получает ledger `reactivate/reactivated`, розница — `grant/granted`.
   Уникальные event keys и один audit фиксируют происхождение. Проверяются
   хеши защищённых денежных строк, подписок, провайдеров, очередей, остальных
   прав, существующих ledger/audit и служебных сообщений. Личный Business
   Telegram полностью исключён даже из fingerprint. Неожиданный эффект вызывает
   откат всей транзакции; это не заменяет предварительную проверку отсутствия
   внешних вызовов в триггерах.
4. Повторный execute проверяет уже завершённое состояние и возвращает ноль
   изменений, включая ledger/audit. Частичное или изменившееся состояние — HOLD,
   без автоматического «доделывания» и без повторных начислений.

## Проверка результата

Отдельный native read-back: два UUID в составе исторического заказа, два активных
права с текущей lineage и сроком BUSINESS, четыре прежних права полностью
неизменны, деньги/подписки/очереди/уведомления неизменны, ledger=2 и audit=1.
Проверить канонический `user_has_training_lesson_access` на реально существующем
учебном уроке каждого модуля и затем открытие у клиента.

Если раздел содержит только форму обратной связи, RPC на этой форме доказывает
право, но не наличие учебных материалов и не работу обучения. Такой случай
остаётся открытым отдельным follow-up; отсутствующее содержимое не заменяется
другим продуктом. Не сообщать клиенту, что все уроки исправлены, до фактической
проверки. Эта DATA-правка не развёртывает functions и не требует Publish.

## Локальная проверка

`node --test scripts/historical-purchases/bundle-repair.test.mjs`

Тесты в настоящем PostgreSQL runtime PGlite проверяют read-only dry-run,
сохранение полей и других данных, замену устаревшей lineage, идемпотентность,
CAS/ручные блокировки/возвраты/истёкший source, откат неожиданных уведомлений и
изменений денег, частичный ledger и дрифт зависимостей. Допускается
`HISTORICAL_PGLITE_MODULE` с абсолютным file URL существующей библиотеки;
устанавливать отдельные зависимости для этой задачи не требуется.
