# Контекст клиента для автопродажи ЦБ21

## Изменение

Раньше runtime читал только `paid` заказы и объявлял историю покупок полной. Теперь все неудалённые заказы сохраняют фактический статус, а оплата подтверждается отдельно по связанным успешным платёжным записям. Нулевая цена, пробный доступ, возврат, переопределённый статус, повторяющийся платёжный идентификатор и неполная оплата различаются. Суммы возвратов из разных журналов не складываются: это основание передать оформление владельцу.

`entitlements` и `entitlement_sources` читаются отдельно. Тип источника сохраняется буквально: ручной доступ не переименовывается в подарок. Запись доступа не доказывает оплату, заказ не доказывает прохождение курса. Право на льготу по-прежнему решает существующий `sales_offer_eligibility` по настройкам оффера.

Эфиры привязаны только по авторизованному user ID: входы/heartbeat комнаты, выданный доступ, созданная сессия автовеба, позиции плеера, комментарии, вопросы и реакции. Начальная/последняя отметки не являются непрерывным просмотром. `max_watched_seconds` и даже отметка `completed_at` не дают права утверждать, что просмотр завершён. Длительность просмотра неизвестна. CTA runtime events не включены: они описывают показ администратором и не содержат надёжной клиентской идентичности.

Все источники читаются постранично, IN-запросы ограничены 100 идентификаторами. Ошибка чтения или конфликт user/profile останавливает контекст. Нет связывания по телефону/email/имени. В модель не передаются платёжные токены, ответы провайдеров, ссылки, session keys, произвольные meta или причины возврата. История явно ограничена доступными каноническими записями: отсутствие записи не доказывает отсутствие покупки/посещения вне платформы.

Перед оформлением контекст оплаты/доступов перечитывается после ответа ИИ. Существующая оплаченная покупка, спорный paid/partial/refunded заказ или активный доступ не приводят к повторному оформлению: используется существующий handoff. Возможность технической проблемы и её назначение владельцу остаются прежними.

## Проверки и release

- Node: классификация платежей/возвратов/доступов, конфликт идентичности, перемотка/комментарий/регистрация, прежняя последовательность диалога и AI-контракт.
- Deno: чтение 205 заказов через несколько страниц, точная связь платежа по order FK, чужая личность, ошибка запроса, общая сессия автовеба, существующие checkout-контракты и handoff до writer.
- Typecheck: `sales-runtime-worker`.
- GitHub release quality gate должен быть PASS.

Production принадлежит Lovable Cloud. После plan-only ревизии точного PR и merge развернуть **только sales-runtime-worker** из точного merged SHA. Миграций, настроек, изменения цен/прав, активации кампании и Publish интерфейса здесь нет. Сохранить OFF/HUMAN_HOLD.

Безопасная серверная приёмка: health сообщает `client_evidence_revision=v1`; `preview_context` в OFF/HOLD читает фактический контекст, возвращает только счётчики и ограничения, без модели/сообщений/мутаций. Затем `preview_scenario` new_client, graduate и club_consultation с полностью синтетической личностью, без checkout writer, отправки или уведомления. До/после сверить campaign/conversation, queue/jobs/events/outbox/checkout/media. Любая ошибка схемы/идентичности или дельта счётчиков блокирует активацию.

Это backend-изменение: новые UI-скриншоты не применимы. Ранее опубликованные настройки не изменены. Контролируемый тест с НОВОЙ фразой владельца остаётся отдельной приёмкой после согласования правил.
