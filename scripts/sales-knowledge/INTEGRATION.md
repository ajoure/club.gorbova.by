# Контракт подключения после проверки production

Статус: исполняемые локальные модули и тесты. Сетевые адаптеры, база,
распознавание, модель и отправитель здесь не подключены. Миграции и RLS
проектируются после сопоставления реальных таблиц и существующих функций.

## 1. Выгрузка уроков → план расшифровок

`buildInventory` принимает schema_version=1, captured_at, complete,
selected_product_ids, expected_counts для lessons/modules/blocks и массивы:

- `lessons`: id, module_id, product_id при наличии, video_url, content,
  non_video_content_verified для подтверждённых уроков без видео.
- `modules`: id, product_id, parent_module_id.
- `blocks`: id, lesson_id, parent_id, block_type, content.
- `bindings`: id урока, product_ids, verified, basis (`direct`,
  `module_ancestry` или `access_rule`); последнему нужен evidence_id.
- `video_catalog`: source_id, source_revision, aliases, audio_status,
  duration_ms, метаданные transcript. Это проверенный результат чтения
  провайдера, а не ID, догаданный по обрезанному адресу.

Экспорт должен содержать полный целевой набор уроков и все их блоки/предков.
Счётчики снимаются в согласованном снимке. Признак complete нельзя ставить
по успешному HTTP или первой странице. Вложенные parent_id проверяются на
циклы, пропуски и переход к другому уроку. Нестандартное видео/iframe,
неизвестная метаинформация или отсутствие binding блокируют пакет.

Продукт не определяется по названию. Binding — утверждение доверенного
адаптера на основании прямых связей или конкретного правила доступа.
Модульная цепочка дополнительно перепроверяется. Исторические версии,
бонусные доступы и текущие тарифы нельзя объединять по похожему заголовку.

Результат содержит только ID, ревизии и технические признаки; он совместим
с planTranscriptions. Ссылки аудио, названия и исходное содержание в план
не копируются. Сопоставление коротких и полных Kinescope ID задаётся aliases;
два разных видео с одним alias запрещены.

## 2. Сборка и возобновление расшифровки

`assembleTranscript`: source_id, source_revision, duration_ms, window_ms
(по умолчанию 90000), parts с part_index/start_ms/end_ms/source_revision/
status/text. Все плановые интервалы обязательны, включая последний хвост.
Повтор части, щель, перекрытие, неверная ревизия или неготовый текст — ошибка.
Пустой сегмент допустим только с silence_verified=true; весь текст пустым
быть не может. Итог имеет classification=paid_private и content_sha256.

duration_ms и границы получаются из реально декодированного аудио. Простая
проверка временных меток не доказывает точность распознавания речи: перед
использованием нужны выборочное сравнение с записью и проверка пропусков.
Не подменять отсутствующую речь выдуманным резюме.

`planBatch(plan, ledger, limits)` ограничивает число новых видео и суммарную
длительность; ключ строится по видео, ревизии и версии процесса. Любая
существующая попытка блокирует автоматический повтор, кроме завершённой,
которая пропускается. Failed/unknown/running идут в reconciliation, а не в
повторный платный запрос. Это план, не транзакционная очередь: production
должен хранить ключ атомарно, проверять lease и подтверждать результат.

## 3. Закрытый корпус → знания продавца

`compileSalesKnowledge({facts,sources,testimonials}, now)` выполняется
внутри доверенного редакционного процесса. Sources содержат id, revision,
sha256, is_current, product_ids, lesson_ids. Полный text допустим **только
на внутренней стороне этой границы**, для проверки исходника/отзыва.

Fact: id, product_id, lesson_id или null, kind, text, keywords, tariff_ids,
source_id, source_revision, source_sha256, valid_from, valid_until и approval.
Разрешены только topic, learning_outcome, format, prerequisite, exclusion,
tariff_content. Текст краткий, без HTML и URL. Цены и checkout сюда не входят:
для них нужен живой resolver действующего предложения.

Approval: status=approved, approved_by, approved_at, content_sha256,
вычисленный factReviewDigest. Digest связывает одобрение с точным текстом,
продуктом, тарифом, источником и сроком. При редактировании одобрение
недействительно. Дубликаты ID исключаются, а не выбираются по порядку.

**Digest не является цифровой подписью или разрешением.** Любой клиент
технически может его вычислить. Записывать approval может только доверенный
сервер после проверки роли редактора; из ответа модели, клиентского JSON
или переписки одобрения не принимаются. Эти серверные проверки/RLS ещё
не реализованы здесь и обязательны до подключения.

Проверка структуры не умеет семантически отличать краткий учебный ответ
от описания темы. Редактор подтверждает, что текст описывает результат,
а не выдаёт решение. В дальнейших модельных проверках нужны попытки получить
урок по частям, перефразировать закрытое задание и вытянуть исходный текст.
Полные расшифровки не передаются в контекст продавца даже после покупки;
поддержка обучающегося — отдельный режим с проверкой доступа.

`retrieveSalesFacts(packet, request)` работает только с audience=sales.
Request: query, product_ids, tariff_ids, now, max_chars, limit. Поиск
детерминированный, по словам с простым нормированием; это проверяемая основа,
не обещание полноты семантического поиска. При отсутствии совпадения —
clarify_or_handoff. Пакет берётся из доверенного опубликованного хранилища,
не из сообщения клиента. Отозванный источник требует перепубликации пакета;
версия проверяется повторно перед ответом.

## 4. Отзывы

Testimonial: id, product_id, source_id, source_sha256, quote, display_quote,
permission=approved_for_client_use, valid_from/valid_until, approval с
testimonialReviewDigest. Quote обязан точно содержаться в исходнике,
хеш источника проверяется по его тексту; источник связан с этим продуктом.
Редактор отдельно проверяет контекст, актуальность, допустимость
использования и обезличивание display_quote. Изменение отображаемой цитаты
аннулирует одобрение. В выход не копируются имя автора, профиль и исходник.

Отзывы не включаются автоматически в поиск учебных фактов и не доказывают
универсальный результат. Для показа отзывов будущий сервер повторно
проверяет product_id, срок, permission и согласованное место в сценарии.

## 5. Контекст клиента

`buildClientContext(context, now)` принимает проверенную identity
(profile_id, verified, evidence_id), purchases/access/webinar_activity/
preferences и purchase_history_complete. Каждая запись имеет profile_id,
source_id и observed_at. Другой профиль или будущее наблюдение исключаются.

Покупка: product_id, order_id, version, status, payment_verified либо
historical_paid_verified, learner_profile_id. Payer и learner разделены;
возврат сохраняется в истории, но не создаёт доступ. Дубликаты заказа
неоднозначны и исключаются из подтверждённого результата.

Доступ: product_id, verified, revoked=false, starts_at, ends_at либо
perpetual_verified. Отмена автопродления сама по себе не укорачивает
оплаченный срок. Ровно в момент ends_at доступ уже не действующий.

Вебинар: webinar_id, kind registered/commented/watched/completed;
последние два требуют playback_verified. Комментарий не повышается
автоматически до просмотра. Предпочтение: kind professional_goal /
preferred_format / prior_learning_feedback, text,
explicit_customer_statement=true. Оценки лояльности и личные слабости
не входят в контекст. Текст клиента помечен как данные, не инструкция.

Это нормализованная проекция: проверка идентичности, оплата, наследуемые
доступы и фактическое время просмотра устанавливаются серверным адаптером
по production. Не доверять одноимённым флагам из входящего сообщения.

## 6. Право ответить и доставка

`evaluateReply` получает policy, conversation, candidate, now. Policy
содержит approved/mode/version/knowledge_version и явные allowlists
bot_ids/conversation_ids/campaign_ids/product_ids/business_connection_ids.
Shadow и draft никогда не возвращают право автоматической отправки.

Conversation содержит transport, IDs, state, last_inbound_actor/at/seq,
last_answered_inbound_seq, history_revision, явные false для human_hold,
human_requested, opted_out, delivery_uncertain, inflight_reply. Для
Business нужны business_enabled и can_reply. Неизвестные флаги закрывают
отправку. Повтор после ответа возможен только по новому входящему клиента.

Candidate связан с policy_version, knowledge_version, inbound_seq,
history_revision и product_id; intent ограничен product_information,
product_selection, checkout_link; new_question_count≤1, facts_verified=true,
contains_paid_instruction=false. Checkout дополнительно требует
offer_verified. **Флаги результата модели не считаются проверкой:** их
выставляет доверенный валидатор, а не модель или клиент.

`applyConversationEvent` не открывает ожидание по таймеру, оплате или просмотру.
Вмешательство человека/отказ сохраняются после нового входящего и даже
после позднего подтверждения доставки. Подтверждение доставки обязано
ссылаться на pending_delivery_id. Возобновление после ручной паузы требует
отдельного серверного действия уполномоченного сотрудника; здесь его нет.

Чистые функции не обеспечивают блокировки БД и exactly-once доставку.
При интеграции обязательны атомарное занятие диалога, исходящая очередь,
проверка актуальной истории перед send, отдельный Telegram Business adapter,
неизвестный результат доставки без слепого повтора и read-back.

## 7. Что ещё требует Lovable / production

1. Полный актуальный экспорт уроков/видео/источников и реальные счётчики.
2. Сопоставление текущих таблиц и функций с контрактом, план managed-изменений.
3. Закрытое хранилище полного текста, RLS редакций и серверное утверждение.
4. Адаптер существующего STT, атомарная очередь, фактические расходы и retry.
5. Продуктовые условия, реальные отзывы, проверка авторства стиля и редактура.
6. Подключение retrieval/context/policy к существующему ИИ без обхода границ.
7. UI, интеграционные тесты с реальными правами, ревизия и публикация после PASS.

До этого никакой runtime-функции, отправки или настройки production
этот PR не меняет. Он даёт готовые проверяемые операции для интеграции,
а не заменяет производственные проверки синтетическими тестами.
