# Правила работы Codex в `gorbova.by`

Этот файл — активный регламент для Codex и всех агентов в репозитории. Он
действует для каждой новой ветки, пока пользователь явно не задал более узкие
правила. Подробное объяснение и шаблоны находятся в
[`docs/CODEX_LOVABLE_PLAYBOOK.md`](docs/CODEX_LOVABLE_PLAYBOOK.md).

## Единый координатор проекта

- Пользователь передаёт вопросы в один главный чат проекта. Координатор ведёт
  общую очередь, делегирует независимую работу субагентам по направлениям и
  возвращает проверенный результат в главный чат. Не создавать постоянный
  отдельный чат для каждого нового вопроса.
- Перед новой задачей читать [порядок координации](docs/PROJECT_COORDINATION.md)
  и актуальную запись задачи в приватном операционном реестре. История чата и
  старый checkpoint дают указатели, но требуют сверки с текущим состоянием.
- Использовать профили из `.codex/agents/`, когда их направление соответствует
  задаче. Координатор передаёт точный scope, разрешения, владельца файлов,
  проверки и ожидаемый результат. Подзадачи с общим изменяемым ресурсом
  выполнять последовательно; субагент не получает новых бизнес-полномочий.
- Единственный назначенный владелец выполняет управляющие действия Lovable.
  Остальные задачи продолжают независимые чтение, код и проверки. Внешний
  блокер освобождает очередь, сохраняя запрет повтора неопределённой операции.
- Приватные карточки чатов, клиентские случаи, внутренние идентификаторы
  переписки и локальные журналы держать вне этого публичного репозитория.

## Неподвижные границы

- Общение с пользователем, планы и отчёты — на русском языке.
- Каждая новая самостоятельная задача или sprint начинается только в новом
  пустом worktree и новой ветке `codex/<краткий-scope>` от актуального
  `origin/main`; для неё создаётся один отдельный PR. Существующую ветку можно
  продолжать только для той же явно названной задачи/PR. Нельзя добавлять
  новую задачу в грязную общую папку, чужую ветку, generic catch-all или
  `agent/...`-ветку.
- Не трогать чужие ветки, открытые PR, временные файлы и параллельные задачи.
- Не хранить и не выводить токены, ключи, персональные данные, пути файлов
  учеников или подписанные URL.
- Для веб-задач по умолчанию использовать встроенный браузер Codex: поиск,
  обычную навигацию, безопасный read-only discovery, UI-проверки и скриншоты.
  Не открывать Chrome «для удобства». Chrome допустим только если без него
  невозможны уже существующая авторизованная сессия, обязательное расширение
  или функция, которой нет во встроенном браузере; в отчёте назвать причину и
  вернуться к встроенному браузеру для остальной работы.
- GitHub — источник кода и истории. Сначала discovery, затем изменение в
  изолированной ветке, локальные проверки, GitHub checks и PR. `main` не
  редактируется напрямую.
- Перед production-действием определить владельца окружения. Если проект
  использует **свой Supabase**, максимум работы выполняется в собственных
  GitHub и Supabase; Lovable используется лишь для конкретной операции, для
  которой нет эквивалента. Если production Supabase принадлежит **Lovable
  Cloud**, GitHub всё равно остаётся источником кода, а миграции/RLS/Storage/
  Edge Functions/данные применяются только через явную задачу Lovable, не
  прямым CLI/MCP или другим проектом.
- Supabase project ref `ypwsuumurrtkxatoyqhk`, даже если в Supabase Dashboard
  он называется `club.gorbova.by`, — **нерабочий legacy-проект незавершённого
  переноса**. Он не связан с текущим Lovable production, не является source of
  truth и не используется приложением. Его advisors, RLS-предупреждения,
  таблицы и данные не исправлять и не переносить в production без отдельной
  явно названной задачи по архивированию/миграции именно этого legacy-проекта.
  MCP/CLI для него не подключать под именем, которое можно спутать с production.

## Рабочий цикл

1. **Diagnose.** Проверить актуальные `origin/main`, worktrees/PR, существующие
   таблицы/RPC/functions/UI и фактическую production-очередь.
2. **Создать изоляцию.** Для нового scope создать пустой worktree и отдельную
   ветку от `origin/main`; убедиться, что рабочее дерево чистое. Продолжать
   существующую ветку разрешено лишь для той же задачи/PR.
3. **Решить режим.** Небольшой изолированный кодовый патч идёт сразу в GitHub.
   Всё, что касается production-данных, Auth/RLS, Storage, платежей, внешних
   интеграций, Edge Functions, миграций или Publish, сначала получает
   plan-only ревизию Lovable.
4. **GitHub-first.** Реализовать и проверить код в отдельной ветке; создать
   PR. Не считать merge, build или Preview публикацией.
5. **Lovable plan-only (если нужен).** Попросить только прочитать состояние и
   дать структурированный план без code/database/deploy/Publish действий.
   Codex делает одну полную консолидированную ревизию. Повторная ревизия —
   только сверка прежних замечаний, если не появились новые факты.
6. **Lovable execute.** Только после одобрения Codex: синхронизировать точный
   merged SHA, применить перечисленные managed migrations, развернуть ровно
   названные functions и выполнить заранее описанные проверки.
7. **Verify и Publish.** Publish разрешён лишь после всех PASS: GitHub checks,
   миграции/функции, read-back, безопасный runtime smoke и отсутствие
   нерешённого критического finding в scope. После Publish подтвердить URL,
   SHA и релевантную пользовательскую функцию.

## Обязательное визуальное подтверждение UI

- Любое изменение, видимое пользователю — текст, изображение, поле, вёрстка,
  состояние или интерактивное поведение — нельзя называть выполненным или
  опубликованным без **двух скриншотов уже опубликованного результата**:
  отдельного для ПК и отдельного для мобильного viewport.
- Codex сам перепроверяет оба результата по опубликованному URL: изменённый
  элемент и базовый пользовательский сценарий видны и работают, текст и
  изображения читаемы, элементы не обрезаны, не выходят за края, не
  перекрываются и не оказываются вне экрана. Если хотя бы одна проверка не
  проходит, исправить и повторить обе проверки до отчёта.
- Скриншоты должны быть привязаны к URL, опубликованному SHA/версии и
  viewport. `Preview`, локальная сборка, DOM-проверка и HTTP 200 не заменяют
  доказательство опубликованного интерфейса.
- Для чисто backend-задачи не имитировать UI-пруф: явно написать, что он не
  применим, и дать соответствующее доказательство API, данных, логов или
  runtime. В скриншоты нельзя включать персональные данные, платёжные данные,
  ключи и подписанные URL.

## Lovable и последовательная очередь

- Управлять Lovable только официальным подключённым плагином Lovable /
  Lovable.dev. Для проекта «Буква закона» сверять project ID
  `796a93b9-74cc-403c-8ec5-cafdb2a5beaa` и workspace
  `EaRBlfb9sRGL5FIEuz9b`. Не создавать отдельные подключения по задачам.
- Чтение состояния/кода, сообщения, plan-only/execute, ожидание, история,
  diff и разрешённая публикация выполняются инструментами этого плагина.
  Редактор/чат Lovable не открывать через браузер, Computer Use или скрипты;
  диагностический echo/whoami не заменяет официальный плагин. UI-проверка
  опубликованного приложения выполняется отдельно во встроенном браузере.
- Перед каждой новой командой сверять владельца общей очереди, фактические
  сообщения и незавершённые/неопубликованные изменения. Запись владельца —
  средство координации, не техническая блокировка API и не доказательство
  свободы проекта. Неизвестное состояние не считать свободным.
- Занятый Lovable не требует нового разрешения на уже согласованную задачу:
  записать зависимость и продолжать другую доступную работу. После передачи
  владения повторно проверить очередь, полный состав публикации, точный SHA
  и проверки, затем продолжить согласованный шаг без повторного вопроса.
- `accepted`/`queued`, завершённый ответ, `idle` чата и общий
  `is_published=true` не доказывают завершение релиза. Сохранять message_id и
  thread_id; читать конечный `response.status` того же запроса. При ошибке или
  неопределённости отправки сначала сверять исходный запрос, не повторять его.
- При недоступном плагине, защищённом подтверждении или недостаточных правах
  фиксировать точный блокер без браузерного/OAuth-обхода. Переходить к другой
  разрешённой задаче, если она не зависит от блокера.
- Конечную очередь текущей цели вести в активной работе и штатных ожиданиях
  Codex. Не создавать новую автоматизацию для слежения за отдельной задачей
  до завершения. Действующие сервисные расписания учитывать в реестре;
  существующие разовые проверки отключать после проверенной передачи или
  завершения, сохраняя отдельные регулярные сервисы вроде техподдержки.
- Общее разрешение на координацию не отменяет индивидуальные holds, запрет
  Publish или отдельное согласование реальных платежей, отмен, рассылок,
  создания пользователей/контактов и необратимого удаления данных.

## Стоп-правила

- Lovable в execute-режиме **не создаёт код, коммиты или миграции**. При
  расхождении с GitHub SHA, missing dependency, неудачном dry-run, неясном
  rowcount или новом critical finding он останавливается и докладывает.
- Любая массовая операция: dry-run → ожидаемые счётчики → небольшие
  идемпотентные batches → read-back. Никаких blind `UPDATE`/`DELETE`.
- Реальный платёж, отмена подписки, письмо/сообщение, создание пользователя
  или контакта не используются как smoke-тест без отдельного разрешения.
- Новый факт, угрожающий данным, доступам или деньгам, блокирует текущий
  execute. Некритичный хвост попадает в явно помеченный follow-up, а не
  раздувает текущий sprint.

## Как сообщать результат

Пользователю сообщать только факт: что изменено, что не затронуто, какие
проверки прошли, точный SHA/PR/Publish и известные ограничения. Не называть
план выполнением и не выдавать reachability/HTTP 200 за полный runtime-proof.
