## Этап 1. Установление источника срока доступа (диагностика, без записи)

Факты, извлечённые из кода и БД:

- Источник срока: `public.tariffs.access_days` (integer). Читается в `supabase/functions/grant-access-for-order/index.ts:702`:
  ```
  const durationDays = customAccessDays ?? tariff?.access_days ?? 30;
  ```
- Fallback при отсутствии значения: 30 дней, `meta.source_window_rule = 'default_30d'`.
- Уровень хранения: тариф (`tariffs`). Оффер (`tariff_offers`) не имеет собственного поля срока и наследует значение родительского тарифа.
- Редактируется в админке: `src/pages/admin/AdminProductDetailV2.tsx`, форма тарифа, поле «Срок доступа (дней)» (строка 1646).
- Business rule продления: entitlement пересчитывается как `accessStartAt + durationDays`, где `accessStartAt = MAX(order.created_at, existing_sub.access_end_at)`, затем `expires_at = GREATEST(existing, new)` (canonical, `entitlement_sync_engine`).

Проверка гипотезы «все три тарифа дали +90»:

- ORD-296 (Бухгалтер, `access_days=90`): 2026-07-11 + 90 = 2026-10-09 ✅ (90 из своего тарифа).
- ORD-297 (Главный бухгалтер, `access_days=180`): 2026-07-11 + 180 = 2027-01-07 ✅ (180 из своего тарифа).
- ORD-298 (Бизнес-леди, `access_days=270`): 2026-07-11 + 270 = 2027-04-07 ✅ (270 из своего тарифа).

Наблюдение «+90 к предыдущему end» в предыдущем отчёте — некорректная интерпретация. Фактически каждый заказ берёт `access_days` **своего** тарифа и считает от `order.created_at`, а `GREATEST` монотонно повышает `expires_at`. Скрытого fallback 90 нет, значения не совпали случайно.

Итог по этапу 1: источник canonical, отдельный параметр создавать не нужно. Инвариант `expires_at NEVER decreases` + `expires_at = MAX(existing, order.created_at + tariff.access_days)` — утверждённая бизнес-логика.

Отчёт по этому этапу пишется коротко в чате, без нового `.md`.
