## Шаг 1. Deploy (после отдельного разрешения)
- Один вызов `supabase--deploy_edge_functions` с параметром `{"function_names":["websms-send","process-scheduled-broadcasts","telegram-mass-broadcast","telegram-webhook","broadcast-track"]}`.
- `bepaid-webhook`, `referral-sale-date-repair` и остальные функции не трогаются.
- Сначала повторно проверить, что HEAD точный и дерево чистое. При ошибке STOP, повторов нет.

## Шаг 2. Read-back после deploy
- Через официальную аналитику и логи прочитать для каждой из пяти функций: имя, function ID, version, deployment ID, время загрузки.
- Сохранить package digest из ответа deploy.
- Прямого соответствия «развёрнутая версия → Git SHA» в инструментах нет. Это записать как ограничение.

## Шаг 3. Безопасный smoke без побочных эффектов
- По одному OPTIONS-запросу без авторизации к каждой функции: ожидается 200 или 204.
- POST на `websms-send` без авторизации: ожидается 401 `missing_auth`.
- Никаких dispatch, run, replay, вызовов провайдера, обработки очереди или вебхуков с данными.

## Шаг 4. Publish (только после PASS шагов 1–3)
- Перед этим `security--get_scan_results`.
- Затем `preview_ui--publish` с тем же SHA.
- После Publish визуальные пруфы по регламенту: скриншоты ПК и мобильного вида опубликованного URL.

## Шаг 5. Один тестовый SMS: ограничение
- `websms-send` требует настоящий JWT сотрудника (admin, super_admin или employee) и `request_id`.
- Легитимного управляемого способа вызвать функцию от имени сотрудника у агента нет. Подставлять токены, выдавать себя за пользователя и обходить проверку нельзя.
- Поэтому тестовую отправку на подтверждённого получателя с `request_id` `30623bc6-bddd-47a1-baf9-e68f9a5506c2` и утверждённым текстом выполняет сам Sergey или сотрудник из интерфейса опубликованного приложения.
- После отправки агент только читает итог: `sms_broadcast_summary` и статус без PII. Неопределённый результат повторно не отправлять.
