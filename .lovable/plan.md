## 1. Канонический механизм

Существующий и единственно допустимый путь — Edge Function **`rules-retroapply`** (уже в registry, деплой не требуется):
- `mode: "preview"` — read-only, ничего не пишет;
- `mode: "execute"` + `apply_categories: ["missing_access"]` (safe_only), `allow_reduce_access: false`;
- поддерживает `source_product_id`, `source_tariff_id`, `user_ids` (батчирование без full-scan);
- идемпотентность встроена: `skipped_idempotent` при уже активном entitlement, каждый прогон помечается `batch_id = RETROAPPLY-<YYYY-MM-DD>-<uuid8>` в `entitlements.meta`.

Ничего нового создавать не нужно. `repair-cb20-entitlements` и `access-rules-nightly-reconcile` в этом плане НЕ используются (они умеют отзывать доступ).

Предпосылка: активные `access_rules` для исторического продукта уже есть — ровно 3 правила `training_content` (по одному на каждый из трёх тарифов, `access_mode: partial`, фиксированные `allowed_module_ids`). То есть объём модулей задаётся правилом, а не решением исполнителя.

## 2. Инварианты (предикаты допуска строки)

Строка обрабатывается, только если ВСЕ условия истинны:
1. `orders_v2.status = 'paid'` и `product_id` целевой;
2. `orders_v2.user_id IS NOT NULL` (Auth-аккаунт существует);
3. `orders_v2.tariff_id IS NOT NULL` и для него есть `access_rules.is_active = true`;
4. нет активного entitlement: `status='active' AND (expires_at IS NULL OR expires_at > now())`;
5. категория `rules-retroapply` = `missing_access` (никаких `reducible_by_rule`, `conflict_existing`, `requires_manual_review`).

Запрещено: изменять деньги, заказы, платежи, подписки, создавать пользователей, трогать неоплаченные заказы, отзывать существующий доступ.
