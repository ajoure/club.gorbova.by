
# ПАТЧ: Глобальная сверка сделок, привязок и доступов + массовое продление

---

## ГЛАВНОЕ ПРАВИЛО

Ничего нового не придумывать. Все проверки, исправления, продления и отображение доступов выполняются **только по уже существующей конфигурации системы**:

- `products_v2` — продукты
- `tariffs` — тарифы
- `subscriptions_v2` — подписки
- `entitlements` — записи доступа
- `access_rules` — правила доступа
- текущие связи продукт → тариф → тренинг → Telegram

Запрещено:
- связывать продукты вручную «по смыслу»
- создавать доступы на основе предположений
- вводить исключения, которых нет в текущей конфигурации
- превращать исторические сделки в текущие доступы без прямого основания

Если основание не доказано через существующие данные — случай уходит в статус **«требуется ручная проверка»**.

## Фаза А — Аудит (только чтение)

### Действие

Python-скрипт `/tmp/orders_reconciliation_audit.py` (копия в `/mnt/documents/`). Только SELECT-запросы, никаких записей в БД.

### Классификация каждой сделки и каждого доступа

Обязательная развилка:

| Статус основания | Описание |
|---|---|
| `есть_текущее_основание` | Активная подписка / действующий тариф / действующее entitlement / действующее правило в access_rules |
| `основание_историческое_и_истекло` | Была покупка, но срок доступа уже закончился |
| `основание_не_доказано` | Нет подтверждения ни через одну из таблиц системы |
| `архивный_или_неактуальный_продукт` | Продукт неактивен или архивный |
| `защищенный_случай` | staff / admin / test / split_parent / needs_mapping |

### Сегментация заказов

- `обычный` — нет признаков split/import
- `родительский_split` — `meta->>'split_status' in ('children_created','finalized')`
- `дочерний_split` — `meta->>'split_from_order_id' is not null`
- `импорт` — `reconcile_source in ('bepaid_archive_import','getcourse_historical','csv_active_import')`
- `ручной_административный` — `reconcile_source='manual' OR meta->>'source'='admin'`

### Правила защищённого пропуска

Авто-исправление запрещено если:
- `meta->>'needs_mapping' = 'true'`
- staff/admin/test/demo пользователь
- родительский split-заказ
- статус: refunded / canceled / failed
- неоднозначная связка profile → user
- `количество_дублей_активных_доступов > 1`

### CSV-артефакты (10 файлов, все с `_<ид_пакета>` в имени)

1. **полный_аудит_сделок** — все ~2708 сделок, ~35 колонок
2. **сводка_по_категориям** — количества по каждому типу проблем
3. **исправимые_user_id** — кандидаты на восстановление user_id в заказах
4. **исправимые_product_id** — сделки без product_id с маппингом
5. **исправимые_отсутствующие_доступы** — только случаи с доказанным текущим основанием
6. **отсутствующие_подписки_только_обнаружение** — gap paid+tariff без subscription (без авто-создания)
7. **просроченные_активные_подписки** — active с access_end_at < now()
8. **защищённые_пропуски** — все исключения из авто-ремонта
9. **требуется_ручная_проверка** — все остальные неразрешённые случаи
10. **итоговые_показатели** — сводная таблица метрик

### Поиск записей доступа — унифицированный

Поиск по `(user_id, product_id)`, затем fallback по `(user_id, product_code)`. Фиксация: `способ_сопоставления`, `устаревший_null_product_id`, `количество_дублей_активных_доступов`.

## Фаза Б — Исправление данных (последовательные патчи)

### Главное правило исправлений

Создавать запись доступа можно **только** если на текущую дату есть доказанное основание в существующей конфигурации. Запрещено:
- создавать доступ только по факту старой покупки
- восстанавливать просроченный доступ без действующего основания
- продлевать доступы вне существующих правил продукта

Если основание не доказано → **требуется_ручная_проверка**.

Для каждой созданной или обновлённой записи доступа в proof обязательно показать, каким именно действующим правилом системы она подтверждена. Если это нельзя показать — запись не создавать.

### Б1. Восстановление user_id в заказах

- `orders_v2.user_id IS NULL`, `profiles.user_id IS NOT NULL`, однозначная связка
- ~217 кандидатов

### Б2. Нормализация product_id в заказах (обязательный отдельный патч)

- 18 заказов без product_id
- Маппинг через tariff.product_id, цепочку платежей, meta
- Обновлять только при `уверенность = высокая`
- medium/low → только ручная проверка

### Б3. Сверка записей доступа (entitlements)

**Жёсткие правила:**
- запрещено создавать или восстанавливать доступ по одной только исторической сделке
- запрещено оживлять старые доступы, если они уже должны быть завершены по сроку
- запрещено продлевать доступы «по смыслу», вне существующих правил продукта

Действия:
- active подписка без entitlement → создать (основание: действующая подписка)
- paid заказ без entitlement → создать **только если есть текущее основание** (активная подписка / неистёкший срок тарифа)
- entitlement с `product_id IS NULL` → обновить product_id
- расхождение expires_at → выровнять
- `количество_дублей > 1` → только ручная проверка

### Б4. Обнаружение пропущенных подписок (только discovery)

- Все paid + tariff_id без subscription → сегментация по типу
- В этом патче **не создавать** подписки автоматически
- Только классификация и отчёт

### Б5. Просроченные активные подписки

- `status='active' AND access_end_at < now()`
- Категории: `реально_просроченная` / `ожидание_grace` / `ожидание_провайдера` / `ручная_проверка`
- Переводить в expired только `реально_просроченная`

### Б6. Итоговый proof

CSV `сверка_до_после_<ид_пакета>.csv`:
- метрика / было / стало / дельта / основание
- Для каждой созданной записи доступа — указание конкретного правила системы

## Фаза Г — Массовое продление доступа (только после Б)

### Жёсткий STOP-guard

- Массовое продление доступно **только** для уже валидных текущих доступов
- Нельзя массово продлевать спорные, архивные, исторические или не подтверждённые системой случаи
- Если новый срок опирается не на существующее правило, а на ручную догадку — строка блокируется
- Не создаёт и не редактирует `subscriptions_v2` напрямую

### Новые файлы

| Файл | Назначение |
|---|---|
| `src/components/admin/BulkExtendAccessDialog.tsx` | Диалог массового продления |

### Изменяемые файлы

| Файл | Изменение |
|---|---|
| `src/components/admin/BulkActionsBar.tsx` | + prop `onBulkExtendAccess`, кнопка «Продлить доступ» |
| `src/pages/admin/AdminDeals.tsx` | + state/handler для диалога, проверка eligibility |

### Диалог — 3 шага

**Шаг 1 — Настройка:**
- Количество дней
- Режим: продлить (от текущего конца) / выдать (от сегодня)
- Область: только доступ / доступ + Telegram / без Telegram

**Шаг 2 — Предпросмотр (обязательный, блокирующий):**

Для каждой выбранной сделки таблица:
- номер сделки / email / продукт / текущий срок / целевой срок / режим / Telegram / результат / причина

Результат: `применить` / `пропустить` / `заблокировано`

Eligibility: пропускать если нет user_id, нет product_id, родительский split, защищённый, canceled/refunded, дубли доступов, новый срок ≤ текущего (идемпотентный guard)

**Шаг 3 — Выполнение:**
- Вызов `grant-access-for-order` для каждой строки с результатом `применить`
- Построчная таблица результатов: успех / пропущено / ошибка
- Кнопка закрытия только после отображения итога

### Кнопка в BulkActionsBar
- Показывается только при `canEdit === true`
- Активна только если есть хотя бы 1 eligible сделка (status=paid, product_id не null, user_id не null, не split_parent)
- Иначе disabled с tooltip

## Критерии завершения

### Аудит
- 10 CSV с ид_пакета в именах
- Каждая проблемная строка в конкретной категории
- Развилка по основанию доступа для каждой записи
- Унифицированный поиск доступов по двум ключам

### Исправление данных
- 0 исправимых paid-заказов без user_id
- 0 high-confidence заказов без product_id
- 0 активных подписок без доступа среди разрешённых к исправлению
- 0 просроченных активных подписок в категории `реально_просроченная`
- Дубли доступов не созданы
- Proof до/после сохранён
- audit_logs записаны
- **Нет ни одной новой записи доступа, созданной без доказанного основания**

### Вкладка «Доступы»
- Показывает только текущие активные доступы по умолчанию
- Просроченные скрыты, доступны через toggle
- Исторические покупки не превращаются в активные доступы

### Массовое продление
- Кнопка «Продлить доступ» в bulk actions
- Предпросмотр обязателен
- Построчные причины пропуска видны
- Идемпотентный guard: новый срок ≤ текущего → пропуск
- Защищённые случаи не обрабатываются
