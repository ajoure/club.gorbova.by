## Почему это исключает повторное исполнение и сохраняет parity ledger↔файлы

- Любой будущий прогон миграций (managed sync, локальный `supabase db push`, восстановление окружения) берёт версии из имён файлов. Версия `20260814134846` в ledger отсутствует, поэтому такой файл был бы применён **повторно**. SQL идемпотентен по DDL (`DROP POLICY IF EXISTS`, `CREATE OR REPLACE`), но повторное применение всё равно создаёт вторую запись ledger, расхождение истории и риск отката ручных пост-правок политик.
- После удаления остаётся ровно один файл на одну ledger-версию: `20260814161253` ↔ одноимённый файл. Достигается 1:1 parity, диагностика и будущие ревью читают ту же SQL, что реально применена в production.
- Схема не меняется: удаляется только файл-дубликат, DDL уже в базе.

## Hard stop conditions

- `git diff` PR содержит что-либо кроме одного удаления файла и одной изменённой строки импорта — стоп.
- В ledger обнаружена версия `20260814134846` или отсутствует `20260814161253` — стоп, реконсиляция пересматривается.
- SQL-тела двух файлов оказались не byte-equivalent (кроме финального `\n`) — стоп.
- Падение `vitest` / typecheck / build либо GitHub checks — стоп, без merge.
- После merge managed sync читает SHA, отличный от merged SHA — стоп до Publish.
- Publish только после production UI proof на менеджерском доступе: runtime-медиана Contacts > 6052 мс или Deals > 2248 мс, расхождение row count (101 / 10), любая RLS/запросная ошибка или пропажа исторических записей — стоп без Publish.
- Любое предложение выполнить SQL, новую миграцию или откат схемы в рамках этого scope — стоп.

## Технические детали

- Тип изменения: только репозиторий. База, Edge Functions и настройки не затрагиваются.
- Порядок: PR от свежего origin/main → checks → merge → exact-SHA managed sync → UI proof → Publish.
