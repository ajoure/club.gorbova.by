План:

## 1. Проблема

Нужно проверить и исправить доступ к вебинарам строго по правилам продукта Gorbova Club:

- вебинары должны быть доступны только тарифу **Club BUSINESS**;
- доступ BUSINESS должен быть ограничен `month-gate`: пользователь видит только те месяцы вебинаров, за которые у него есть успешная оплаченная сделка/платёж с корректным `meta.deal_month`;
- **Club FULL** не должен видеть вебинары, потому что его правило на «Базу знаний» не включает вебинарные модули;
- **Club CHAT** не должен видеть вебинары;
- **ИДЕОЛОГИЯ** пока не должна видеть вебинары;
- пользователи без активного доступа к **Gorbova Club BUSINESS** не должны видеть вебинары вообще;
- новые успешные оплаты должны автоматически получать `meta.deal_month`, иначе month-gate не сможет корректно открыть нужный месяц.

Убираю из плана непонятные «количества когорт». Это не бизнес-логика, а только выбор тестовых примеров. В плане будет не «3/2/1 контакта», а обязательные сценарии проверки.

## 2. Диагностика

Фактические правила, найденные сейчас:

### Правило Club BUSINESS

`access_rules.id = 70510431-53ef-4b36-9dc3-acb5d8698834`

- `product_id = Gorbova Club`
- `tariff_id = BUSINESS`
- `target_ref = База знаний`
- `conditions.access_mode = partial`
- `conditions.match_purchase_month = true`
- `allowed_module_ids` содержит root «Вебинары» и вебинарные месячные модули.

Это единственное правило, которое должно открывать вебинары Club-клиентам, и только через month-gate.

### Правило Club FULL

`access_rules.id = 19b66114-022f-49f7-a092-fbeb3db4a566`

- `product_id = Gorbova Club`
- `tariff_id = FULL`
- `target_ref = База знаний`
- `conditions.access_mode = partial`
- `allowed_module_ids` не содержит вебинарных модулей.

Вывод: **FULL вебинары не получает**. Это корректно по текущим правилам.

### Правило Club CHAT

Есть smoke/test правило для CHAT, но оно не включает вебинары. По бизнес-логике CHAT не имеет доступа к базе знаний/вебинарам. Значит **CHAT вебинары не получает**.

### ИДЕОЛОГИЯ

Отдельного правила на вебинары для ИДЕОЛОГИИ нет. Значит **ИДЕОЛОГИЯ вебинары не получает**.

### Подозрительные standalone-правила

Найдены активные `training_content` правила на root «База знаний» для отдельных продуктов, без `tariff_id`, например:

- `a377fb0b...` — продукт «БЕЗОПАСНОСТЬ...», allowed один вебинар 2025-01;
- `ecf3e655...` — продукт «Как не платить штрафы», allowed один вебинар 2025-09;
- `417e5071...` — продукт «Налоговый кодекс-2026», сейчас `access_mode='full'` после предыдущего фикса.

Важная поправка: это **не значит автоматически “видно всем вообще без покупки”**. В текущем client read-path правило применяется только если у пользователя уже есть entitlement по соответствующему `product_id`. Но это всё равно потенциальный баг для задачи вебинаров, потому что вебинарные модули имеют `product_id = Gorbova Club`, а доступ к вебинарам должен определяться только Club BUSINESS + month-gate, а не standalone-продуктами.

Отдельно нужно проверить, не создают ли эти standalone-правила обход вебинарного default-deny через synthetic/legacy entitlement path или через `access_mode='full'` на «Базу знаний».

## 3. Предлагаемое решение

### A. Зафиксировать инвариант доступа к вебинарам

Инвариант:

```text
Вебинарный модуль доступен пользователю только если:
1) есть активный доступ/entitlement к Gorbova Club,
2) есть тариф BUSINESS или entitlement с meta.tariff_id = BUSINESS,
3) модуль входит в BUSINESS access_rule,
4) если у модуля есть content_month — есть paid orders_v2 с meta.deal_month = content_month по BUSINESS,
5) статус оплаты успешный, source != rule_engine.
```

Все остальные случаи:

- FULL без BUSINESS -> 0 вебинаров;
- CHAT -> 0 вебинаров;
- ИДЕОЛОГИЯ -> 0 вебинаров;
- standalone-продукты -> 0 вебинаров в разделе Club webinars;
- нет Club BUSINESS -> 0 вебинаров;
- BUSINESS есть, но нет оплаты нужного месяца -> вебинар виден как locked/нет доступа к месяцу, без открытия уроков.

### B. Исправить `meta.deal_month` для новых оплат

Добавить безопасный database-trigger на `orders_v2`:

- срабатывает на INSERT/UPDATE;
- если `status='paid'` и `meta.deal_month` пустой;
- выставляет месяц из `deal_date` или `created_at` в формате `YYYY-MM` по timezone Europe/Minsk;
- не перезаписывает уже заданный месяц;
- пишет технический маркер в meta, например `deal_month_source='auto_trigger'`.

Это решает кейс Ирины Тройнич и все будущие оплаты: новая успешная оплата сразу получает месяц для month-gate.

### C. Проверить и закрыть обход standalone-правил

Перед изменениями будет dry-run:

1. найти все активные `training_content` правила на root «База знаний», которые:
  - не относятся к `product_id = Gorbova Club` + `tariff_id = BUSINESS`,
  - но прямо или косвенно открывают вебинарные модули;
2. отдельно проверить правила с `access_mode='full'` на «База знаний» для standalone-продуктов, потому что `full` может открыть все дочерние модули root, включая «Вебинары»;
3. проверить текущий runtime: `useActiveTrainingContentRules`, `resolveTrainingContentFilter`, `useSidebarModules`, `useModuleMonthGate`, `useMonthGate`.

Если dry-run подтвердит обход, исправление будет одним из безопасных вариантов:

- либо деактивировать/сузить standalone-правила, которые открывают вебинары;
- либо добавить в read-path жёсткий guard: для ветки root «Вебинары» разрешать только правило `Gorbova Club + BUSINESS + match_purchase_month=true`, остальные `training_content` правила на webinar subtree игнорировать.

Приоритетный вариант — **guard в read-path + точечная чистка правил**, чтобы не сломать standalone-продукты вне вебинаров.

### D. QA без «искусственных количеств когорт»

Будет проверена не “когорта 3/2/1”, а обязательная матрица сценариев:

1. **BUSINESS, одна успешная оплата за месяц X**
  Ожидание: открыт только вебинар месяца X; остальные месяцы locked/закрыты.
2. **BUSINESS, несколько успешных оплат за разные месяцы**
  Ожидание: открыты только эти месяцы; месяцы без оплат закрыты.
3. **BUSINESS, есть оплата, но у заказа нет `meta.deal_month**`
  Ожидание после фикса/backfill: месяц восстановлен, соответствующий вебинар открыт.
4. **FULL без BUSINESS**
  Ожидание: 0 доступных вебинаров.
5. **CHAT**
  Ожидание: 0 доступных вебинаров.
6. **ИДЕОЛОГИЯ**
  Ожидание: 0 доступных вебинаров.
7. **Standalone-продукт, который исторически связан с одним вебинаром**
  Ожидание: 0 доступных вебинаров в Club webinars, если нет BUSINESS.
8. **Нет активного Club/BUSINESS доступа**
  Ожидание: 0 доступных вебинаров.
9. **Исторические оплаты 2025 года**
  Ожидание: каждый paid order с `deal_month=2025-MM` открывает только соответствующий вебинар 2025-MM.
10. **Свежая сегодняшняя оплата, например Ирина Тройнич / «Бухгалтерия как бизнес» или релевантный Club BUSINESS кейс**
  Ожидание: paid order получил `deal_month`; если это BUSINESS Club — месяц сразу участвует в доступе; если это не Club BUSINESS — вебинары не открываются.

## 6. Dry-run

Перед execute:

1. SQL-аудит всех активных `training_content` правил на root «База знаний»:
  - `product_id`, `tariff_id`, `target_ref`, `access_mode`, `allowed_module_ids`, `match_purchase_month`;
  - какие из них затрагивают webinar subtree.
2. SQL-аудит всех вебинарных модулей:
  - `id`, `parent_module_id`, `product_id`, `content_month`, `is_active`.
3. SQL-аудит заказов с `status='paid'`, где `meta.deal_month` пустой:
  - отдельно по Club BUSINESS;
  - отдельно по всем продуктам, чтобы не смешивать вебинарный доступ с другими продуктами.
4. Runtime-аудит 10 реальных пользователей по сценариям выше:
  - их активные подписки;
  - paid orders;
  - `deal_month`;
  - результат `has_month_purchase_bulk`;
  - ожидаемый/фактический доступ по каждому вебинарному месяцу.
5. Отдельный dry-run по Ирининой сегодняшней оплате:
  - найти заказ;
  - определить, почему `deal_month` не проставился;
  - показать, что trigger исправит будущие оплаты и какой backfill нужен для текущей.

## 7. Execute

После approval:

1. Установить trigger автозаполнения `orders_v2.meta.deal_month`.
2. Сделать точечный backfill только для paid-заказов без `deal_month`, где месяц однозначно выводится из даты сделки.
3. Если dry-run подтвердит обход вебинаров standalone-правилами:
  - применить минимальный guard/cleanup, который гарантирует: webinar subtree открывается только Club BUSINESS rule;
  - не ломать standalone-продукты за пределами вебинаров.
4. Сформировать proof-файлы.
5. Провести повторный verify по всем сценариям.

## 8. STOP-guards

Работу остановить, если:

- найдено больше ожидаемого количества правил, затрагивающих webinar subtree;
- у paid-заказов без `deal_month` невозможно однозначно определить месяц;
- backfill затрагивает не только `status='paid'`;
- dry-run показывает, что cleanup standalone-правила сломает доступ к не-вебинарному продукту;
- `has_month_purchase_bulk` расходится с фактической историей paid orders;
- для Ирины найден продукт не Club BUSINESS и бизнес-ожидание отличается от текущего правила.

## 9. DoD

Задача считается выполненной, когда:

- новые paid-заказы автоматически получают `meta.deal_month`;
- Ирина/аналогичный свежий paid-заказ имеет корректный месяц;
- BUSINESS видит только оплаченные месяцы вебинаров;
- FULL видит 0 вебинаров;
- CHAT видит 0 вебинаров;
- ИДЕОЛОГИЯ видит 0 вебинаров;
- standalone-продукт без Club BUSINESS не открывает Club webinars;
- пользователь без активного Club BUSINESS не видит вебинары;
- proof-файл содержит таблицу expected/actual по сценариям;
- нет ручных вставок доступов и нет второго source of truth.

## 10. Риски и зависимости

- Старые правила standalone-продуктов могли использоваться как бонусный доступ к отдельным материалам. Поэтому cleanup выполняется только после dry-run и максимально точечно.
- `access_mode='full'` на root «База знаний» для standalone-продукта потенциально опасен: он может расширять доступ шире, чем предполагалось.
- `deal_month` зависит от корректной даты сделки; если дата оплаты и бизнес-месяц отличаются, такие строки нужно помечать для ручной проверки, а не чинить автоматически вслепую.
