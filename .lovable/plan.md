## 3. Разрывы против origin/main 81b3ea6b

1. **Business-ветка не вызывает AI.** Вебхук обрабатывает `business_message` и возвращает
   ответ раньше блока AI; `invokeAISupport` вызывается только в ветке транспорта `bot`.
   Нужен вызов генерации внутри business-ветки с явным `transport='business'`,
   `business_connection_id`, `business_account_id` и chat_id личного диалога.
2. **Нет различия «ручное сообщение Екатерины» и «ответ AI».** Исходящие из business-ветки
   пишутся как owner-сообщения; отдельного признака автора (manual / ai) в контракте нет.
   Без него правило «ручной ответ → пауза AI» нельзя реализовать без ложных срабатываний
   на собственное эхо.
3. **Дедупликация.** Для business есть уникальный индекс
   `(bot_id, business_connection_id, telegram_user_id, message_id)`; отдельного
   `telegram_update_id`-индекса, как у транспорта `bot`, нет. Атомарность генерации
   (один ответ на одно входящее) требует собственного ключа идемпотентности.
4. **Пауза не отменяет уже запущенную генерацию.** Проверок состояния диалога
   в момент отправки нет; AI-hold работает только через `ai_handoffs`, ключ которых —
   `telegram_user_id + bot_id`, без транспорта и без этапа продажи.
5. **Внутреннее поручение невозможно с сервера.** `assign_contact_center_dialog_v2`
   требует `auth.uid()` и права `communication/manage`, выбирает сообщение только по
   `user_id` без фильтра транспорта; `contact-center-assignment-notify` требует JWT сотрудника.
   Серверный сценарий (AI молча зовёт человека) упирается в оба гейта.
6. **Возобновление с контекстом.** Хранилища этапа диалога, факта приветствия и
   «последний ответ — человек → WAIT_CUSTOMER» нет. Нужна отдельная строка состояния диалога.
7. **Точные офферы.** Ответы должны опираться на 12 UUID офферов выше, а не на текстовые цены.

## 4. Узкий GitHub-first план (реализация — Codex, отдельная ветка и PR)

1. **PR-A (данные состояния, additive):** таблица состояния AI-продаж по диалогу
   (bot_id, business_connection_id, telegram_user_id, state: OFF/ACTIVE/PAUSED/WAIT_CUSTOMER/HANDOFF,
   stage, greeted_at, last_human_reply_at, trigger_matched_at, версия скрипта), RLS + GRANT,
   уникальность на диалог, ключ идемпотентности на входящее сообщение.
2. **PR-B (вебхук):** в business-ветке после сохранения — проверка стартового условия
   (точная фраза анкеты, значение задаётся настройкой, пока unset), состояние диалога,
   и только затем постановка задачи на генерацию. Пауза и WAIT_CUSTOMER проверяются
   и до генерации, и непосредственно перед отправкой.
3. **PR-C (различение авторства):** явная пометка исходящих (manual / ai / operator)
   и правило: любое ручное сообщение владельца в диалоге переводит состояние в PAUSED.
4. **PR-D (тихая эскалация):** при сложном вопросе — без фразы «сейчас уточню»,
   состояние HANDOFF, внутреннее поручение сотруднику через существующий контакт-центр
   серверным путём (отдельная функция с сервисным контекстом и аудитом вместо JWT-гейта).
5. **PR-E (UI):** в выбранном диалоге кнопки «включить / пауза / продолжить»;
   продолжение сохраняет историю, этап и ответы человека, повторное приветствие запрещено.
6. **PR-F (офферы и стиль):** ответы берут ровно 12 офферов и даты потока из БД;
   стиль — из ранее собранных реплик; знания: обычный ЦБ + 20 поток + его созвоны.

Порядок: код и тесты в GitHub → ревизия → merge с точным SHA → применение миграции →
деплой только перечисленных функций → проверки → Publish отдельно.
