План:

1. **Проблема**

- Сейчас самостоятельная регистрация работает только для части старых профилей.

- Кнопка **«Отправить приглашение»** показывается только когда у контакта **нет `user_id` и есть email**. Поэтому у Ирины из Telegram её нет: у неё есть Telegram ID, но в профиле нет email.

- Обнаруженная фактическая причина: backend-функция привязки нового пользователя ищет старый профиль только со статусами `archived` и `imported`. Но в базе есть старые/импортированные профили без аккаунта со статусами `active`, `blocked`, `banned` и разными `source` — они не подхватываются при регистрации и создается новый профиль или регистрация ломается конфликтами.

- По письмам: текущие логи показывают, что `auth-actions` отправляет через Yandex SMTP и пишет `sent`, но домен Lovable Emails `sent.gorbova.by` сейчас в статусе **Pending DNS**. Это может ломать/задерживать системную доставку auth-писем и должно быть явно диагностировано в отчете. Отдельно проверю, не уходит ли часть писем через старый `auth-email-hook`/очередь вместо канонического `auth-actions`.

2. **Диагностика**

- Проверить фактический состав профилей без auth-аккаунта:

  - `status/source` распределение;

  - наличие email;

  - дубли по email;

  - конфликты `telegram_user_id`;

  - реальные последние ошибки auth/edge/email логов.

- Проверить текущую `handle_new_user()` и триггер на создании auth-пользователя.

- Проверить `auth-actions.reset_password` и `confirm_signup`: какие статусы он считает импортированными, что делает при отсутствии auth-пользователя, где пишет audit/email log.

- Проверить UI карточки контакта: почему кнопка приглашения зависит только от `!user_id && email`, и не вводит ли это в заблуждение для Telegram-only гостей.

3. **Предлагаемое решение**

- Сделать единый канонический claim-flow для регистрации старых профилей:

  - при новом signup искать существующий профиль по нормализованному email, если `user_id IS NULL`;

  - разрешить claim не только `archived/imported`, но и безопасные legacy-кейсы без аккаунта: `active`, `blocked`, старые import/manual/site_form источники;

  - не claim-ить `banned` автоматически без отдельного решения, чтобы не снять бан случайно;

  - если найден профиль — привязать `user_id`, сохранить существующий `profile.id`, перевести только допустимые статусы в `active`, перенести orders/subscriptions/entitlements как уже делает текущая функция;

  - писать audit log с причиной claim и старым статусом/source.

- Обновить `auth-actions`:

  - при `reset_password` авто-создавать auth-пользователя для любого безопасного профиля без `user_id` и email, а не только для `status IN ('archived','imported')`;

  - возвращать администратору/клиенту понятный результат, но без утечки существования email в публичном режиме;

  - писать подробный audit/email-log: найден профиль, создан auth-user, письмо сгенерировано, письмо отправлено/ошибка.

- Исправить signup UX:

  - если пользователь вводит email старого профиля и регистрируется сам — он не должен попадать в тупик «уже зарегистрирован / письмо не пришло»;

  - после signup отправлять подтверждение через существующий `auth-actions.confirm_signup`, но добавить fallback/логирование ошибок.

- Исправить UI карточки контакта:

  - показывать приглашение для всех контактов без аккаунта **с email**, независимо от статуса `active/imported/archived`;

  - для Telegram-only контактов без email показать не кнопку приглашения, а понятный бейдж/tooltip «нужен email для приглашения», чтобы было ясно почему кнопки нет.

4. **Изменяемые компоненты**

- Database/RPC/trigger:

  - `public.handle_new_user()` — расширение логики claim существующего профиля по email.

  - При необходимости вспомогательная SQL-функция для нормализации email/выбора claimable profile, если текущая функция станет слишком большой.

- Edge functions:

  - `supabase/functions/auth-actions/index.ts` — расширить auto-provision для legacy профилей без аккаунта и усилить логирование.

- UI:

  - `src/components/admin/ContactDetailSheet.tsx` — условия/подсказки для кнопки «Отправить приглашение».

  - При необходимости `src/pages/Auth.tsx` и `src/hooks/useInlineAuth.ts` — только если диагностика покажет, что самостоятельная регистрация обрабатывает ошибку неправильно.

- Email infra:

  - read-only проверка статуса домена/логов; не менять DNS автоматически.

5. **Что не будет изменено**

- Не буду массово создавать auth-аккаунты всем 11k+ импортированным пользователям без явного отдельного решения.

- Не буду автоматически разблокировать `banned` профили.

- Не буду менять платежи, entitlements или CRM вне переносов, которые уже являются частью claim-flow.

- Не буду добавлять новую параллельную систему приглашений.

6. **Dry-run**

- Перед миграцией выполнить SELECT-проверки:

  - сколько профилей попадут в claimable statuses;

  - сколько исключены как `banned`;

  - есть ли дубли email;

  - какие профили имеют email + `user_id IS NULL` и почему сейчас кнопка/регистрация не работают.

- Проверить function logs `auth-actions` и email logs по последним жалобам.

- Смоделировать на безопасном тестовом профиле без массовых UPDATE:

  - signup существующего legacy email;

  - reset password existing legacy email;

  - Telegram-only профиль без email.

7. **Execute**

- Внести SQL-миграцию с обновленной `handle_new_user()` и audit logging.

- Обновить `auth-actions` и задеплоить функцию.

- Обновить UI карточки контакта для прозрачного статуса приглашения.

- Если найдена проблема в `auth-email-hook`/очереди или DNS pending — зафиксировать в отчете как отдельную внешнюю/инфраструктурную причину и предложить/выполнить безопасный backend-фоллоу-ап без ручных секретов.

8. **STOP-guards**

- Остановиться, если dry-run показывает массовый claim `banned` или профилей с неоднозначным email-дублем.

- Остановиться, если `handle_new_user()` уже имеет другую более новую claim-логику, чтобы не откатить последние патчи.

- Остановиться, если письмо не отправляется из-за DNS/domain pending и требуется действие владельца домена.

- Остановиться, если тестовый signup может затронуть реального клиента без явного тестового профиля.

9. **DoD**

- Для архивного/imported/legacy профиля без `user_id` и с email самостоятельная регистрация создает auth-user и привязывает существующий `profiles.id`, а не создает дубль.

- `reset_password` для такого профиля автоматически создает auth-user и отправляет письмо без ручного приглашения.

- В `audit_logs` виден claim/profile_link event, в `email_logs` видна попытка отправки письма с результатом.

- В карточке контакта понятно, почему кнопка приглашения есть или отсутствует.

- Проверено симуляцией: один claimable профиль с email, один уже привязанный профиль, один Telegram-only профиль без email.

10. **Риски и зависимости**

- Доставка писем зависит от DNS/почтовой инфраструктуры; код может корректно отправить SMTP, но письмо может попадать в спам или не доставляться из-за домена в Pending.

- У старых данных могут быть дубли email; их нельзя автоматически привязывать без правила приоритета.

- `banned` аккаунты требуют отдельного бизнес-решения: регистрировать их или оставлять заблокированными.
