# Ревизия кода CDC-фикстуры (PR724 `20e839c1…`) — только собственный пустой target

Режим: только чтение. Код не запускался, к базе не подключался, файлы проекта не менялись. Production-источник не затронут. Этот файл содержит только ревизию — режим планирования требует его создать.

## Вердикт: FAIL до исправления B1–B3, затем условный PASS

Блокеры ниже ломают тесты, а не безопасность. Каждый из них останавливает прогон отказом при первом же `drain` и запускает очистку. Вред target не наносится, но запускать прогон бессмысленно: результат будет «FAIL T1».

## Блокеры

**B1. bytea (уверенность высокая).** wal2json формирует значение через функцию вывода типа в сессии читателя. Там `bytea_output='hex'`, поэтому значение приходит как `\x00ff0a`. `value('raw')` отвергает `\` и выдаёт `unsupported_bytea_encoding` уже на первом INSERT в T1.
Исправление: проверять `^\\x([0-9a-f]{2})*$` и передавать `CAST(%s AS bytea)` — либо `decode(substr(%s,3),'hex')`. Офлайн-тест должен принимать `\xdead`, а отвергать «голый» hex, escape-формат и нечётную длину.

**B2. json/jsonb (уверенность высокая; проверить на fixture).** wal2json выводит значения json/jsonb без кавычек, как вложенный JSON. После `json.loads` значение становится `dict`. psycopg не умеет передать dict в `CAST(%s AS json)`, поэтому T1 упадёт.
Исправление:
- если значение не строка, сериализовать его через `json.dumps(v, ensure_ascii=False, separators=(',',':'))` с `object_pairs_hook`, сохраняющим порядок и дубликаты ключей;
- если внутри встретился Decimal (дробное число), отказ `json_float_unsupported`;
- принимать и вариант со строкой.

Ограничение: для типа `json` (не jsonb) побайтное совпадение доказуемо только для фикстур в компактной канонической форме — `{"fixture":1}`, `{"zero":"\u0000"}`. Пробелы и форма escape в общем случае не восстанавливаются. Это зафиксировать в `known_production_gaps`.

**B3. xid в событиях I/U/D/T (UNKNOWN, предлагаю защитное исправление).** В format-version 2 `include-xids` гарантированно добавляет xid в B и C. В записях изменений xid может отсутствовать. Сейчас пустой xid даёт `change_outside_transaction`.
Исправление: событие внутри открытой транзакции принимать без xid. Отказывать, только если xid присутствует и не совпадает. Добавить два офлайн-теста: «без xid — принято» и «чужой xid — отказ».

## Существенные замечания (не блокеры, исправить в том же PR)

- **N1. Восстановление после сбоя между CREATE и сохранением манифеста.** Если сбой произошёл после `pg_create_logical_replication_slot` или `CREATE SCHEMA`, но до `save_manifest`, флаги `*_created` остаются false. Очистка возвращает `unverified_*_ownership`. Это отказ в безопасную сторону, но очистить ресурс тогда невозможно никогда.
  Исправление: разрешить удаление при одновременном выполнении трёх условий:
  - записан `stream_creation_intent` или `schema_creation_intent`;
  - имя точно совпадает с nonce;
  - для потока — `plugin='wal2json'`, `database='postgres'`, `active=false`; для схемы — комментарий `gorbova-cdc-probe:<nonce>` и владелец `postgres`.
  Заодно унифицировать ключи `creation_intent` и `stream_creation_intent` и добавить intent для схемы.
- **N2. Транзакции на autocommit-соединениях.** `execute('BEGIN')`, затем `writer.commit()`/`rollback()`. Опираться на неявное поведение psycopg нельзя: в T4, T5, T9 явно выполнять `COMMIT`/`ROLLBACK` и проверять `conn.info.transaction_status == IDLE`.
- **N3. Название T9_no_partial_ack вводит в заблуждение.** Тест проверяет подтверждение без durable-записи, а не частичное подтверждение. Частичность закрывает `transactions()`. Переименовать в `T9_no_ack_before_receipt`.
- **N4. Граница T12 не проверена.** Тест не проверяет край commit_lsn, равный подтверждённому. Добавить: после advance вызвать `pg_replication_slot_advance` повторно на той же позиции (no-op, end_lsn равен) и убедиться, что peek пуст.
- **N5. T13 проверяет только штатное закрытие соединения.** Добавить `pg_terminate_backend(reader_pid)` с control-сессии во время простоя и проверить, что поток `active=false` и чтение продолжается без пропусков.
- **N6. T10 на границе.** `frames > 40` проходит ровно при 42 кадрах (B + 40 + C). Порог задать от фактического числа записей и проверять отдельно `raw_bytes > 786432`. Проверка остаётся клиентской симуляцией, а не доказательством транспорта.

## Проверено, замечаний нет

- Peek-only: `pg_logical_slot_get_changes` нигде не используется.
- Advance только после чтения durable-записи `(stream, xid, commit_lsn, digest)` из sink.
- Позиция — `C.nextlsn` (end_lsn), сверяется с ответом advance.
- Порядок задаёт commit LSN; транзакции без C отвергаются; чужие schema/table отвергаются.
- Дедупликация при потерянном ACK (T11) и изменённый digest дают отказ.
- Бюджет: TTL 300 с, удерживаемый WAL до 64 MiB, `wal_status`, `catalog_xmin` в отчёте; `statement_timeout` 15 с.
- Опции wal2json v2: `actions` включает truncate, `add-tables` только на src, numeric как строка (NaN и 30+ знаков), пустые транзакции выключены.
- TOAST: UPDATE без столбца body не затирает его (обновляются только присланные столбцы), отдельно при DEFAULT и FULL.
- Таблица без PK: DEFAULT — ожидаемая потеря UPDATE; FULL — удаляется ровно одна из дубликатов по ctid LIMIT 1. Контрпример перекрытия (3 строки, затем 2 у source и 1 у target) честно помечен как пробел.
- Изоляция: схема с REVOKE от PUBLIC/anon/authenticated/service_role; T14 проверяет триггеры, публикации, USAGE, каталог и последовательности Auth.
- Очистка: удаляется только собственный поток или схема при совпадении владельца; независимый `readback_only`.
- Режим plan-only не подключается к базе и не создаёт файлов.
