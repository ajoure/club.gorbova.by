
# ПЛАН: СВЕРКА И ОЧИСТКА ДОСТУПОВ

## ГЛАВНОЕ ПРАВИЛО (действует на все фазы)

Источником истины по доступам являются **только** действующие правила системы:
- `products_v2`, `tariffs`, `subscriptions_v2`, `entitlements`, `access_rules`
- текущие связи продукта, тарифа, тренинга и Telegram

**Запрещено:**
- вводить новую бизнес-логику доступа
- создавать доступ по одной только старой оплаченной сделке
- оживлять истекшие исторические доступы без текущего основания
- выдавать доступ по архивным или неактуальным продуктам
- использовать массовое продление для спорных или исторических случаев
- связывать продукты вручную «по смыслу»

**Обязательная классификация** для каждой сделки/записи доступа:
1. `есть_текущее_основание`
2. `основание_историческое_и_истекло`
3. `основание_не_доказано`
4. `архивный_или_неактуальный_продукт`
5. `защищенный_случай`

Без классификации переход к исправлениям запрещён.

## ФАЗА Б — Исправления данных только по доказанным текущим основаниям

### Б1. Восстановление `user_id` в сделках
- Связка: `orders_v2.profile_id → profiles.user_id`
- Только при однозначном соответствии (1 профиль = 1 user)
- Proof: до/после для каждой строки

### Б2. Восстановление `product_id` в сделках
- Цепочка: `orders_v2.tariff_id → tariffs.product_id`
- Fallback: `payments_v2.product_code → products_v2.code`
- Только high-confidence связки
- Proof: до/после + источник связки

### Б3. Нормализация записей доступа (entitlements)

**Действия строго по классификации:**
- `создать_запись_доступа` — **только** если подтверждено действующее основание на текущую дату (активная подписка, действующий тариф, действующее правило в access_rules)
- `обновить_запись_доступа` — только если доступ уже должен существовать и нужно лишь выровнять срок/метаданные
- `не_требует_действий` — для исторических, истёкших и архивных кейсов
- `требуется_ручная_проверка` — если система не может строго доказать текущее право доступа

**STOP-guard:**
- Запрещено создавать доступы по старым сделкам, если срок продукта/тарифа/подписки уже истёк
- Запрещено создавать доступы по архивным продуктам
- Запрещено продлевать «мёртвые» исторические доступы только по факту старой оплаты
- Историческая покупка сама по себе основанием НЕ является

### Б4. Исправление просроченных активных подписок
- `subscriptions_v2` со `status = 'active'` и `access_end_at < now()`
- Действие: перевести в `status = 'expired'`

### Б5. Аудит-лог
- Каждое изменение записывается в `audit_logs` с `batch_id`
- Действие: `entitlement.repaired` / `subscription.expired` / `order.user_id_backfilled`

### Б6. Proof до/после
- Для каждой созданной/обновлённой записи показать:
  - `подтверждающее_основание_доступа` — конкретное правило/подписка
  - `источник_правила_доступа` — таблица, ID, поля
  - Почему запись должна существовать именно сейчас
- Если подтверждение невозможно — это ошибка, запись не создаётся

## ФАЗА Г — Массовое продление только для валидных текущих доступов

**Порядок:** Фаза Г запускается только после завершения Фазы В.

### Г1. Компонент `BulkExtendAccessDialog.tsx`
- 3 шага: Настройка → Предварительный просмотр → Выполнение
- В preview строка допускается к применению только если это валидный текущий доступ
- Исторические, архивные, спорные, не подтверждённые системой случаи → `пропустить` или `заблокировано`
- Нельзя использовать bulk-extend как способ «оживить» старые сделки

### Г2. Гард основания (обязательный)
- Каждая строка в preview проверяется на наличие действующего основания
- Если основание не доказано — строка блокируется с пояснением
- Идемпотентный гард: запрещено сокращать текущие сроки доступа

### Г3. Интеграция
- Добавить кнопку «Продлить доступ» в `BulkActionsBar.tsx`
