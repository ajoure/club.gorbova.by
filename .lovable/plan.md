## Stage 5.0.2 — UI карточки документа

Только `PackageDocumentCard.tsx` и его child-компоненты. Бизнес-логика и атомарный save не трогаются.

1. **Нумерация документов.** Сейчас единственный документ показывается как «#2 …». Номер слева от заголовка = `index + 1` по отрисованному отсортированному списку документов сессии (а не `sort_order`). Один документ → «1».
2. **Поля — одностолбцовый layout.** Убираем 2-колоночный grid. Все `FieldRow` друг под другом, одинаковой ширины, одинаковой высоты инпута (date/text/textarea — общий wrapper, фиксированный min-height). Лейбл сверху, инпут под ним, под инпутом — только бейджи «общее значение / обязательное» и краткий error-hint.
3. **Tooltip с описанием поля.** Справа от лейбла — иконка `Info` (lucide, `icon-xs`, `text-muted-foreground` → `text-foreground` на hover). При hover/focus — shadcn `Tooltip` с `description` из catalog. Если описания нет — иконка не рендерится. Tooltip полупрозрачный (`bg-popover/95 backdrop-blur`).
4. **Симметрия и плотность.** Единый `space-y-4`, одинаковая высота `Input` и кастомного date-picker, единый стиль `Badge`. Прогресс полей и ролей переносим в шапку карточки одной строкой.
5. **Никаких технических ID** (FLD-/pf-/UUID) в основном UI. Допустимо только внутри tooltip / dev-режима.

Файлы: `src/components/ai-documents/packages/PackageDocumentCard.tsx`, `PackageFieldsClientForm.tsx`, при необходимости — мелкий helper `FieldRow`.

## Stage 5.0.3 — Контракт наименования ЮЛ и колонки «Пример» (без новой логики)

### Канонический контракт (single source of truth)

Для юридического лица три независимые сущности:

| Сущность | Пример | Что это |
|---|---|---|
| `org_form_short` | `ЗАО` | Форма собственности, кратко. Без кавычек. |
| `org_form_long` | `Закрытое акционерное общество` | Форма собственности, развёрнуто. Без кавычек. |
| `name` (чистое) | `АЖУР инкам` | Без формы собственности, без внешних кавычек. |
| `short_name` | `ЗАО «АЖУР инкам»` | Составное краткое. Кавычки `«…»` только вокруг чистого name. |
| `full_name` | `Закрытое акционерное общество «АЖУР инкам»` | Составное полное. Те же правила. |

Запрещённые выводы (never): `«ЗАО»`, `ЗАО «ЗАО «АЖУР инкам»»`, `«ЗАО «АЖУР инкам»»`, `ЗАО / «ЗАО «АЖУР инкам»»`. Двойные кавычки и дублирование формы собственности — баг.

### Не писать новую логику — переиспользовать billing

Перед любой правкой провести аудит:

1. SQL по `fields_registry`: точные `key`, `label`, `options`, `deprecated_at`, `replaced_by` для всей группы legal_details + executor + customer. Зафиксировать в proof реальный контракт `FLD-000103` (`customer.name`) и `FLD-000104` (`customer.short_name`) — что они отдают: чистое name, short_name или full_name.
2. Поиск всех resolver-веток (`supabase/functions/_shared/` + клиентских utils): найти canonical helper, который уже формирует для billing-документов `org_form_short`, `org_form_long`, чистое `name`, `short_name`, `full_name`, типографские кавычки `«…»`, защиту от двойных кавычек и дублирования org_form.
3. Поиск использования в billing-шаблонах: убедиться, что в реальной генерации billing нет регрессии.
4. Runtime-пример billing-документа до правок (plain-text через pandoc) — baseline.

Если canonical helper найден — package resolver вызывает **тот же** helper. Если нет — извлекаем shared util из существующего billing-кода **без изменения** billing-поведения и подключаем обе ветки. Никаких параллельных словарей и копий нормализации.

### Нормализация входа

Helper должен принимать любой из вариантов входа и давать один результат:

```
вход                              → чистое name
АЖУР инкам                        → АЖУР инкам
«АЖУР инкам»                      → АЖУР инкам
ЗАО «АЖУР инкам»                  → АЖУР инкам
"АЖУР инкам"                      → АЖУР инкам
```

Сборка составных идёт уже из чистого `name` + выбранной формы.

### Семантика модификаторов package namespace

```
package.ul.FLD-000010                 → ЗАО
package.ul.FLD-000010|format=long     → Закрытое акционерное общество
package.ul.FLD-000010|format=full     → Закрытое акционерное общество  (alias на long)
```

Если billing helper использует один из вариантов `long`/`full` — package-ветка адаптирует modifier к существующему канону, **не** создаёт вторую реализацию.

### Resolver-тесты (exact strings)

Добавить unit-тесты с точными ожидаемыми строками:

```
package.ul.FLD-000010                 → ЗАО
package.ul.FLD-000010|format=long     → Закрытое акционерное общество
<token чистое name>                   → АЖУР инкам
<token short_name>                    → ЗАО «АЖУР инкам»
<token full_name>                     → Закрытое акционерное общество «АЖУР инкам»
```

Плюс normalization-тесты: входы `АЖУР инкам`, `«АЖУР инкам»`, `ЗАО «АЖУР инкам»`, `"АЖУР инкам"` → одинаковый результат, без двойных кавычек.

### Шапка приказа

Не «чинить визуально». Решение зависит от смысла токена в шаблоне:

- два отдельных токена (`org_form_long` + чистое `name`) → допустим вывод вида «Закрытое акционерное общество / «АЖУР инкам»» (если так стоит в шаблоне);
- один токен `full_name` → `Закрытое акционерное общество «АЖУР инкам»`;
- один токен `short_name` → `ЗАО «АЖУР инкам»`.

**Шаблон DOCX не мигрируем на FLD-000103/104**, пока не доказано, что они работают в package-context (у `field:FLD-*` и `package.ul.FLD-*` разные источники данных). Предпочтительный путь: оставить package namespace, подключить shared formatter, менять токены DOCX только если текущая семантика шаблона действительно неверна — и тогда отдельным микро-коммитом с обоснованием в proof.

### Колонка «Пример» в таблице «Плейсхолдеры для Word»

Должна показывать клиенту человекочитаемые примеры, идентичные канону:

```
Форма собственности, кратко       → ЗАО
Форма собственности, развёрнуто   → Закрытое акционерное общество
Название без формы собственности  → АЖУР инкам
Краткое наименование              → ЗАО «АЖУР инкам»
Полное наименование               → Закрытое акционерное общество «АЖУР инкам»
```

Дубликат FLD-ID в строках «Краткое название» / «Название» (обе сейчас показывают `FLD-000011`) — исправить так, чтобы каждая строка соответствовала своему реальному resolver-контракту (после аудита из пункта 1). Никаких догадок по названию — только по выходу helper.

## Stage 5 — Atomic runtime proof

Без новых правок. Контракт `save_session_document_atomic`:
- field-only save → 1 audit, изменился только нужный per-item row;
- role-only save (full desired-state) → 1 audit, лишние роли удалены только в этом item;
- field+role одной транзакцией → 1 audit;
- save без изменений → no-op;
- broken payload → 4xx, dirty сохраняется, DB не меняется, success-toast не показан;
- orphan session-level значение не меняется ни в одном сценарии.

Proof: `.lovable/proofs/stage5_unified_runtime.md`.
