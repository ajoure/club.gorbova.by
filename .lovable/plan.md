# План: исправить аудиторию рассылок «Покупал когда-либо»

## Корень проблемы

Фильтр **«Покупал когда-либо»** в Контакт-центре опирается на таблицу `subscriptions_v2`, а не на реальные оплаченные заказы (`orders_v2`).

Для продукта «Ценный бухгалтер | 1 ступень 2.0» + 3 тарифа:

| Источник | Уникальных покупателей |
|---|---|
| `subscriptions_v2` (что использует фильтр сейчас) | **1** (Katerina Kaplia) |
| `orders_v2` со `status='paid'` (реальная покупка) | **210** (213 если включить заказы без tariff_id, после ранее запланированной чистки) |

`subscriptions_v2` хранит только активные подписки/рекуррентные тарифы. Все разовые покупки и исторические оплаты лежат **только** в `orders_v2`. Поэтому при попытке сделать рассылку по покупателям курса виден только 1 человек.

## Что меняем

1. Переписать SQL-функцию `resolve_broadcast_audience_user_ids`, чтобы режим `purchased` брал покупателей из **`orders_v2`** (как канонического источника коммерческих транзакций — см. `mem://commercial-logic/orders/commercial-entity-sot`), а не из `subscriptions_v2`.

2. Логика для `purchased`:
   - брать из `orders_v2` все заказы с `product_id` из правила;
   - фильтровать `status IN ('paid','active','completed')` (только реально оплаченные, без `canceled`/`pending`/`failed`);
   - применять фильтр `tariff_ids`, если он задан;
   - **исключать** синтетические заказы (`reconcile_source = 'rule_engine'`) — это требование `mem://commercial-logic/orders/synthetic-order-analytics-safety`;
   - резолвить `user_id`: сначала `orders_v2.user_id`, при NULL — через `profile_id → profiles.user_id`, при NULL — через `customer_email → profiles.email`.

3. То же самое применить к зеркальному правилу `exclude → purchased`.

4. Дополнительно вернуть в счётчике аудитории «no-channel»-покупателей (есть профиль, но нет ни telegram, ни email) только в логи, чтобы было видно, кому невозможно отправить.

## Ожидаемый результат

После патча в окне рассылки для тестового условия (продукт ЦБ-1 + 3 тарифа + «Покупал когда-либо»):
- **Аудитория ≈ 210 покупателей** (точное число зависит от того, у скольких есть telegram/email; полные цифры покажу dry-run перед применением).
- Katerina Kaplia остаётся в выборке.
- Telegram/Email-счётчики разделятся корректно.

## Порядок работ (Diagnose → Plan → Dry run → Execute → Verify)

1. **Dry-run RPC** — собрать выборку по новой логике на тестовых фильтрах и показать счётчики (всего / telegram / email / без каналов) до развёртывания миграции.
2. **Migration** — пересоздать `resolve_broadcast_audience_user_ids` с новой логикой `purchased`. Сигнатура функции и поведение для `active_access`, exclude-блока, club-фильтров, channels — не меняются.
3. **Verify** — после миграции прогнать тот же фильтр в UI, сверить с dry-run.

## Что НЕ трогаем

- Таблицу `subscriptions_v2` и связанную с ней логику подписок.
- UI Контакт-центра (RuleListEditor, BroadcastsTabContent) — контракт фильтров остаётся.
- Edge-функции `email-mass-broadcast` / `telegram-mass-broadcast` — они вызывают ту же RPC, изменение прозрачно.
- Режим `active_access` — он уже корректно смотрит в `entitlements`.

## DoD

- Для продукта ЦБ-1 + 3 тарифа + «Покупал когда-либо» аудитория ≥ 200 покупателей (вместо 1).
- Прежние рассылки в режиме `active_access` работают без изменений.
- Синтетические заказы `rule_engine` не попадают в выборку.
- Каноническая запись о изменении: `mem://architecture/communications/broadcast-audience-purchased-source-of-truth`.
