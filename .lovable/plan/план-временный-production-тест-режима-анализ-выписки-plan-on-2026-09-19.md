## 3. Порядок исполнения (после отдельного APPROVE)

1. **Создание аккаунта.** Через Admin Auth API: `email_confirm: true`, без отправки писем (никаких invite/magic-link/signup-mail), роль — обычный пользователь, никаких admin/superadmin (иначе сработает admin-bypass и тест будет недействителен).
2. **Негативный прогон (без доступа).** Вход тестовым аккаунтом → `/ai`: ожидается, что сценарий «Анализ выписки» недоступен, `ai-access-status` не отдаёт этот сценарий, прямой вызов `bank-statement-analyzer` → отказ по доступу (не 500).
3. **Выдача ровно одной временной связки.** Один INSERT в `subscriptions_v2`: выбранные product_id+tariff_id, `status='active'`, `access_end_at = now() + 2 часа`, метка в metadata. `access_rules` и тарифы не трогаются.
4. **Позитивный прогон.** Повторный вход → `/ai` на ПК (1280×800) и mobile (390×844): сценарий виден, загрузка синтетического CSV без PII (вымышленные УНП/суммы/контрагенты), получение отчёта, подтверждение блока сверки с МНС/ГРП (lookup отрабатывает и по «не найдено» тоже).
5. **Скриншоты** опубликованного URL: по одному для ПК и mobile, без персональных и платёжных данных.

## 4. Вход без раскрытия пароля

Пароль генерируется одноразово в памяти сессии исполнения, используется только формой входа через Playwright и нигде не печатается: не в чат, не в логи, не в скриншоты, не в файлы репозитория. В отчёте фиксируется только факт успешного входа. Токены и cookie не выводятся.
