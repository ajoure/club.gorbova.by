# <ORDER_NUMBER>: план исправления счёта (только план)

## Что проверено (чтение)
- Заказ: <ORDER_NUMBER>, статус pending, оплачено 0, тип плательщика entrepreneur, нужное предложение. Документов по заказу: 0.
- В предложении <INVOICE_OFFER> один сценарий: legal_entity / bank_transfer, шаблон <LEGAL_ENTITY_TEMPLATE> (ЮЛ), исполнитель <EXECUTOR_ID>, включён. Сценария для entrepreneur нет, поэтому сервер отвечает 403 document_not_enabled_for_offer.
- Шаблон <IP_TEMPLATE> («Счёт-акт ИП») активен, исполнитель <EXECUTOR_ID> активен.
- Во всех активных предложениях 13 включённых сценариев entrepreneur, и все 13 используют <IP_TEMPLATE>. Но есть исключения: часть предложений держит entrepreneur-сценарий выключенным, а <OTHER_OFFER> подключает шаблон ИП к legal_entity. Это вне задачи, не трогаем.

## Исправление (одно предложение, rowcount = 1)
1. Перед записью: заблокировать строку предложения и проверить, что в meta.document_scenarios ровно 1 элемент (id <EXISTING_SCENARIO>) и нет элемента с payer_type=entrepreneur. Иначе STOP.
2. Один UPDATE tariff_offers по id = <INVOICE_OFFER>: в конец массива добавить
   `{id: новый uuid, payer_type: entrepreneur, payment_channels: [bank_transfer], template_id: <IP_TEMPLATE>…, executor_id: <EXECUTOR_ID>…, is_enabled: true, requires_required_requisites: true}`.
   Остальной meta и сценарий legal_entity не меняются. Ожидаемый rowcount = 1, иначе откат.
3. Проверка после записи: в массиве 2 элемента, первый совпадает с исходным побайтно, второй равен добавленному. Другие ключи meta не изменились (сравнить хэш meta без document_scenarios).
4. Откат: убрать из массива только добавленный элемент по его id.
