# Полный перенос Clubguru на собственную инфраструктуру

Дата проверки: 9 ноября 2026 года, Europe/Warsaw. Статус: план, не разрешение на исполнение. Бизнес-данные обеих баз, конфигурация, функции, webhooks, DNS и публикация в ходе проверки не менялись.

## 1. Точная цель

Создать и проверить полную самостоятельную копию действующего проекта Clubguru: публичный сайт, личные кабинеты, административную часть, базу данных, учётные записи, файлы, Edge Functions, фоновые процессы, платежные и прочие интеграции. Backend разместить в существующем собственном Supabase club.gorbova.by, фронтенд и вспомогательные сервисы — в собственных аккаунтах вне Lovable. Пока копия готовится, текущий сайт продолжает работать, принимать изменения и развиваться в Lovable. Переключать пользователей только после доказанной функциональной эквивалентности и синхронизации; затем прекратить все рабочие зависимости от Lovable.

Требования: отсутствие потери подтверждённых данных, повторных списаний, сообщений и выдач доступа; отсутствие планового отключения сайта; сохранение возможности контролируемого отката. Это критерии приёмки, а не уже подтверждённые гарантии.

В этой задаче название Clubguru.by относится к обсуждаемому приложению из GitHub ajoure/club.gorbova.by и Lovable «Буква закона». Владение доменом Clubguru.by, его DNS и связь с действующими gorbova.by/club.gorbova.by ещё не проверены. Домен не переименовывать и DNS не менять до составления точного реестра всех доменов и поддоменов. Уточнение названия не мешает подготовке общей архитектуры.

Supabase покрывает backend; отказ от Lovable также требует отдельного фронтенд-хостинга, независимого CI/CD и замены его runtime AI и connectors.

Рекомендуемая стратегия:

1. Сделать полный независимый backup target: схема, данные, Auth, migration history, определения функций и конфигурация. Доказать восстановление в изолированной среде. До этого не освобождать ни одной таблицы.
2. Сохранить исходные 3 071 строки и старую структуру в закрытом восстановимом архиве с provenance. Архив не доступен Data API/обычным пользователям и не участвует в фоновых процессах.
3. За рабочую исходную версию новой базы взять текущий production. Старые target данные классифицировать: точный дубль; изменённый дубль; запись с другим ID и тем же бизнес-ключом; удалённая/погашенная запись; действительно уникальная запись; историческая конфигурация.
4. Для каждой из 805 строк и 2 266 совпавших PK составить решение. Архивное сохранение не означает автоматического включения в рабочие счета и доступы. Не восстанавливать отменённые подписки, старые права и удалённые платежи.
5. Единый реестр old target ID → source canonical ID → действие → основание. Для Auth по умолчанию сохранять canonical source UUID; архивировать прежнюю запись target, отдельно проверить все связи. Новые активные записи создавать только по проверенному решению.
6. Подготовить точный проверенный сценарий преобразования target; запрещены blind TRUNCATE/CASCADE, переименование public вслепую и импорт дампа поверх конфликтующей схемы. Проверить определения функций, search_path, default privileges и зависимости Supabase-managed схем. Каждая потеря активной строки должна быть объяснена её переносом/сопоставлением, а исходник — сохранён.

На этапе плана backup, архивирование и merge не выполнялись.

## 4. Независимая архитектура и параллельная работа

GitHub остаётся единственным источником кода. Не создавать второй расходящийся репозиторий. Текущий frontend — React 18 + Vite 6.4.3, статическая сборка. Запланировать хостинг статической сборки с HTTPS/CDN, SPA fallback, собственными preview и rollback; выбрать провайдера и стоимость перед созданием ресурсов. Это может быть управляемый хостинг или существующий пригодный сервер, но конкретный вариант пока не принят.

Выделить три окружения: действующий production Lovable; изолированная репетиционная среда; будущий production в существующем target. Новый платный ресурс требует отдельного согласования стоимости. Локальная полномасштабная репетиция сейчас не запланирована: на Mac около 22 GiB свободно, этого недостаточно для безопасного многогигабайтного restore с Docker, индексами и запасом. Текущая задача создаёт только небольшие документы и метаданные.

Новая копия защищена от индексации и случайного публичного доступа. В ней отсутствуют активные provider webhooks, автосписания, рассылки, выдача/отзыв Telegram-доступов и другие необратимые эффекты. Применить не только флаг UI, но и серверные gates/allowlists и отключённые job runners. Реальные токены провайдеров не должны позволять репетиционной среде выполнять такие операции.

Пока Lovable развивает сайт:

- Принимать только merged GitHub SHA с зелёными проверками, автоматически собирать независимый preview той же версии. Preview-копия не становится production.
- После каждого изменения схемы фиксировать migration ID, live schema hash, связанные функции и контракт данных. Source migration history и файлы GitHub сверять отдельно: их количества различаются; это не разрешение массового повторного db push.
- Для каждого переноса вести checkpoint: source SHA, target release SHA, номер согласованного снимка, cursor потока изменений, Storage manifest version, список ещё не перенесённых изменений.
- Повторять только обработку новых изменений; DDL и breaking changes применять в порядке зависимостей. Пересекающиеся изменения согласовывать с владельцем текущего scope, не останавливая прочие задачи.
- Исключить внезапное автоматическое переключение .env, домена или backend существующего проекта. Старые отключённые deploy workflows не включать поверх их прежних правил: подготовить проверяемый новый pipeline для собственного окружения.
- Перед cutover кратко зафиксировать release candidate, не блокируя доступ пользователей к сайту. Новые релизы Lovable после этого кандидата явно откладываются или включаются после повторной проверки.

## 5. Непрерывная синхронизация и отсутствие простоя

Полный экспорт — исходная копия. Он не переносит последующие INSERT/UPDATE/DELETE, смену паролей, регистрации и изменения файлов. MAX(updated_at), периодический экспорт таблиц или негарантированная двойная запись не обеспечивают отсутствие потерь.

Официальная документация Lovable для стандартного сценария предусматривает паузу записей и отдельно указывает, что приложению без паузы нужен собственный инструмент инкрементального копирования:
https://docs.lovable.dev/tips-tricks/external-deployment-hosting#complete-a-move-away-from-lovable

До обещания бесшовного переключения выполнить техническую проверку одного из поддерживаемых вариантов:

1. Предпочтительно: согласованный snapshot + CDC/logical replication с известным LSN/эквивалентным курсором и replay. Доступность в Lovable Cloud не доказана; не пытаться получить DB password или обходить managed boundary.
2. Если native CDC недоступен: отдельно разработать и проверить транзакционный журнал изменений/outbox либо поддерживаемый migration bridge через официальный Lovable. Он должен покрывать все writers и таблицы, UPDATE/DELETE, порядок транзакций, повторы, схемы и long transactions. Journal начинает работать до baseline и сохраняется до завершения отката. Особо доказать покрытие Auth и файлов; прикладные public-триггеры не покрывают их автоматически.
3. Если ни один вариант не обеспечивает полноту и cutover fencing, статус «без остановки записи» остаётся BLOCKED. Существующий сайт продолжает работать. Переход по приблизительно совпавшим counts недопустим; короткую паузу записи нельзя подменять обещанием нулевого простоя.

Источник остаётся единственным владельцем записей до точки переключения. Нельзя делить финансовые записи между двумя активными backend. В точке cutover требуется проверенная передача владения: старые writer leases истекли/заблокированы, target догнал checkpoint, новые операции направляются новому writer. Приём пользовательских запросов во время передачи должен идти через устойчивый буфер/маршрутизатор с подтверждённым сохранением и idempotency, а не теряться или исполняться дважды.

Отдельные потоки:

- Данные: транзакционные границы, insert/update/delete, sequence state, FK, tombstones, cancelled/refunded/deleted сущности, финансовые ledger и архивы.
- Auth: регистрации, email/password changes, identities, блокировки, роли, подтверждения и восстановление пароля. Пароли и hashes не передавать модели; переносить штатным архивом/закрытым проверенным процессом.
- Storage: начальный манифест, новые и изменённые версии, удаления, uploads in progress, закрытые бакеты, MIME, cache control и права. Проверка SHA-256 байтов; metadata.size/ETag сами по себе недостаточны.
- Внешние события: устойчивый inbox/буфер, idempotency по event ID и бизнес-ключу, упорядочивание, retry и DLQ. Подтверждать приём webhook только после надёжного сохранения. Окна повторов каждого провайдера проверить; не предполагать бесконечный retry.
- Старые открытые вкладки/закэшированные JS/service worker, прямые ссылки на старый Supabase и signed URLs. Простая смена DNS сайта не перенаправит уже встроенные backend URL. Нужен проверенный совместимый переходный маршрут либо обновление клиентов; legacy endpoint может временно служить только мостом к единственному владельцу данных.
- Долгие Realtime/WebSocket сессии, live events, незавершённые checkout/3DS, multipart uploads. Не выбирать окно с активным эфиром и не делать неявный reset.
- Обратный поток изменений для отката после открытия target на запись.

Переходные мосты к старому Cloud допустимы только на период миграции. К завершению отказа от Lovable их зависимость должна стать нулевой.

## 7. Технический состав переноса

### База и история

Переносить actual live schema, не реконструировать её слепо из всех старых миграций. Сверить source history 1 228 записей с 1 405 SQL-файлами GitHub и target history 28 записей; проверить missing/extra, hashes и фактически применённые изменения. Не подделывать историю и не отмечать все файлы applied без доказательств. Baseline восстановленной live schema и дальнейшие reviewed migrations должны иметь честный audit trail.

В scope: таблицы всех прикладных схем; enum/domain types; sequences/identity и next values; FK/unique/check; индексы, grants/default privileges, owners, functions/search_path, views и SECURITY INVOKER, triggers, RLS, publications и replica identity, расширения. pgmq присутствует в source и отсутствует в target — проверить необходимость и совместимость. Managed auth/storage/realtime объекты сопоставлять по версиям сервисов; не удалять их схемы вслепую.

Официальный Cloud export — сжатый PostgreSQL archive для pg_restore; не SQL для вставки в SQL Editor. Проверить фактический файл через listing, версию client и поддержку сжатия. Экспорт включает пользователей и hashes, но не файлы Storage, секреты или настройки провайдеров. Пределы документации: база до 15 GB, export-файл до 5 GB, один запуск в 24 часа. Размер физической базы не доказывает размер архива. Репетиционный и финальный exports планировать с учётом cadence; при превышении лимита — поддерживаемый маршрут платформы, без очистки истории ради размера.
Источник: https://docs.lovable.dev/features/database-backups

Официальный плагин не предоставляет отдельного метода запуска/download полного export или полноценного CDC. На этом этапе не доказан автоматический маршрут экспорта без dashboard/support. ## 8. Проверка полноты и приёмка

До baseline сформировать полный реестр функций продукта, включая редко используемые и только административные. У каждой строки — сценарий, исходное поведение, данные, роли, интеграции, результат на копии и доказательство.

Обязательные gates:

1. Все таблицы и строки baseline учтены. По PK — missing/extra=0 для source snapshot; отличие из-за архивированных target записей отдельно объяснено. По детерминированным chunk checksums — content mismatch=0; все исключения перечислены. Для source private/auth и не-табличных объектов отдельные проверки.
2. Финансы: counts и суммы по валюте/статусу/провайдеру/периоду, order-payment allocations, refunds, ledger, balances, access periods, entitlements и referrals совпадают. Не суммировать разные валюты. Дубли provider UID/receipt/order и необъяснённые сироты отсутствуют.
3. Auth: совпадают пользователи/identities/UUID; вход, выход, recovery и роли проверены на разрешённых тестовых аккаунтах, без создания реальных пользователей или писем как smoke.
4. Storage: все объекты манифеста доставлены; SHA-256 совпадает, отсутствуют несогласованные uploads/deletes, private объекты не публичны; просмотр, скачивание и разрешённая загрузка работают.
5. Все FK/constraints валидны, sequences готовы к следующей записи; schema diff объяснён; source and target deployment/config сверены.
6. CDC/bridge: baseline+replay проверены на concurrent writes/deletes/DDL; gap=0, финальный cutover cursor применён; backlog и неподтверждённые события учтены, а не удалены ради «нулевой очереди».
7. Единственный исполнитель платежей, рассылок, доступов и каждого job. Отсутствие повторных side effects подтверждено журналом event/idempotency keys и read-back.
8. Все обязательные пользовательские сценарии PASS: сайт, вход, профиль, покупка без реального списания, сохранённый доступ, урок/прогресс, видео/эфир, сообщения, документы, кабинет и админка.
9. Новая опубликованная копия: скриншоты ПК и mobile по независимому URL/точному SHA; после реального switch повторить на основном домене. Проверить читаемость, границы, navigation и базовые сценарии. Не использовать production PII на скриншотах.
10. Нагрузочная и длительная проверка покрывает пиковые часы и критические циклы jobs; backup/restore и rollback отрепетированы. Критичные/высокие findings в scope отсутствуют; некритичные приняты в реестр.
11. Проверка независимости: runtime и deployment не требуют Lovable Cloud, AI gateway, managed connectors, Publish или старых secrets. Временные мосты перечислены и имеют условие отключения.

До выполнения этих gates формулировка «точная работающая копия» недопустима.

## 9. Переключение и откат

Перед предъявлением решения пользователю: точные source/target SHA, состояние данных и cursor, финальная матрица PASS, capacity, release artifact, DNS/TTL/SSL, список provider changes, ответственные, порядок jobs и запрет двойного writer. Подтвердить, что все конкурирующие deployment/repair задачи завершены или согласованы по scope.

На переключении: закрепить источник событий; передать writer ownership с fencing; дождаться применения финального checkpoint; переключить маршрутизацию и собственный опубликованный frontend; переместить внешние webhooks с durable inbox; затем включить target consumers/jobs по проверенному списку. DNS не считается атомарной передачей writer. Контролировать открытые старые клиенты и rollback journal.

Откат до первой target записи: вернуть routing/release и владельца jobs по подготовленному сценарию; перепроверить неисполненные события. Даже здесь учитывать новые источниковые записи после baseline.

Откат после target записей: сначала fence target writers и сохранить журнал; синхронизировать обратные изменения в source, включая Auth/Storage и удаления, сверить финансы/дедупликацию; только после этого вернуть writer ownership и трафик. Смена DNS обратно без обратной синхронизации запрещена. Если обратный replay не доказан, после открытия записей доступен только forward recovery — это должно блокировать обещание полноценного отката.

Предлагаемый, ещё не согласованный период наблюдения — не менее 14 дней и полный существенный платёжный цикл, если он длиннее. В этот период source сохраняется восстановимым, его старые consumers fenced; он не становится параллельным активным production. Критерий досрочного rollback: необъяснённая потеря/дубль платежа или права, расхождение баланса, нарушение изоляции, потеря webhook либо отказ обязательного сценария. Некритичные задержки сравнивать с измеренным baseline/SLO, не назначать произвольные обещания.

## 10. Когда можно отказаться от Lovable

Полный отказ — отдельная проверяемая финальная фаза:

- Все пользовательские домены и сборки обслуживаются собственным hosting.
- База/Auth/Storage/Realtime/Functions/jobs работают в собственном Supabase и своих сервисах.
- Нет остаточных runtime/build/deploy вызовов к Lovable; мосты отключены после сверки.
- Основные аккаунты, backups, документация и доступы принадлежат владельцу; восстановление выполнено независимо.
- Сохранены обе исходные базы, исходники, config и полный журнал переноса. Уникальные документы/видео не удалены.
- После периода наблюдения отдельно выполняются unpublish/disconnect/прекращение подписки. Удаление Cloud — необратимое действие, не часть smoke и не автоматическое следствие смены DNS.
- Исторический .lovable/plan.md не является утверждённым runbook и не запускается.
