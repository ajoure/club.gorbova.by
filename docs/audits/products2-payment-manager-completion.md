# Products 2 — подготовка завершения: выбор менеджера в платежах

Дата: 2026-09-01. Статус: **исправляется blocker plan-only; не объединено, не опубликовано**.

После команды пользователя «Продолжай» выполнена plan-only ревизия в уже
авторизованной канонической вкладке Lovable. Ревизия ничего не меняла и нашла
RBAC-blocker: `useStaffOptions` зависит от `users.view`, хотя страница платежей
доступна с `entitlements.view`. В ответ подготовлен узкий RPC-контракт; до его
повторной plan-only проверки merge, production apply и Publish запрещены.

## GitHub-артефакт и scope

- База: `72e901add20798d86c8474e65392e84643f80223` (`origin/main`, PR #400).
- Ветка: `codex/products2-payment-manager-options`; точный head SHA фиксируется
  в PR и повторно проверяется перед продолжением.
- `get_payment_manager_options_v1`: отдельный минимальный справочник для
  платежей, разрешённый только при `entitlements.view`; возвращает только
  `user_id` и отображаемое имя сотрудников с non-user ролью. Он не расширяет
  `users.view` и не ослабляет RLS таблиц.
- `usePaymentManagerOptions`: этот RPC-справочник + текущие назначения из
  загруженных платежей. Дедупликация по `user_id`, не по имени.
- `PaymentsFilters` / `PaymentsTabContent`: выбор сотрудника при пустом периоде,
  сохранение выбранного значения и имени при смене периода, включая бывшего
  сотрудника; загрузка / ошибка с повтором / пустой справочник; пояснение пустой
  выдачи. На мобильном — одна колонка; строка поиска и кнопки переносятся.
- Общий `PeriodSelector`: ограничение высоты доступным viewport и внутренний
  скролл, чтобы «Все периоды» не оказывался за верхней границей экрана.
  Семантика дат и пресетов не изменена; это общий компонент, при приёмке
  проверить также выбор периода в отчёте.

## Что это НЕ делает

Фильтр по-прежнему использует **назначение в платеже** из текущей версии
`payment_sales_attribution`, а не сегодняшнего ответственного в сделке.
Справочник позволяет выбрать менеджера даже с нулевой выдачей; он не назначает
этому человеку старые платежи. «Все менеджеры» и «Без менеджера» сохранены.
Фильтры хранятся в состоянии страницы; сохранение после полной перезагрузки
страницы или повторного входа этим патчем не добавляется.

Добавлен один локальный GitHub migration-файл с read-only RPC; он ещё не
применён. Нет Edge Functions, зависимостей, ослабления RLS или backfill. Не
менялись сделки, назначения, платежи, подписки, доступы, провайдеры, контакты и
уведомления. Прямой доступ к production Supabase не используется: применение
возможно только через Lovable после точного merged SHA.

## Порядок продолжения — только после нового разрешения

1. Проверить актуальный `origin/main`, head этого PR, зелёные checks, отсутствие
   конфликтов и новых критичных findings. Если база изменилась — пересверить
   diff и повторить проверки. Не смешивать другие PR.
2. Найти ровно одну каноническую вкладку проекта Lovable. Если она занята или
   содержит неотправленный ввод пользователя — остановиться, не создавать дубль.
3. Отправить **только plan-only** ниже и выполнить одну консолидированную
   ревизию. При необходимости backend-изменения остановить frontend-only
   завершение; новый код/миграции должны сначала пройти отдельный GitHub PR.
4. После всех PASS и разрешения merge получить точный merged SHA из GitHub.
   Не подставлять head ветки вместо SHA merge-коммита. Сверить diff и sync.
5. Через Lovable подтвердить exact SHA и применить ровно одну managed migration.
   Lovable записал каноническую managed version как
   `20260901173624_61a1bf5a-04e4-45e3-966e-e0fb484ae79e.sql`; исходный локальный
   draft `20260901170547_payment_manager_options_directory.sql` не был записан
   в migration history и удалён из Git во избежание двойного replay. Список
   deploy functions **пуст**. Проверить права и read-back RPC под допустимой ролью.
6. Publish только после всех применимых PASS. Затем проверить опубликованный
   `https://gorbova.by/admin/payments` и отдельно отчёт с общим выбором периода.
   Привязать URL, SHA/build и viewport к двум отдельным скриншотам ПК/mobile.
   На скриншотах не должно быть реальных персональных/платёжных данных.

## Оставшиеся части полного завершения Products 2

1. **Исторические назначения.** Перед обещанием «все платежи менеджера» нужен
   отдельный read-only dry-run через Lovable: точные IDs и счётчики, достоверный
   источник назначения, список неоднозначных записей, проверка согласованного
   исключения. Любая уже назначенная запись защищена от перезаписи. Только
   после отдельного согласования списка/счётчиков возможны небольшие
   идемпотентные batches и read-back. Настоящий патч этого не выполняет.
2. **История сделок, отдельный PR #399.** На 2026-08-31 он OPEN/DRAFT, head
   `f54b894d850039e479f22ad3b93a501e33f6518b`; code/contracts/build и guards
   SUCCESS, production smoke SKIPPED. Не входит в этот PR и не изменялся.
   Перед его завершением отдельно перепроверить актуальную базу и read-back.
   Ранее обнаруженная медленная audit-выборка нуждается в повторной проверке
   через Lovable. Никакого DDL или блокирующего индексирования без отдельного
   согласования окна; нельзя скрывать старую историю фильтром по дате.

Rollback frontend после публикации: отдельный revert PR только этого diff,
checks, затем Lovable sync/Publish точного revert SHA. Данные не откатывать:
этот релиз их не меняет. До merge достаточно оставить PR не объединённым.

Полный спринт нельзя объявлять закрытым по одному наличию dropdown: именной
production выбор, достоверность исторической атрибуции и опубликованные
desktop/mobile доказательства — отдельные критерии приёмки.
