# GLOBAL ENGINEERING RULES

Единый регламент работы lovable.dev для всех веток проекта.

Этот регламент обязателен для всех веток проекта и всех задач разработки.

Любая работа lovable.dev должна быть строго разделена на два типа сообщений:

1. План
2. Отчет о выполнении

Эти два типа сообщений используются для синхронизации с ChatGPT и архитектурным контролем проекта.

---

## 1. ТИПЫ СООБЩЕНИЙ

### 1.1. План

Если lovable.dev описывает будущую работу, сообщение обязательно должно начинаться так:

> План:

После этого указывается:
- что будет сделано
- какие изменения планируются
- какие файлы, таблицы, RPC, edge functions, UI будут затронуты
- какие проверки будут выполнены
- какие риски есть
- какие зависимости существуют

План описывает будущую работу, а не выполненную.

### 1.2. Отчет о выполнении

Если lovable.dev описывает уже выполненную работу, сообщение обязательно должно начинаться так:

> Отчет о выполнении:

После этого указывается:
- что реально было сделано
- какие файлы изменены
- какие SQL, функции, edge functions, UI были изменены
- какие данные были затронуты
- какие проверки подтверждают результат

Отчет описывает фактический результат, а не намерения.

---

## 2. СТРОГОЕ РАЗДЕЛЕНИЕ

Запрещено:
- смешивать план и отчет в одном сообщении
- писать "сделано" без фактического выполнения
- описывать будущую работу как уже выполненную
- выдавать предположение за факт
- публиковать результат без описания реальных изменений

Каждое инженерное сообщение должно быть либо `План:` либо `Отчет о выполнении:`

---

## 3. ОБЯЗАТЕЛЬНЫЙ ПОРЯДОК РАБОТЫ

Любая задача должна выполняться в следующем порядке:

1. Diagnose
2. Plan
3. Dry run
4. Execute
5. Verify

Пропуск этапов запрещен.

---

## 4. ОБЯЗАТЕЛЬНЫЙ ДОЗАПРОС ОКРУЖЕНИЯ

Перед выполнением любой задачи lovable.dev обязан проверить существующее окружение.

Если информации недостаточно, необходимо запросить:
- существующие таблицы
- существующие RPC
- существующие edge functions
- существующие UI-компоненты
- существующие cron и background jobs
- существующие enum
- существующие foreign keys
- существующие связи данных
- текущий source of truth
- похожие механизмы в других модулях

Цель: не создавать дубли и не строить параллельную архитектуру.

---

## 5. ФОРМАТ ПЛАНА

Каждый план должен содержать:

1. **Проблема** — Краткое описание задачи или дефекта.
2. **Диагностика** — Фактическое состояние системы на текущий момент.
3. **Предлагаемое решение** — Что именно будет изменено.
4. **Изменяемые компоненты** — файлы, таблицы, RPC, edge functions, UI-компоненты, cron и jobs.
5. **Что не будет изменено** — Явно указать, что остается вне scope.
6. **Dry-run** — Описание безопасной проверки перед реальным применением изменений.
7. **Execute** — Описание реального выполнения изменений.
8. **STOP-guards** — Условия аварийной остановки (неожиданные зависимости, аномальные значения, слишком большой rowcount, расхождение структуры, потеря source of truth).
9. **DoD** — Критерии, по которым задача считается выполненной.
10. **Риски и зависимости** — Потенциальные проблемы и ограничения.
11. **Требуется дополнительная информация** — Если данных недостаточно, явно указать.

---

## 6. ФОРМАТ PATCH

Каждый PATCH обязан содержать:
- Problem
- Diagnose
- Dry-run
- Execute
- STOP-guard
- DoD
- SYSTEM ACTOR proof

PATCH без этих пунктов считается неполным.

---

## 7. ФОРМАТ ОТЧЕТА О ВЫПОЛНЕНИИ

1. **Что сделано** — Фактически выполненные действия.
2. **Измененные файлы** — Перечень файлов.
3. **Измененные элементы системы** — SQL, таблицы, функции, RPC, edge functions, UI-компоненты, cron и jobs.
4. **Подтверждение результата** — SQL, логи, audit_logs, UI-пруфы, rowcount, diff-summary.
5. **Отклонения от плана** — Если в ходе выполнения были изменения.
6. **Что не сделано** — Если задача выполнена частично.
7. **Следующие шаги** — Если требуется дополнительный PATCH или новый план.

---

## 8. ЧАСТИЧНОЕ ВЫПОЛНЕНИЕ

Если задача выполнена не полностью:

> Отчет о выполнении: Выполнено частично.

Обязательно перечислить: что сделано, что не сделано, почему, что нужно сделать следующим шагом.

---

## 9. ЗАПРЕЩЕНО

- создавать новые таблицы без проверки существующих
- создавать новые RPC без проверки существующих
- создавать новые edge functions без проверки существующих
- дублировать UI-компоненты
- создавать второй источник истины
- создавать параллельные workflow
- плодить статусы, enum, кнопки, вкладки, процессы
- изменять архитектуру без плана
- выполнять массовые UPDATE или DELETE без dry-run и STOP-guards
- додумывать архитектуру без проверки фактов

---

## 10. СИНХРОНИЗАЦИЯ С CHATGPT

Lovable.dev обязан использовать заголовки `План:` и `Отчет о выполнении:`. ChatGPT использует их для разных режимов проверки.

---

## 11–12. ПРАВИЛА РАБОТЫ С ПЛАНАМИ И ОТЧЕТАМИ

- План = только будущая работа, не факт.
- Отчет = только фактически выполненное, не намерение.
- План должен быть пригоден для проверки ChatGPT.
- В отчете — только реально внесенные изменения, реальные доказательства.

---

## 13. АРХИТЕКТУРНЫЕ ПРИНЦИПЫ

- ID-driven architecture
- единый source of truth
- event-driven взаимодействие
- отсутствие скрытых side-effects
- add-only и минимальные правки
- безопасные миграции
- идемпотентность операций
- полная наблюдаемость
- полная auditability
- защита от дублирования
- zero hidden state
- deterministic linking
- predictable execution

---

## 14. ARCHITECTURAL SAFETY RULES

1. Нельзя создавать второй source of truth.
2. Нельзя создавать новую сущность без проверки существующих.
3. Нельзя дублировать бизнес-логику.
4. Нельзя добавлять скрытые side-effects.
5. Нельзя делать массовые изменения без guards (dry-run, expected rowcount, stop-guard, verify).
6. Нельзя менять production-логику без compatibility strategy.
7. Нельзя внедрять новую автоматизацию без проверки существующих cron и jobs.
8. Нельзя использовать текст как источник связи — только ID.
9. Нельзя делать DELETE без стратегии (soft-delete, archived_at, status-based exclusion).
10. Нельзя выпускать изменение без DoD.
11. Нельзя считать UI доказательством без backend-proof.
12. Нельзя смешивать diagnosis и execute.
13. Нельзя выполнять blind fix (причина не доказана → fix запрещен).
14. Нельзя плодить новые enum и статусы без архитектурной причины.
15. Любая критическая операция должна быть обратимой или контролируемой.

---

## 15. DO NOT DUPLICATE RULE

Перед созданием чего-либо нового проверить: таблицы, views, materialized views, RPC, SQL functions, edge functions, cron jobs, UI-компоненты, маршруты, вкладки, кнопки, enum, статусы, источники данных. Если аналог существует — сначала оценить переиспользование.

---

## 16. SAFE DATA RULES

- все даты — timestamptz
- все внутренние связи — UUID
- все критические операции — через audit_logs
- все массовые изменения — сначала dry-run
- все UPDATE — только с WHERE
- все risky changes — с rowcount guard
- все soft-delete и archiving — явно отражать в плане
- все reconciliation и repair операции — оформлять отдельным PATCH

---

## 17. SAFE UI RULES

UI должен: отображать, вызывать существующие сервисы, показывать подтвержденный статус, не создавать скрытые побочные эффекты.

Запрещено: дублировать workflow в UI, строить альтернативную state machine в интерфейсе, делать бизнес-решения только на фронтенде.

---

## 18. SAFE EDGE FUNCTION RULES

Edge functions обязаны: быть идемпотентными, иметь явный вход и выход, иметь guards, писать audit и log, не делать скрытых cross-domain мутаций, использовать существующие сервисы и канонические сущности, не создавать параллельную архитектуру.

---

## 19. SAFE MIGRATION RULES

Любая миграция обязана: иметь scope, цель, не ломать production, иметь план перехода, проверку результата, не создавать дубли, учитывать совместимость.

Legacy migration: `legacy system → compatibility layer → canonical architecture`.

---

## 20. ОБЯЗАТЕЛЬНЫЕ ПРОВЕРКИ ПЕРЕД EXECUTE

1. Есть ли уже аналогичная таблица, функция или workflow
2. Есть ли дублирующий источник истины
3. Есть ли риск race condition
4. Есть ли риск потери ссылочной целостности
5. Есть ли риск массового повреждения данных
6. Есть ли откат или безопасный fallback
7. Есть ли понятный DoD

---

## 21. ГЛАВНОЕ ПРАВИЛО

- Будущая работа → `План:`
- Выполненная работа → `Отчет о выполнении:`
- Другие форматы инженерных сообщений не допускаются.

---

## 22. POST-DEPLOY WEBHOOK SMOKE (D2-BIS)

После любого передеплоя edge function через агентский `supabase--deploy_edge_functions` ОБЯЗАТЕЛЕН runtime smoke на production URL соответствующего webhook:

1. Smoke сразу, через 30 секунд и через 2 минуты.
2. Бить по `https://<project-ref>.functions.supabase.co/<function-name>`, не через `supabase.functions.invoke()`.
3. PASS = НЕ platform-401 (маркеры: `UNAUTHORIZED_NO_AUTH_HEADER`, `Missing authorization header`, `Invalid JWT`). Application-level 401 с нашим `reason` в теле — допустим.
4. Если хотя бы один probe = platform-401 → запустить GitHub workflow `Supabase Migration & Deploy` в режиме `deploy-functions` (он использует `supabase functions deploy --all` через CLI и применяет `config.toml`).
5. CI guard `verify-webhook-runtime.yml` запускает эту же проверку автоматически (после `apply-migrations`, по cron, по push в webhook-функции).
6. CI guard `verify-webhook-public.yml` остаётся как git-state проверка (что в `config.toml` для каждого webhook стоит `verify_jwt = false`).

Этот раздел отражает корректирующее правило после повторной регрессии D2 (Phase 3.3) и Phase 3.4: агентский deploy НЕ синхронизирует `verify_jwt` из `config.toml`, и платформа сбрасывает функцию в дефолт `verify_jwt = true`.

---

## 23. ОСНОВНАЯ ЦЕЛЬ

Все эти правила нужны для того, чтобы платформа могла: безопасно масштабироваться, не превращаться в архитектурный хаос, сохранять единый source of truth, поддерживать стабильные интеграции, быть полностью аудируемой, развиваться без каскадных отказов, выдерживать enterprise-нагрузку.
