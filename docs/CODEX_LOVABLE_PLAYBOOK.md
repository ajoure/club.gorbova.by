# Рабочая библия `gorbova.by`: Codex, GitHub и Lovable

Этот документ устанавливает единый процесс для всех будущих веток проекта.
Его цель — сделать работу предсказуемой: не смешивать независимые спринты,
сначала получать проверяемый код в GitHub, а Lovable использовать только там,
где он действительно является production-границей.

## 1. Что является источником истины

| Область | Источник истины | Что считается доказательством |
| --- | --- | --- |
| Исходный код и история | GitHub | точный SHA, diff, PR и CI checks |
| Production БД, Storage, RLS, Edge Functions | Lovable Cloud | managed migration/deploy, read-back и безопасный smoke |
| Публикация интерфейса | Lovable Publish | опубликованный SHA/URL, безопасная проверка сценария и скриншоты ПК + mobile |
| Бизнес-правила | существующие канонические сущности и контракты | discovery до изменения, а не новый параллельный workflow |

Ни merge, ни `npm run build`, ни HTTP 200 сами по себе не доказывают
production-готовность. Они подтверждают только свой слой.

### 1.1. Два режима владения production-инфраструктурой

Сначала выясняется, кому принадлежит рабочий Supabase и deployment-контур.
Нельзя переносить правила одного режима в другой по привычке.

| Режим | Где выполняется максимум работы | Роль Lovable |
| --- | --- | --- |
| **Свой GitHub + свой Supabase** | в изолированной GitHub-ветке и в своём Supabase через проверяемые миграции, secrets и deploy-процесс проекта | только для конкретной операции, которую нельзя выполнить без Lovable |
| **GitHub + Lovable Cloud Supabase** | код и проверки — в GitHub; Lovable не является автором кода | единственная разрешённая production-граница для БД, RLS, Storage, Edge Functions и Publish |

В обоих режимах действует GitHub-first: сначала discovery, изолированная
ветка, проверки и PR. Отличается только исполнитель последнего
production-шага. Для своего Supabase не создаётся искусственная зависимость
от Lovable; для Lovable Cloud не используется прямой Supabase CLI/MCP или
чужой проект как обход его production-границы.

### 1.2. Когда останавливаться перед Lovable

Стандартный режим: Codex максимально завершает GitHub- и доступную
Supabase-часть сам. Когда для следующего действия действительно требуется
Lovable, Codex сообщает точный SHA, действие и проверку, затем ждёт явного
разрешения пользователя и подтверждения, что чат Lovable свободен.

Исключение: если пользователь уже дал широкую команду «выполни всё»,
«доведи до конца» или «выполни и опубликуй», это разрешает необходимый
переход в Lovable без дополнительной остановки. Тогда Codex самостоятельно
завершает execute и Publish, но только после всех обычных stop-guards и
проверок. Это никогда не даёт автоматического права делать реальный платёж,
отменять подписку, отправлять рассылку, создавать пользователей/контакты или
удалять данные без отдельного разрешения.

## 2. Обычный рабочий поток

```text
discovery → изолированная GitHub-ветка → локальные проверки → PR/CI
          → (если production-risk) Lovable plan-only → ревизия Codex
          → exact-SHA execute в Lovable → read-back/smoke → Publish
          → визуальная проверка ПК + mobile → отчёт
```

### 2.1. Изоляция GitHub

1. Перед работой проверить `git status`, открытые PR, `origin/main` и scope.
2. Создать чистый worktree и ветку `codex/<scope>` от актуального `origin/main`.
3. В этой папке менять только файлы текущего scope. Не очищать и не
   «исправлять» изменения соседних задач.
4. До PR выполнить подходящие проверки: форматирование/diff-check, сборку,
   тесты и узкие безопасные проверки контракта.
5. Открыть PR. Merge возможен только с понятным diff и зелёными обязательными
   проверками. При конфликте с новой версией `main` — rebase/merge и повторная
   проверка, а не force-push поверх чужой работы.

Независимые ветки могут идти параллельно. Перед merge и Publish проверяется
только их фактическое пересечение по файлам, миграциям и контрактам, а не
останавливается вся работа из-за самого существования другого PR.

## 3. Когда нужен Lovable plan-only

Codex не обязан гонять Lovable через план для простой документации, локального
рефакторинга или изолированного frontend-патча: это добавляет время и токены.
Но plan-only обязателен до execute для изменений, затрагивающих:

- миграции, данные, RLS/Auth, Storage;
- платежи, подписки, выдачу доступа или возвраты;
- Edge Functions, webhooks, cron и внешние интеграции;
- массовые repair/reconcile операции;
- общий Publish, если есть security findings или несколько зависимых модулей.

### 3.1. Как использовать план без лишней переписки

Пользователю не нужно вручную принимать каждый план Lovable. Codex сам
заказывает план, сверяет его с GitHub и архитектурой, вносит одну
консолидированную правку и только потом даёт Lovable команду execute.

В plan-only запросе обязателен запрет на любые изменения:

```text
Режим PLAN-ONLY. Ничего не меняй: не создавай коммиты, код, миграции,
данные, functions и не нажимай Publish. Сначала проведи read-only discovery
и верни план на русском: scope, точный SHA, затрагиваемые компоненты,
dry-run, stop-guards, DoD, что остаётся вне scope и безопасные проверки.
```

Codex делает одну глубокую ревизию плана: scope, source of truth,
совместимость, DDL/контракты, порядок операций, rollback, данные, проверки и
границы. Второй проход — только «внесено / частично / не внесено». Новые
обязательные правки появляются лишь при новом факте: новом коде, схеме,
runtime-результате, blocker или изменении scope.

## 4. Правило exact-SHA execute

После GitHub merge команда Lovable должна содержать exact SHA и строгий
перечень разрешённых действий. Пример структуры:

```text
Режим EXECUTE. Используй только GitHub main SHA <sha>.
Не меняй код и не создавай коммиты/миграции. Разрешены только:
1) <managed migration list in order>;
2) deploy <exact function list>;
3) <dry-run and verification list>.
Если SHA расходится, dry-run не проходит, есть missing reference, неожиданный
rowcount, ошибка deploy или critical finding — остановись без execute,
удаления и Publish. Сообщи только обезличенные счётчики и причину.
```

Это правило появилось после реального отклонения: Lovable качественно выполнил
dry-run и read-back student uploads, но всё же создал лишний повторяемый
коммит, хотя ему было запрещено создавать коммиты. Поэтому Lovable не является
автором production-кода в этом процессе; он — управляемый исполнитель уже
проверенного GitHub-артефакта.

## 5. Данные, миграции и безопасность

- Сначала искать существующие таблицы, RPC, функции, cron/jobs, UI и source
  of truth. Не создавать параллельные сущности или второй workflow.
- Связи строить по стабильным идентификаторам; не по отображаемому тексту,
  email, slug или названию.
- Новая миграция должна быть совместимой, идемпотентной, узкой и иметь
  проверяемый результат. Не переписывать применённую историю миграций.
- Массовое изменение: dry-run с ожидаемым rowcount, stop-guard, маленькие
  batches, затем read-back. Удаление — только после безопасной копии/перевода
  ссылки и явной проверки; для обычных сущностей предпочитать soft-delete.
- Не выдавать `service_role` в браузер и не создавать `SECURITY DEFINER` как
  обход RLS. Для RLS проверять ownership и доступ каждой роли.
- Для Storage разделять публичные материалы и приватные пользовательские
  файлы; приватная раздача — через ограниченный по времени серверный URL.
- Для денег и доступа сохранять идемпотентность, источник события и
  audit/lineage. Внешний провайдер — не имитируется реальным списанием при
  проверке.

## 6. Проверка до Publish

Publish допускается только после полного набора фактов для данного scope:

1. GitHub: точный merged SHA, понятный diff, проверки PR.
2. Lovable: применены именно перечисленные миграции и развернуты именно
   перечисленные functions.
3. Data read-back: права, политики, счётчики и ссылки соответствуют DoD.
4. Runtime: безопасный smoke нужного пути. Для webhook после deploy проверять
   production URL, а не только клиентскую invoke-обёртку; smoke не создаёт
   пользователя, платёж, письмо, сообщение или отмену.
5. Security: нет критического finding в scope. Чужой critical finding не
   маскируется: он оформляется отдельной изолированной задачей.
6. Publish: URL доступен, а нужный пользовательский сценарий проверен на
   допустимых тестовых данных.

Если хотя бы один пункт не доказан, в отчёте говорится «не подтверждено», а
не «готово». Для боевых платежей, рассылок и live-событий безопасная
проверка не заменяет полноценный контролируемый приёмочный тест.

### 6.1. Обязательное доказательство видимого UI

Если задача меняет то, что видит пользователь — текст, изображение, поле,
вёрстку, состояние или интерактивное поведение — «готово» и «опубликовано»
допустимы только после всех следующих фактов:

1. Проверен опубликованный URL с точным опубликованным SHA/версией, а не
   Preview, локальная сборка, DOM-assertion или HTTP 200.
2. Сделаны и приложены к отчёту **два отдельных скриншота** этого результата:
   desktop и representative mobile viewport; у каждого известны URL, версия и
   viewport.
3. Codex сам визуально сверил оба вида: требуемое изменение и базовый
   пользовательский сценарий видны и работают; текст и картинки читаемы;
   ничего не обрезано, не выходит за край, не перекрывается и не остаётся вне
   экрана.
4. При любой ошибке в одном viewport патч исправляется и обе визуальные
   проверки повторяются до итогового отчёта.

Для backend-only задачи UI-доказательство честно помечается «не применимо»;
вместо него приводится доказательство на нужном слое (данные/API/logs/runtime).
В визуальные доказательства не включаются персональные/платёжные данные,
ключи, токены, пути пользовательских файлов или подписанные URL.

## 7. Спринты, blockers и хвосты

- Один sprint имеет один основной scope. Его нужно довести до PR, deploy и
  проверки, а не бросать после первого локального build.
- Критический новый факт (риск денег, доступов, данных, security или неверный
  source of truth) останавливает execute.
- Некритичный вопрос не тормозит безопасный основной scope: он фиксируется в
  `deferred`/follow-up с причиной и проверкой, которая нужна позже.
- Старая проблема из мониторинга не смешивается с текущим release. Её
  диагностируют и исправляют отдельной веткой, чтобы исправление платежей не
  случайно попало вместе с изменением обучения или CRM.

## 8. Коммуникация и отчёт

Codex работает самостоятельно, поэтому ручной ритуал «План / Отчёт Lovable»
для каждой мелкой задачи не обязателен. В сообщениях пользователю нужно ясно
разделять:

- **План** — только будущие действия, scope и риски;
- **Отчёт о выполненной работе** — только свершившиеся изменения и доказательства.

Итог должен включать: изменённые компоненты, что намеренно не трогалось,
проверки, SHA/PR/Publish при наличии, rollback/ограничения и список
действительно оставшихся проблем. Нельзя помещать в отчёт ключи, токены,
личные данные, содержимое пользовательских файлов или подписанные ссылки.

## 9. Приоритет документов

1. Явная команда пользователя и системные требования безопасности.
2. `AGENTS.md` в корне репозитория.
3. Этот playbook.
4. `docs/ENGINEERING_RULES.md` — полезная архитектурная справка и шаблон для
   ручной проверки плана, но не требование гонять Lovable через plan/report
   на каждой мелкой задаче.

Архитектурные идеи из старой «библии» — целевой ориентир. Они не дают права
переписывать зрелый production-модуль целиком в рамках несвязанного патча.
