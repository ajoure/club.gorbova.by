# Документы последнего оплаченного продления

## Доказанные причины

В read-only Lovable discovery на `3572c55b80dace2b8ef74a3a8f5c80cf0fc1062b`
подтверждены две независимые части одного пользовательского сценария:

- штатный bePaid rebill materializer сохраняет серверную lineage, но может
  не копировать `card_last4` / `meta.payment_method`; канал становится `other`,
  и существующий сценарий документа для карты не выбирается;
- `/purchases` передаёт в документы подписки FK первоначального заказа,
  даже когда оплачено более позднее продление.

Воспроизведение в тестах синтетическое: январский первоначальный заказ,
октябрьское продление, один и тот же provider subscription ID. Клиентские
данные, документы, реквизиты и подписанные ссылки здесь не сохраняются.

## Контракт исправления

Канал `card` восстанавливается только для точной серверной lineage
`provider=bepaid`, `source=rebill_flow_insert`,
`materialization_run=bepaid_webhook_rebill_v2`, непустого
`bepaid_subscription_id` и отсутствующих явных method/channel. Остальные
ветки, включая ERIP, transfer, wallet и неизвестный явно заданный канал,
не расширяются.

Документ и чек выбираются из одного последнего реального положительного
`succeeded` платежа `paid` заказа. Проверяются владелец, продукт, тариф,
provider binding или точная серверная parent lineage. Исключены чужая
подписка, другой продукт/тариф, тесты, ручные платежи, отменённые/возвращённые
заказы и неоднозначные одинаковые даты. При ошибке запроса нет fallback на
старый FK. Сортировка только по подтверждённому `paid_at`.

Не меняются финансовые записи, офферы, шаблоны, сроки доступа, согласия,
webhook, cron, RLS, миграции и история документов. Отдельный дефект ссылки
`/admin/orders/:id` остаётся вне этого PR.

## Проверки и выпуск

Локально: 68 Vitest (оба зеркала канала, селектор, wiring экрана и сохранение
Stripe cancellation guard), TypeScript, production build, narrow ESLint,
Edge Function reference check и `git diff --check`.

После зелёных GitHub checks и merge использовать только точный merged SHA.
Lovable execute не пишет код/коммиты/миграции. Минимальный список deploy:

1. `canonical-document-generate-strict`;
2. `canonical-document-payment-hook`;
3. `canonical-deal-document-overrides`.

Все три импортируют изменённый общий resolver напрямую или через snapshot.
После deploy проверить источник/версию, безопасный HTTP preflight и
read-only предикат выбора существующего сценария. HTTP 200 не считается
генерацией документа или клиентским E2E.

Сверить ограниченные fingerprints исходного заказа/платежа и число документов
до/после. Не выполнять generation, preview (может писать snapshot/audit),
payment-hook invoke, реальные платежи, сообщения, impersonation или создание
пользователя как smoke. Не читать клиентские файлы.

Publish — только после проверок. В опубликованном UI нужны отдельные PC и
mobile подтверждения изменённого элемента без ПДн. Админский read-back не
заменяет проверку self-service под клиентом; при недоступности последнего
честно оставить это подтверждение ожидающим ответа клиента.
