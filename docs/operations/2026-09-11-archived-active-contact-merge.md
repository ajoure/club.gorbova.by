# Объединение архивных дублей с активными контактами

Статус: разрешено пользователем 11.09.2026; read-only preflight, production ещё не изменён.
Ветка: `codex/archived-active-contact-merge`, исходный SHA `0b716e284`.

Пользователь расширил сверку исторических покупок 17/18 потоков на всю базу:
объединить архивные контакты с активными при совпадении email ИЛИ телефона,
сохранить email и учётную запись для входа активного контакта, собрать покупки
и убрать доказанные дубли. Это заменяет первоначальное решение только перепривязать
покупку строки 18:36 без объединения контактов.

## Границы совпадения

- Email: `lower(trim(email))`; телефон: только цифры, не менее 7. Пустые значения
  не образуют совпадения. Не добавлять страну, не менять Gmail dots/plus.
- Только archived → active. Совпадение по одному признаку достаточно по прямому
  указанию пользователя. Несколько активных кандидатов требуют отдельного выбора.
- Активный master сохраняет login email/auth. Уже объединённый в этот же master
  архивный контакт не является новой операцией; проверить оставшиеся связи.
- Контакты сохраняются как архивные aliases с `merged_to_profile_id`, а не физически
  удаляются. Заказы, оплаты, возвраты и самостоятельные доступы сохраняются.
- Одинаковый продукт/тариф сам по себе не означает дубль покупки. Проверять внешний
  источник/идентификатор заказа, платёжные связи, период и состав компонентов.

## Порядок исполнения

1. Через канонический Lovable Cloud получить точный текущий snapshot пар и всех
   зависимостей profile_id/user_id, включая не объявленные FK; наружу только UUID,
   основание совпадения, счётчики и признаки конфликтов, без контактных данных.
2. Проверить неоднозначные активные masters, Auth/Telegram collisions, прежний
   merged_to, уникальные ограничения и побочные эффекты триггеров.
3. Подготовить атомарный перенос с до/после журналом точных ID. Штатный
   `merge-clients` нельзя вслепую запускать массово: он не проверяет ошибки каждого
   переноса и не охватывает все user_id/profile_id связи, например entitlement_sources.
4. GitHub PR и необходимые проверки, затем точный merged SHA в Lovable. Dry-run →
   ожидаемые счётчики → одна пилотная пара → read-back → небольшие идемпотентные batches.
5. Проверить сохранение активного login email/auth, покупок/денег/сроков/истории,
   отсутствие оставшихся ссылок на архивного владельца в перенесённых сущностях,
   повторный запуск с нулевыми изменениями. Никаких клиентских сообщений и платежей.
6. После объединения заново пересчитать исторические покупки 17/18; прежний
   inventory до объединения нельзя использовать как окончательный payload импорта.
