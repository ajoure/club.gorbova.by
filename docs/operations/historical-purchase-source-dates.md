# Исторические даты ЦБ: источник вместо времени импорта

286 history-only фактов, добавленных из листов «17 поток» / «18 поток», имели
`deal_date = NULL`; карточка показывала `created_at` импорта 11.09.2026.
Колонка D исходного списка содержит дату создания старой сделки, колонка E —
отдельную дату оплаты. Каноническая дата сделки определяется D: поздняя оплата
не должна менять месяц/дату сделки (существующий контракт rebill).

Проверка Sheets 11.09.2026: 141 строка, 139 заполненных D, 18 заполненных E.
Из 286 добавленных фактов точная исходная дата есть у 285, все в 2024 году.
Один факт из строки 17:88 остаётся без известной даты. Изменять дату на основании
года/начала потока или другого заказа нельзя. Для объединённых повторных строк
берётся самая ранняя реальная исходная сделка на тот же продукт; модуль учитывает
только строки с отметкой 1 в собственной колонке. Единственный такой новый факт —
полный курс 18:14/53: первая сделка 27.07.2024, ссылка на источник 18:14.

Даты D/E интерпретируются в явно проверенной timezone таблицы Europe/Moscow
(UTC+03:00 в 2024). D записывается в `deal_date`; E сохраняется в `meta.source_paid_at`,
не создаёт платёж. `created_at`, владелец, сумма, статус и purchase_snapshot неизменны.
Триггер сохраняет `deal_month` пустым для всего этого history-only batch даже с
известной датой, чтобы исправление истории не открывало месячный контент.

## Управляемое применение

GitHub migration `20260911163000_historical_purchase_source_dates.sql` устанавливает
только узкий RPC `admin_repair_historical_cb_dates` и уточняет существующий
no-month guard. Применение данных — отдельно, через Lovable Cloud service role.
RPC принимает только 15 закреплённых SHA256 payload, до 20 фактов в запросе.
Payload с ID/исходными refs/датами передаётся отдельным приватным артефактом;
контакты и их данные не входят в Git.

1. Read-only сверить 285 IDs, batch/source refs/product и NULL deal_date; ожидать
   285 совпадений. Предыдущие импорты GetCourse/CSV с верными датами не изменять.
2. Применить точную merged migration через Lovable Cloud.
3. Для первого batch вызвать RPC `_mode='dry-run'`, затем `'rollback'`, проверить
   исходные даты/audit неизменны. Никаких других API/писем/доступов.
4. Для каждого из 15 batches: dry-run с точным числом missing, execute, read-back.
   Конфликт source refs/даты/денег, сторонний side effect — остановить batch.
5. Повторный вызов должен дать `changes=0`; финал 285 точных дат, 285 audit записей,
   0 новых платежей/подписок/самостоятельных доступов, `deal_month` отсутствует,
   `created_at` и остальная запись сохранены. Один неизвестный факт не изменяется.
6. После Publish проверить карточку/детали/таблицу/экспорт/редактор: 2024 там, где
   дата восстановлена, «Историческая покупка · дата неизвестна» для 17:88.
   Нужны опубликованные desktop/mobile скриншоты без персональных данных.

До этих проверок PR/локальная сборка не являются публикацией или data repair.

## Проверки

- PGlite: источник/отметки/дубликаты, ACL, фиксированный payload, dry-run, rollback,
  execute, replay, защита существующей даты, audit, no-month и side effects.
- Vitest: каноническая дата не зависит от rebill, неизвестная история не получает
  дату импорта или сегодня, сортировка неизвестных дат в конец.
- Production Vite build; актуальные GitHub checks.
