# Точная дата существующего оплаченного доступа

Продолжение платёжного восстановления после PR #405. Не создаёт отдельный
checkout, продукт, заказ или новую ветку авторизации. Боевые данные и Publish
этим кодовым патчем не выполняются.

## Почему нужен патч

Авторизованный администратор не мог вызвать точное восстановление через
существующую форму сделки: она не передавала конечную дату, а при наличии
подписки кнопка отсутствовала. Массовый ручной редактор здесь не используется:
его выбор подписки не соответствует безопасному exact-восстановлению.

## Контракт

- В карточке уже оплаченной сделки появляется «Исправить срок доступа» только
  для `admin` / `super_admin`. Та же форма доступна через оплату → сделку;
  заполнение pipeline ради обхода не требуется.
- Точная дата вводится в часовом поясе браузера с секундами и миллисекундами;
  предварительный просмотр показывает также UTC. Невозможные даты, сокращение,
  неоднозначная подписка и ошибки загрузки блокируют действие.
- Exact-запрос использует `orderId`, `customAccessEndAt`,
  `expectedExistingSubscriptionId`, `extendFromCurrent: true`. Не передаёт
  `customAccessDays`, `manualSubscriptionId`, `adminManualAccessEdit`.
- Перед exact-запросом UI проверяет capability через авторизованный read-only
  GET той же функции. Старый backend вернёт `orderId required`, поэтому форма
  не отправит POST без подтверждённой серверной защиты. GET выполняется после
  той же проверки реальной роли, до чтения заказа и любых записей.
- Сервер проверяет ожидаемую существующую подписку до idempotent-resync,
  перед использованием provider/legacy-кандидата и до выдачи. Не совпала цель,
  невалиден предыдущий конец или запрос сокращает срок → отказ, не CREATE.
  При устаревшей order-scoped подписке допускается дальнейший поиск доказанного
  provider-linked преемника; прежний parent сам не становится extend-целью.
- Явная конечная дата проверяется строго: даже недостающая миллисекунда не
  считается выполнением. Старый 12-часовой допуск остаётся только у неявного
  legacy-окна. Матрица авторизации остаётся прежней.
- Exact-режим не присоединяет платёжный метод, не меняет auto_renew и не
  пересобирает billing snapshot/сумму. Сохраняет историческое начало подписки.
- `skipped`, `manual_review` и неподтверждённый ответ не показывают успех.
  После grant форма читает подписку и entitlement по возвращённым ID,
  проверяет владельца, продукт, тариф, связь с заказом и обе конечные даты.
  Показывается фактически подтверждённый срок, а не локальный расчёт.
- Основной доступ и состояние Telegram/GetCourse не смешиваются: ошибка
  интеграции показывается отдельно. Логика отправки уведомлений не меняется.

## Rollout и приёмка

GitHub checks → exact merged SHA → managed deploy `grant-access-for-order`
с новым локальным helper → безопасные OPTIONS/invalid-auth проверки → вход
реального администратора в Preview → свежий provider GET/точные guards →
согласованные восстановления и read-back → остальные workers/migration
предыдущего платёжного плана → Publish только после всех PASS.

Нужны отдельные скриншоты уже опубликованного результата на ПК и мобильном
viewport без персональных/платёжных данных. Локальные тесты и Preview их не
заменяют. Ожидаемый вход администратора не заменяется извлечением JWT/ключей.
Скрытые тарифы и оплата остатка существующей рассрочки идут следующим scope.
