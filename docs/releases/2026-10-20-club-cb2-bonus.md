# ЦБ2: бонус клуба, предупреждения и историческая покупка

Исходный baseline: `095b85f1e96203c51b72a5052ce55092d70fd430`.
Маркер функций: `club-cb2-bonus-2026-10-20-v1`.

## Managed release

1. Только Lovable Cloud; GitHub — источник кода. Проверить свободный чат,
   точный merged SHA и отсутствие чужих неопубликованных изменений.
2. До миграции проверить определения функций и точные имена/типы столбцов.
   Baseline MD5 `public.user_has_training_lesson_access(uuid,uuid)`:
   `b09773ee0fba422bc158f781fb4d5947`.
   Приватный legacy resolver не изменять. При расхождении STOP.
3. Применить ровно `20261020131240_club_cb2_bonus_access.sql`.
   Она не меняет заказы/платежи/подписки/даты/выданные доступы автоматически.
4. Развернуть `send-email`, `subscription-renewal-reminders`,
   `grant-access-for-order`, `access-rules-nightly-reconcile`,
   `rules-retroapply`, `referral-redemption-worker`.
   Существующий общий release digest включает весь `_shared`; после его
   пересчёта также развернуть только упаковку/маркер `sales-runtime-worker`,
   `sales-runtime-control`, `telegram-webhook`, `telegram-media-worker`.
   Их бизнес-логика не изменена. Проверить прежние защищённые health probes
   без сообщений и обработки очередей; четыре digest должны совпасть.
   Для send-email gateway verify_jwt=false, но обязательны точный managed
   service key либо живой проверенный JWT сотрудника с прежним RBAC.
   Никакого доверия декодированному role claim без проверки подписи.
5. Только no-send probe `send-email` с `{action:"diagnose"}`: service/staff PASS,
   anonymous/anon key/forged JWT/обычный клиент DENY, SMTP/log inserts=0.
6. Проверить всех текущих покупателей Business/Ideology: купившие ЦБ2 сохраняют
   правильный срок, непокупатели не получают бонус и метаданные уроков.
   Ручные и собственные оплаченные права сохраняются независимо от клуба.
   Более длинная агрегированная запись не продлевает реальное окно клуба.
7. Сравнить reminder dry-run без отправки и без запуска production cron:
   ложные предупреждения по покрытым ЦБ2 пропускаются; рекуррентные платежи
   клуба, рассрочки и другие продукты не затрагиваются.
8. Историческую нулевую покупку исправлять только по отдельно подтверждённым
   владельцем параметрам: service-only RPC `repair_cb2_historical_order`.
   До UPDATE проверить триггеры orders_v2; dry-run changed=1, затем один UPDATE,
   повтор changed=0. base_price/final_price/paid_amount равны подтверждённой
   полной оплате; payments/subscriptions/grants created=0. Тариф, поток,
   статус, дата импорта и deal_month неизменны. Источник и подтверждение
   сохранены в historical_provenance, аудит ровно один.
   ID заказа, приватный источник и финансовые значения не входят в этот файл.
9. Одно отдельно разрешённое владельцем письмо — с уникальным idempotency_key.
   Не повторять при неоднозначном результате. Успех SMTP и фактическое получение
   в ящике проверять отдельно. Старые письма/уведомления не переотправлять.
10. Publish только после PASS; сохранить точный SHA, публичный URL, два
    опубликованных UI-скриншота (ПК и mobile 390×844) без персональных данных.

## Регрессии

- PGlite исполняет реальную миграцию и RLS: покупатель/непокупатель, оба тарифа,
  окончание клуба, ручной и самостоятельный доступ, возврат/подарок/тест,
  linked profile, историческая нулевая сумма, ACL, повторяемость миграции,
  guarded repair и идемпотентность без новых платежей.
- Deno: фактический общий grant engine, SMTP authorization, no false success,
  canonical covering window и неизменность recurring/других продуктов.
- Vitest: компактный русский срок доступа, ошибка и pending не бессрочны.
- CB21 RLS и расписание остаются отдельными существующими проверками.
