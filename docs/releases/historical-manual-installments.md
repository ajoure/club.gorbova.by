# Историческая ручная рассрочка на исходной покупке

Сценарий применяется сотрудником только к ранее согласованным двум взносам,
когда первый уже подтверждён реальной оплатой на существующей сделке. Он не
заменяет обязательный банковский mandate новых публичных рассрочек и не создаёт
новую покупку, платёж, пользователя, провайдера или рекуррентное списание.

## Путь администратора

Контакт → «Рассрочки» → «Оформить историческую рассрочку». Выбрать исходную
сделку, подтверждённую общую сумму и срок остатка, записать решение владельца и
основание. Для известного графика указывается срок от первой оплаты; если клиент
сейчас погашает остаток и прежний срок не подтверждён, выбрать «Остаток к оплате
сейчас». Старую дату при этом не придумываем. «Проверить расчёт» ничего не записывает. После проверки полной суммы,
реально оплаченной части, остатка и срока нажать «Подтвердить условия».

Подтверждение меняет общую сумму и статус только этой сделки, сохраняя квитанцию,
получателя, продукт, тариф и существующий доступ. Договор сохраняется отдельной
неизменяемой записью; повтор возвращает её без второй записи и аудита.

«Проверить доступ по первому взносу» сохраняет существующий срок. Для новой
выдачи на частичной оплате период вычисляется из фактического первого платежа
и сохранённого срока покупки либо исходного тарифа. Истёкшее окно не открывается.
Отдельный durable dispatch допускает один вызов канонической выдачи; неизвестный
результат блокирует повтор и требует read-back реальных прав.

После подтверждения карточка долга появляется в той же вкладке. «Ссылка на
погашение» принимает ровно весь фактический остаток одним разовым платежом.
Сохраняются исходная покупка и доступ, никакой фиктивный bePaid mandate не нужен.
Повтор использует текущую ссылку. Новая оплата фиксируется на исходной сделке
атомарно с погашением ссылки и одним аудитом; существующий provider UID не
перепривязывается к другой покупке. Возвраты, другие деньги или неверная сумма
останавливают автоматическую запись и остаются для сверки.
В ручном сценарии потерянный ответ провайдера, неполный успешный ответ и
неопределённый HTTP-отказ сохраняются как `unknown`. Незавершённый `creating`
не освобождается по таймеру; новый запрос провайдеру до сверки не выполняется.

## Managed release

1. Официальный Lovable Cloud: сверить очередь, exact merged SHA и определения
   заменяемой `create_existing_installment_payment_link_v1` с GitHub baseline.
   При расхождении остановиться. Не менять данные клиентов во время preflight.
2. Применить `20261126143000_historical_manual_installments.sql`. Она создаёт
   только staff-only таблицы/функции; исторического backfill нет. Проверить RLS,
   ACL, сигнатуры, rowcounts (клиентские записи не создаются применением миграции).
3. Развернуть ровно `admin-historical-manual-installment`,
   `admin-create-public-link`, `public-checkout`, `bepaid-webhook`.
   Последние три используют изменённые shared repayment helpers.
   `grant-access-for-order` остаётся существующим каноническим исполнителем.
4. Проверить unauthorized/student DENY без записи, безопасные preview и
   read-back. Реальный платёж и клиентскую отправку не использовать как smoke.
5. Publish UI после PASS; проверить контакт → «Рассрочки», расчёт/подтверждение,
   карточку долга и разовую ссылку на ПК и mobile. Сохранить два обезличенных
   скриншота опубликованного URL, SHA и viewport. Локальный build этого не заменяет.
6. Конкретные клиентские действия выполнить отдельно в разрешённом объёме с
   проверкой свежей истории и платежей. Не повторять уже зарегистрированный
   первый взнос. Точные ID/документы/суммы клиента находятся в приватном журнале.

## Аттестации и границы

Общий `CB21_RELEASE_DIGEST` и штатный preflight manifest обновляются как
fingerprints исходников для CI. Это не аттестация опубликованного CB21 runtime.
Четыре CB21 функции, `instagram-monitor` и `system-health-full-check` не
развёртываются ради изменения source hashes; их согласованные опубликованные
пакеты сохраняются. После объединения параллельных shared-code PR пересчитать
fingerprints и повторить проверки на точном итоговом HEAD.

Локальные тесты исполняют реальную миграцию и handler-ветки. Отдельная команда
`PG_TEST_BIN=<установленный PostgreSQL bin> node tests/sql/historical-manual-installment-concurrency.mjs`
создаёт собственный временный localhost cluster и проверяет два независимых
соединения: один договор/аудит, одна выдача и один финальный платёж при гонке.
Никаких production URL этот тест не принимает.
