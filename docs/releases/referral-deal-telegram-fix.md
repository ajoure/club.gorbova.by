# Реферальная выдача: сделка и Telegram

Существующая атомарная выдача уже создаёт REF orders_v2. Карточка контакта должна показывать их отдельно от денежных платежей: стоимость в бонусах, без денежного возврата и без добавления к оплаченной выручке. После выдачи обновляется contact-deals.

Worker использует существующие resolveAccessForOrder и telegram-grant-access с конечным сроком. Для активного доступа включено уведомление. Подтверждение доставки или канонический replay обязательны; HTTP 200 недостаточно. Перед повтором проверяется журнал доставки по order/source, включая ручную отправку. Отправленное сообщение без зеркала требует восстановления истории, автоматический повтор запрещён. До привязки Telegram сохраняется retry существующего outbox без новых pending notifications.

## Выпуск

1. Lovable PLAN-ONLY: свежие order/item/source/outbox и delivery evidence; без PII/ссылок/секретов.
2. PR checks PASS, merge, сверить точный SHA в Lovable.
3. Развернуть только referral-redemption-worker с локальным delivery.ts. Миграций нет. Остальные functions не менять.
4. Dry-run worker и отказ без авторизации. Для уже завершённой выдачи: сначала доказать отсутствие доставки; затем только её существующий outbox item вернуть в pending с точным ID, ожидаемая дельта 1, без нового redemption/order/source/списания. При подтверждённой доставке повтор не делать.
5. Read-back: canonical outgoing message + dm_sent + mirror, срок и единственность исходного source/order, неизменный баланс.
6. Publish, проверка карточки сделки на ПК и mobile, обезличенные скриншоты опубликованного результата.

Откат кода: revert PR и managed redeploy прежнего worker. Не удалять бизнес-записи и историю сообщений.
