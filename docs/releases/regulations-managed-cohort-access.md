# Регламенты бухгалтерии для последующих потоков ЦБ

## Граница изменения

Backend-only. Единственное изменение — product predicate в ветке полностью
оплаченной конечной рассрочки `user_has_access_to_rule`. Для регламентов продукт
выбирается существующим активным тарифным правилом `access_rules`, а не двумя
зашитыми UUID. Три других AI-инструмента остаются в прежнем scope ЦБ20/21.
Все проверки платежей, возвратов, личности, ручной проверки, срока и количества
циклов сохранены; обычная ветка подписки и продуктовых entitlements не меняется.
Не создаются пользователи, продукты, тарифы, правила, рассылки или новая подсистема.

## Настройка следующего потока администратором

После создания реально продаваемого потока: Products 2 → карточка нужного
продукта → Доступы → добавить правило типа «Доступ к разделу» →
«AI: Регламенты бухгалтерии» → выбрать конкретный тариф → включить правило.
Повторить для остальных тарифов, которым положен этот инструмент. Использовать
UUID раздела как `target_ref`, не строковый код. Не выбирать старые потоки,
другие ступени или глобальное правило без тарифа.

Название продукта не влияет на доступ. Новый продукт без настроенного правила
ничего не получает. Новые тарифы не наследуют правила автоматически: администратор
явно определяет их доступ в существующей карточке. После настройки обычная
действующая подписка или полностью оплаченная конечная рассрочка проходит
серверную проверку; отсутствие оплаты/истечение приобретённого периода — отказ
в ветке рассрочки. Existing `past_due` с действующим окном остаётся прежним
платформенным поведением, не переименовывается в неоплаченную покупку.

## STOP и rollback

При несовпадении exact SHA/source hash, новом правиле/продукте вне scope,
необъяснимой пользовательской дельте или новом критическом finding — STOP.
Миграция сама отвергает неизвестное тело функции и сохраняет ACL/owner через
CREATE OR REPLACE; повторное применение допускает только тот же точный патч.
Rollback — отдельная GitHub migration возвращает единственный predicate,
после проверки exact post-definition; контрольная сумма возвращается к исходной.
Нельзя повторно применять старую миграцию как обход migration journal или
откатывать чужие изменения. После rollback read-back owner/ACL/наборов доступа.

Существующий finding: authenticated может вызывать RPC с чужим p_user и узнать
boolean состояния доступа. Эта миграция не расширяет callable ACL и не
исправляет глобальный контракт; finding не скрывать, вынести отдельно.
