# Исправление продукта ошибочной оплаты в карточке контакта

Нативное действие администратора сначала показывает проверенный расчёт, затем
атомарно исправляет продукт одной полностью оплаченной покупки. Банковская
квитанция и идентификатор/сумма её распределения сохраняются. Операция не
создаёт списание, возврат, новую покупку или отмену подписки провайдера.

Область намеренно узкая: единственная покупка Club на 250 BYN с одним primary
item, доказанная отдельная предыдущая оплата Club и существующая подписка BBB.
Восстанавливаются основной период Club и десять бонусов с точными прежними
датами из успешного `access_grant_ledger`. Неполное доказательство, последующая
независимая выдача, конфликт графа, возврат, реферальное распределение или
активное автосписание Club блокируют действие. Pending mandate допускается
только без расписания/списания и платежей связанного заказа.

BBB получает 30 дней от существующей границы оплаченного периода. Перед
изменением сервер повторяет расчёт под блокировками и сверяет hash графа.
Provider rows дополнительно сверяются после записи: они должны сохраниться
целиком. Неопределённый результат клиент проверяет чтением прежнего запроса;
повторный dispatch автоматически не выполняется. Тот же request идемпотентен,
другой request для той же квитанции отклоняется.

Повторный вызов `grant-access-for-order` читает подтверждённую коррекцию до
manual-date, primary и bonus writers, включая 3DS. Без committed ledger
переигрывание блокируется. Старые записи grant ledger не переписываются;
точные до/после и основание сохраняются в отдельном реестре коррекции и аудите.

## Managed release

Кандидат требует отдельной ревизии и exact SHA checks. Координатор применяет
только миграцию `20261126133000_contact_payment_reallocation.sql` и развёртывает
`grant-access-for-order`. Производственную коррекцию выполняет координатор из
карточки контакта после свежего preview, проверки счётчиков и разрешения на
конкретный случай. Остановка отдельного provider mandate остаётся отдельным
действием с собственным подтверждением результата.

Новый helper меняет fingerprint всего `_shared`; `CB21_RELEASE_DIGEST` пересчитан
по прежнему алгоритму, manifest сгенерирован штатным скриптом. Это fingerprint
исходников кандидата. Он не подтверждает deployment других пакетов и не требует
их развёртывания. Исторические доказательства и verifier tests не изменены.

## Проверки и ограничения

PGlite исполняет саму миграцию: сохранение квитанций, раздельные даты бонусов,
идемпотентность повторов, stale graph, отказ без BEFORE, откат при ошибке аудита
и права администратора. Handler-тест исполняет актуальный grant handler для
повторных запросов основных вызывающих маршрутов; полномочия вызывающего
подменены в изолированном тесте. UI проверяет preview/confirm и восстановление
неопределённой операции. Отдельный тест запускает собственный PostgreSQL 17 с приватным Unix socket:
две сессии воспроизводят чтение старого grant, commit коррекции и старую запись
primary/bonus/meta, подписки, заказа, независимого entitlement source, grant ledger и Telegram. Дополнительно подтверждается
ожидание UPDATE на row lock до commit коррекции, затем отказ по свежему fence.
Триггеры БД запрещают восстановление исправленного графа старым payload;
будущая отдельная оплаченная покупка Club сохраняет возможность продления.
Одновременный повтор одного request создаёт одну коррекцию и один аудит;
ошибка финального аудита откатывает весь граф.

Production preview/read-back и desktop/mobile доказательства опубликованного
интерфейса ещё обязательны. До них изменение не считать выпущенным.

Локальный запуск PostgreSQL: `node --test scripts/tests/payment-reallocation-postgres-concurrency.test.mjs`. Он создаёт и останавливает собственный кластер PostgreSQL 17; 17 сценариев и родительский тест проходят без skips.
