## 2. Факты по API

### 2.1 Авторизация (Call.htm)

- Схема: HTTP `Authorization: Basic base64(login:password)`. Альтернативно —
  параметры `login`/`password` в URL или JSON-теле POST.
- Content-Type: `application/json`. Метод всегда `POST`.
- Дополнительно рекомендуется передавать `X-Correlation-ID` (UUID v4) — «уникальность
  действия», рекомендовано при создании заказов. Не является Idempotency-Key в
  строгом смысле, но выступает как ключ дедупликации на стороне РР.
- Секретный ключ (`secretKey`) — это отдельный ключ **нотификаций** для каждого
  аккаунта партнёра. Используется только для проверки подписи webhook, НЕ для
  HTTP-auth (см. ProcNotifications.htm).
- Timestamp/rewind в подписи запросов — **нет** (в отличие от подписи нотификаций).
- Раздельные host/endpoint для test vs battle в доках **явно не указаны**.
  Косвенное упоминание тестового режима: «в тестовом режиме валюта партнёра РР
  всегда равна валюте заказа» (GetOrderStatus.htm, поле `receiptAmount`).
  **Открытый вопрос к РР**: активируется ли test-режим переключателем в кабинете
  партнёра при неизменном base URL `https://pay.rrllc.ru/api/v2`, или требуется
  отдельный host / отдельный аккаунт.

### 2.2 Создание заказа (CreateOrder.htm)

- URL: `POST https://pay.rrllc.ru/api/v2/createOrder`.
- Обязательные поля запроса:
  - `order.id` — id заказа в нотации магазина, до 80 символов. Используется как
    внешний ключ во всех дальнейших методах и приходит обратно в нотификациях
    как `id`.
  - `order.amount` — сумма заказа. Рекомендованный формат — строка `"37900.50"`
    (double также допустим). Единицы — рубли/валюта заказа (не minor units).
  - `order.items[]` — массив позиций (`name`, `quantity`, `price`).
  - `order.version` — версия API, для нас `"2.0"`.
- Валюта `order.currency` (необязательно, по умолчанию `RUB`): `RUB`, `BYN`,
  `KZT`, `KGS`, `UZS`.
- Опциональные: `notification_url`, `complete_url`, `fail_url`,
  `client_info.{first_name,last_name,middle_name,phone,email}`,
  `credit_variants`, `credit_mode`, `countries`, `extend_observe`.
- Минимальная сумма для рассрочки в самой спецификации API **не зафиксирована**.
  Порог 9 900 ₽ — продуктовое требование РР для схемы «рассрочка/кредит».
  Гейт применяется на нашей стороне (`PublicPayPage`), а не на стороне API.
- Идемпотентность: заголовок `X-Correlation-ID` (UUID v4, рекомендовано).
  Естественным ключом дедупликации выступает `order.id` — повторный `createOrder`
  с тем же id вернёт ошибку/существующий заказ (422 «business logic»).
- Ответ 200: `{ "status": "new", "link": "https://…" }` — `link` это страница
  оплаты РР, на которую редиректим клиента. Iframe **не используется**, чувствительных
  данных клиента на нашем фронте не собираем.

### 2.3 Статусы (Statuses.htm)

Основные статусы заказа (используются для автоматизации):

- `new` — заказ создан, страница оплаты не открывалась.
- `approved` — страница оплаты открыта.
- `accepted` — заявка отправлена, в очереди обработки.
- `wait_client`, `processing`, `approved_credit` — промежуточные.
- `authorized` — сумма авторизованных платежей/рассрочек = сумма заказа, один
  договор. **Финальный оплачено** для v1.
- `authorized_all` — сумма авторизаций = сумма заказа, но договоров несколько
  (актуально с API 1.1). **Также финальный оплачено**.
- `authorized_partially` — часть суммы авторизована (v1 НЕ считаем оплаченным).
- `rejected` — заявка отклонена.
- `canceled` — отменено магазином.
- `canceled_by_user` — отменено пользователем / клиент не вышел на связь.
- `refunded` — сделан возврат.

Расширенные статусы (`extend_status` в getOrderStatus) — только информационные,
на автоматизации не завязываемся. Цитата из доков (Statuses.htm §Интерпретация):
«Используйте обычные статусы для автоматического завершения заказов».

### 2.4 Webhook / нотификации (ProcNotifications.htm)

- URL нотификаций задаётся при создании заказа в поле `notification_url`.
  Регистрация URL глобально в кабинете партнёра не требуется (можно менять
  per-order).
- Метод: `POST`, тело — JSON. Retry-политика РР в доках не описана
  (**открытый вопрос к РР**: сколько попыток, интервал).
- Payload:
  ```json
  { "id": "<order.id>", "type": "order_changed|status_changed",
    "newStatus": "<status>", "salt": "<random>", "sign": "<hex md5>" }
  ```
- Подпись:
  ```
  sign = md5(newStatus + "_" + secretKey + "_" + salt)
  ```
  где `secretKey` — секретный ключ нотификаций аккаунта партнёра (у нас
  хранится в `integration_instances.config_secrets.secret_key`).
- Валидация: если `sign` не совпадает — нотификацию не обрабатывать.
- Стабильный external id для idempotency в `provider_events`:
  сочетание `(id, newStatus, salt)` уникально; для дедупликации разумно
  использовать `sign` (полное совпадение подписи = полный дубль payload) или
  `(id + newStatus + salt)`. Финализируется в контракте адаптера.
- Рекомендация РР: после каждой нотификации дополнительно дергать
  `getOrderStatus` — это «дополнительная проверка подлинности нотификации и
  получение подробностей о платежах». В нашем адаптере — обязательный шаг
  перед завершением заказа.

### 2.5 Статус-запрос (GetOrderStatus.htm)

- URL: `POST https://pay.rrllc.ru/api/v2/{orderId}/getOrderStatus` (orderId — часть пути).
- Возвращает `status`, `currency`, `amount`, `completedAmount`, `creditAmount`,
  `commission` (double, в валюте заказа), массив `payments[]` со статусами
  каждого договора (`wait|canceled|rejected|authorized`), суммами, комиссиями,
  выбранным сроком, банком-эмитентом, гражданством клиента.
- Rate-limit — общий: `429` + заголовок `X-Retry-After` (секунды до повтора).
  Числовых квот в доках нет.

### 2.6 Отмена / возврат

- В публичном API v2.0 endpoint отмены/возврата **не описан**.
- Терминальные негативные статусы (`canceled`, `canceled_by_user`, `rejected`,
  `refunded`) приходят как результат действий клиента/оператора/магазина в
  кабинете РР, но публичного `cancelOrder`/`refundOrder` в доках нет.
- Вывод для v1: отмену/возврат из нашей админки НЕ инициируем через API,
  только отражаем статус, полученный из webhook / `getOrderStatus`.

### 2.7 Комиссия

- Приходит в `getOrderStatus.commission` (double, валюта заказа), а также
  per-payment в `payments[i].commission` / `payments[i].creditCommission`.
- В webhook payload комиссии нет — только `newStatus`. Комиссию забираем
  всегда через `getOrderStatus` после финального статуса.
- Единицы: рубли/валюта заказа (double). Для хранения в `payments_v2` конвертируем
  в minor units: `Math.round(commission * 100)`.
- Знак: положительный, «потеря партнёра относительно суммы заказа».

### 2.8 Ошибки (Call.htm)

- HTTP: 200 успех, 400 общая ошибка, 401 auth, 403 доступ, 422 бизнес-логика,
  429 rate-limit (+ `X-Retry-After`), 500 неизвестная.
- Формат: `error.text` — человекочитаемое, `error.code` — числовой код,
  `error.subject.field` — поле, если ошибка по конкретному полю.
- Ретраибельные: 429 (с задержкой из `X-Retry-After`), 500 (с backoff).
  Терминальные: 400/401/403/422 — не ретраить, логировать и завершать
  execution с ошибкой.

### 2.9 Персональные данные

- `client_info` в `createOrder` **опциональны**. Все поля (ФИО, телефон, email)
  можно не передавать — клиент заполнит их на странице РР самостоятельно.
- Паспорт, адрес, место работы и прочие sensitive PII через API **не передаются**
  — их РР собирает у клиента напрямую на своей стороне (короткая/полная форма).
- Гражданство приходит **обратно** в `getOrderStatus.payments[i].citizenship`
  (ISO 3166-1 3-letter) — это результат выбора клиента, не наш ввод.

## 3. Stop-guards (вердикт)

| # | Проверка | Вердикт | Основание |
|---|----------|---------|-----------|
| 1 | Подпись webhook | ✅ YES | `md5(newStatus + "_" + secretKey + "_" + salt)` (ProcNotifications.htm) |
| 2 | Однозначный «финальный оплачено» статус | ✅ YES | `authorized` (v1.0/2.0), `authorized_all` (≥1.1) (Statuses.htm) |
| 3 | Стабильный external id для idempotency | ✅ YES | `order.id` (мы генерируем) + `(id, newStatus, salt, sign)` для дедупа webhook |
| 4 | Не требуется iframe с sensitive-данными на нашем фронте | ✅ YES | createOrder возвращает `link` для redirect (CreateOrder.htm) |
| 5 | Полный test flow без реальных денег | ⚠️ PARTIAL | Test-режим упоминается (GetOrderStatus.htm), но отдельный host/активация не задокументирована. **Открытый вопрос к РР** |
| 6 | API комиссии | ✅ YES | `getOrderStatus.commission` + per-payment (GetOrderStatus.htm) |
| 7 | Не требуется передача лишних PII на нашей стороне | ✅ YES | `client_info` полностью опционально, паспорт/адрес не передаются (CreateOrder.htm) |

**Итог: GO с одним открытым вопросом к РР** — уточнить активацию тестового
режима (тот же base URL с признаком test-аккаунта / отдельный host / отдельный
логин). До получения ответа — интеграция включается только в battle-режиме
после подтверждения; test-режим в UI сохраняется, но полный runtime-proof
переносится на этап после ответа РР.

## 4. Открытые вопросы к РР (нужно уточнить у поддержки перед battle-запуском)

1. Как активируется test-режим: отдельный host, отдельный аккаунт, флаг в
   кабинете? Есть ли URL вида `https://pay-test.rrllc.ru` или аналог?
2. Retry-политика для нотификаций: сколько попыток, интервал, требуется ли
   от нас конкретный HTTP-статус (200 vs 2xx) для подтверждения приёма?
3. Минимальная сумма 9 900 ₽ — это фиксированный порог продуктовой линейки
   или зависит от банка-партнёра и страны клиента?
4. Что происходит с уже созданным заказом (`order.id`) при повторном вызове
   `createOrder` с тем же id — возвращается существующий `link`, ошибка 422,
   создаётся новый? Влияет на нашу idempotency-стратегию.
5. Как правильно завершить заказ при `authorized_partially` — ждать до
   `authorized`/`authorized_all`, или считать частичную авторизацию поводом
   для partial-fulfillment (в v1 — нет, но хотим подтвердить у РР).

## 5. Runtime evidence

В этом шаге не выполнялось — probe не требовался (документация покрыла все
stop-guards, кроме №5, где ответ вне API-доков). Никаких вызовов к API РР
из проекта в рамках discovery не производилось.
