# Полный просмотр получателей рассылки

Проблема: окно показывало «Первые 50 из 59» без перехода к остальным.
SQL возвращал только первые 50 email-контактов, хотя total_count включал
также Telegram-получателей. Учебная ветка preview отдельно обрезала список до 100.

Патч добавляет страницы по 50 получателей, точный диапазон, переход назад/вперёд,
сброс страницы при смене фильтров, загрузку/ошибку/повтор, перенос длинных значений.
Список SQL строится из того же объединения адресатов, которое уже использует
счётчик. Основные resolvers, правила отбора, функции отправки и права не меняются.
Параметры страниц применяются только к preview. Старый сервер без метаданных
страницы вызывает явную ошибку, а не повторяет первые 50 под видом следующей страницы.

## Локальная проверка

- Vitest: сценарии 59 = 50 + 9, переход назад, смена фильтров, ошибка и повтор,
  несовместимый сервер, пустая аудитория.
- Endpoint: валидация пагинации, неизменность фильтров, подмена внутренних
  параметров, auth/RBAC, учебная аудитория из 259 адресатов и последняя страница.
- SQL: фактическая миграция выполнена дважды в одноразовом PGlite; 59 уникальных
  адресатов, 4 только с Telegram, одинаковые/пустые имена, стабильная сортировка,
  сохранение счётчиков, пустая и отсутствующая страница, ограничение размера,
  отказ неавторизованной роли. Это синтетический тест, не production read-back.
- Встроенный браузер: реальный компонент с синтетическим API, 390×844 и 1280×800;
  переход к 51–59, прокрутка до последнего адресата, перенос длинных имени/email,
  доступность навигации. Это локальный UI, не доказательство публикации.

SQL-тест использует только одноразовый PGlite и не принимает URL базы:

```sh
qa_dir=$(mktemp -d)
npm install --prefix "$qa_dir" --ignore-scripts --no-audit --no-fund @electric-sql/pglite
PGLITE_MODULE_PATH="$qa_dir/node_modules/@electric-sql/pglite/dist/index.js" node tests/sql/broadcast-audience-preview-pagination.mjs
```

## Переход в production после разрешения

1. В каноническом свободном чате Lovable провести PLAN-ONLY: без изменений
   сверить GitHub SHA, текущие определения preview RPC, миграции и Edge Function.
   Проверить отсутствие drift и совместимость существующих auth/filters.
2. После ревизии плана и зелёного CI слить PR. Зафиксировать точный merged SHA.
3. Через Lovable применить только
   `20260910073936_broadcast_audience_preview_pagination.sql`, затем развернуть
   только `broadcast-audience-preview` из merged SHA. Код/коммиты/новые миграции
   Lovable создавать запрещено. Табличные данные не изменяются.
4. Без отправки рассылок проверить preview: исходные фильтры, страницы 0/50,
   отсутствие повторов ID, совпадение объединения страниц со счётчиком;
   отдельно Telegram-only, обе выбранные платформы, пустой и учебный фильтры,
   закрытый доступ без прав. Выводить только обезличенные счётчики.
5. При расхождении SHA, определений RPC, счётчиков, missing dependency или ошибке
   остановиться до Publish. Учебный resolver сохраняет прежнюю семантику;
   совпадение с реальной отправкой проверяется read-only, реальные сообщения
   и создание контактов для smoke запрещены.
6. Только после PASS опубликовать интерфейс. Проверить опубликованный URL/SHA
   на ПК и мобильном viewport; два скриншота с обезличенными данными обязательны.

Rollback: вернуть frontend/Edge Function предыдущего проверенного SHA;
обратно совместимый RPC может оставаться, поскольку default page_limit = 50.
При необходимости вернуть только определение resolve_broadcast_audience из
предыдущего SHA через отдельно согласованную managed migration.
