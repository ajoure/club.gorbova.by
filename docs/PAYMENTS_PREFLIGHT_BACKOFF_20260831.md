# Учёт отказов предварительной проверки очереди

Продолжение платёжного патча после #408. Managed read-only ревизия 31.08.2026
подтвердила: первые 20 кандидатов `bepaid-queue-cron` — старые отказы провайдера
со счётчиком 0. `loadPlan` бросал ошибку до захвата записи, поэтому прежний
обработчик ошибок не назначал следующую попытку. Свежие записи могли ждать
за одними и теми же отказами.

## Контракт изменения

- `recordPreflightFailure` — явный opt-in автоматических обработчиков.
  Ручной exact-вызов без флага сохраняет прежние проверки без записи при
  ошибке preflight. `dryRun` не пишет независимо от флага.
- Opt-in требует исходную строку `expectedUpdatedAt` из JSON PostgREST,
  без преобразования формата или потери микросекунд.
- При неуспешном preflight единственный canonical worker меняет только
  очередь: `error`, счётчик +1, безопасный код ошибки, время попытки и
  повтор через час. После пяти проверок запись остаётся `error` для ручного
  разбора; `NULL next_retry_at` при attempts=5 не делает её кандидатом.
- Сеть, таймаут, HTTP 429/5xx и невалидный JSON провайдера —
  `recovery_provider_unavailable`: повтор через час без расходования пяти
  проверок. Дополнительных GET-повторов внутри одного вызова нет.
- CAS проверяет id/status/updated_at и возвращённую строку. Конкурирующая
  запись не перезаписывается. Это относится и к прежнему execute-error пути.
- Fresh processing, completed/successful, terminal/import и ошибки снимка
  не попадают в новый путь записи. Некорректный явный SBS также не меняет очередь.
- `bepaid-auto-process` учитывает next_retry_at до LIMIT. Canonical worker
  дополнительно откладывает ранние автоматические повторы до provider GET.
- Новый путь отказа не меняет платежи, заказы, подписки, доступы, долги,
  провайдерские подписки, уведомления или контакты. Отказ не превращается
  в успешную оплату. Флаг не запрещает штатное исполнение действительно
  успешного платежа; он не является режимом «никогда не выдавать доступ».

Проверка схемы: у очереди только BEFORE UPDATE триггер обновления updated_at;
он не отправляет уведомления и не запускает платёж. Существующая колонка
`max_attempts` не переопределяет нынешний общий лимит 5; изменение этой политики
не входит в патч. Архив и исторические строки с attempts>=5 не исправляются.

## Проверки и managed rollout

1. Unit/handler tests: declined, stale release, zero-write dry-run/manual,
   snapshot/CAS conflict, пять отказов, future retry, transport failure,
   terminal/import/fresh/completed exclusions, отрицательная авторизация.
2. Полный Vitest, build, Edge contract check и Deno check трёх wrappers.
3. Зелёный PR и exact merged SHA. Production только через канонический Lovable.
4. Deploy targets: `payments-reconcile`, `bepaid-queue-cron`,
   `bepaid-auto-process`, включая shared. Новых миграций/cron нет.
5. OPTIONS и отрицательная авторизация не заменяют runtime-proof. Для одной
   существующей declined-строки: свежий GET и exact dry-run с исходным CAS;
   контролируемый provider mismatch допустим, writes строго 0.
6. Отдельно согласованный exact non-dry-run с opt-in должен изменить ровно
   одну запись очереди. Независимый read-back проверяет её backoff и отсутствие
   любых финансовых/доступных/уведомительных эффектов. Массовый backlog не запускать.
7. Rollout сохраняет ограничения основного спринта: незавершённые оплаченные
   восстановления с клиентскими уведомлениями требуют прежнего согласования.
   Код/CI/merge этого патча сами по себе не являются Publish или закрытием спринта.

Rollback — revert кода через GitHub и managed deployment. Не сбрасывать
накопленные attempts и историю массово: любые необходимые обратные изменения
данных требуют отдельного точного снимка, CAS и read-back.
