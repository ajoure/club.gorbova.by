# CRM Automation v1 — rollout и приемка

Этот документ — runbook для отдельного контролируемого применения. Он **не**
выполняет миграции, не создаёт cron, не публикует Lovable и не включает
автоматизации в production.

## Граница среды данных

Для `gorbova.by` каноническая база — **Lovable Cloud Supabase**, подключённая к
проекту Lovable. Отдельной самостоятельно управляемой Supabase-среды для
rollout нет. Любые изменения базы, RLS, Edge Functions, scheduler/cron,
feature flag или production-данных выполняются **только через явную задачу в
Lovable** после проверки очереди, текущего commit и отсутствия чужого
незавершённого запуска. Не применять изменения напрямую через Supabase MCP,
CLI или сторонний Supabase-проект.

## Что входит в v1

Автоматизации живут в существующих `crm_pipelines` и
`crm_pipeline_stages`, а сущность сделки остаётся `orders_v2`. В production
должны попасть миграции CRM Automation v1–v17, UI настроек воронки и Edge
Function `crm-pipeline-automation-worker` вместе с уже используемыми
`send-email` и `telegram-send-notification`.

Выполняемые источники: вход/выход из стадии, создание сделки, подтверждённый
платёж, изменение белого списка полей, задержка после входа в стадию, точная
дата-время, дни недели и число/последний день месяца. Действия v1: создание
CRM-задачи, Email, Telegram, fallback канала, а также no/error follow-up
задачи. Полный будущий каталог и его ограничения описаны в
[MASTER_SPRINT.md](MASTER_SPRINT.md).

## Обязательный preflight

1. Зафиксировать backup/restore point и окна ответственных за CRM, Email и
   Telegram. Изменения схемы и Edge Functions не выполнять параллельно с
   другим release в этой базе.
2. Сверить порядок миграций, начиная с
   `20260723092218_crm_pipeline_automation_stage_entry_v1.sql` и заканчивая
   `20260723140518_crm_pipeline_automation_deal_field_changed_v17.sql`, с
   фактической migration history целевого проекта. При расхождении остановить
   rollout: не использовать `supabase db push` поверх неизвестной истории.
3. Убедиться, что feature flag остаётся выключенным:
   `app_settings.feature_crm_pipeline_automation_v1 = false`. Миграции создают
   правила и триггеры, но без флага не enqueue-ят новые jobs.
4. Проверить service-role секреты и URL в среде трёх Functions. Никакой
   service-role key, SMTP credential или Telegram token не должен появиться в
   браузере, SQL-логе или коммите.
5. Проверить, что `email_templates`, SMTP account и Telegram-связка тестовой
   сделки уже существуют. Для Telegram нужен допустимый пользователь и
   специальный `message_type=crm_pipeline_automation`; произвольный текстовой
   sender не является частью v1.
6. Выполнить database tests в изолированной базе с включённым `pgtap`, затем
   build и Vitest в release commit. Green CI не заменяет этот шаг.

## Порядок контролируемого включения

1. Применить миграции в утверждённом порядке при выключенном flag и проверить
   objects: таблицы/constraints/routines/triggers, RLS и отсутствие EXECUTE у
   `authenticated` для enqueue routines.
2. Развернуть Functions как один совместимый набор:
   `crm-pipeline-automation-worker`, `send-email`,
   `telegram-send-notification`. До запуска не создавать пользовательских
   правил и не включать flag.
3. Настроить **один** защищённый scheduler вызова worker. Он должен передавать
   service-role только из server-side secret/Vault, иметь явное имя, частоту и
   журнал. Конкретный cron/secret создаётся отдельным одобренным change, а не
   этой веткой.
4. Включить flag только для изолированного smoke-окна. Создать одну тестовую
   воронку/стадию и по одному активному правилу каждого проверяемого типа.
5. Прогнать матрицу ниже, зафиксировать journal/logs и выключить тестовые
   правила. Только после этого включать реальные правила сначала в одной
   воронке, затем поэтапно в остальных.

## Live-smoke матрица

Для каждого сценария подтвердить: создан ровно один job, worker обработал его
до ожидаемого состояния, журнал содержит rule/version/deal/event, а повтор
того же delivery не создал второй side effect.

| Сценарий | Ожидаемое доказательство |
| --- | --- |
| Вход и выход из стадии | один job; `deal_left_stage` не требует оставаться в исходной стадии |
| Создание сделки | job только для выбранной стартовой стадии |
| Подтверждение платежа | `payments_v2.status = succeeded` создаёт job, refund/deleted не создают |
| Изменение поля | job только для выбранного whitelist-поля; update иного поля игнорируется |
| Задержка после входа | время учитывает quiet hours; ушедшая из стадии сделка получает `skipped` |
| Точная дата-время | запуск один раз в timezone правила; повторный tick не дублирует |
| Дни недели | запуск лишь в выбранные дни/локальное время |
| День месяца | 31-е не переносится на короткий месяц; «последний день» работает в феврале |
| CRM-задача | создана каноническим `crm_task_create`; повтор worker восстанавливает, а не дублирует |
| Email/Telegram и fallback | есть запись канонического writer и idempotency key; fallback только после финальной ошибки канала |
| Условия/no/error | несоответствие — `skipped` и один no-task; финальная ошибка — один error-task |

Проверять не только HTTP `200`: это подтверждает приём команды, но не
создание задачи, доставку канала или фиксацию journal. Нужны записи
`crm_pipeline_automation_jobs`, journal, `crm_tasks` либо канонических
channel logs и визуальная проверка настроек существующей воронки.

## Откат и аварийная остановка

1. Немедленно поставить активные правила на паузу и выключить feature flag,
   чтобы прекратить новое enqueue. Не удалять историю, опубликованные версии
   или jobs вручную.
2. Отдельно проинвентаризировать pending/running jobs: flag ограничивает
   источники событий, но не является доказательством отмены уже claimed job.
   Решение — безопасно дообработать, вручную пометить по утверждённой процедуре
   или остановить scheduler — принимается после просмотра очереди.
3. Сохранить job/journal/channel error, время, rule version и correlation key
   для разбора. Только затем исправлять правило или Function в новой ветке.
4. Откат схемы — отдельная миграция после оценки зависимостей; не применять
   destructive rollback "на глаз" к опубликованной истории.

## Граница v1

Не включены до появления серверных event contracts: просрочка платежа, открытие
и клик Email, ответ Telegram, рабочие дни с производственным календарём,
ручной/API запуск, а также wait-nodes, success/timeout branches, циклы,
универсальные entities и аналитика. Эти пункты остаются планом развития, а не
скрытыми обещаниями текущего release.
