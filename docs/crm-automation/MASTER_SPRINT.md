# CRM Automation — мастер-спринт

## Итоговая цель

Создать единую систему автоматизации вокруг существующих `crm_pipelines`,
`crm_pipeline_stages` и сделок `orders_v2`. Администратор настраивает действия
внутри воронки, а не в каждом продукте или оффере. Продукт отвечает только за
маршрутизацию новой сделки в воронку и стартовую стадию.

Система должна:

- показывать автоматизации непосредственно под стадиями воронки;
- поддерживать черновики и неизменяемые опубликованные версии;
- выполнять действия асинхронно, идемпотентно и без блокировки сделки;
- сохранять историю каждого запуска, шага, результата и ошибки;
- переиспользовать канонические CRM-задачи, Email и Telegram;
- позднее поддержать контакты, обучение и вебинары без второго движка.

## UX-принципы

- Стадиальная сетка как в Digital Pipeline, но в визуальном языке текущей CRM.
- Тонкие цветовые акценты стадии, компактные карточки и небольшие кнопки.
- Glassmorphism только как слой иерархии: полупрозрачный фон, blur, тонкая рамка.
- Быстрое действие на стадии доступно без перехода в отдельный конструктор.
- Сложный граф появляется только тогда, когда есть ветвление или ожидание.
- В UI всегда различимы «черновик», «опубликовано», «пауза» и «ошибка».
- Справочный каталог триггеров показывает описание и статус готовности; он не
  позволяет сохранить вариант без server-side event contract.

## Этапы

### 0. Фундамент и архитектурные границы

Результат:

- один мастер-план и словарь сущностей;
- подтверждены канонические таблицы и writers;
- отдельная ветка и feature-safe реализация;
- Lovable и production не затрагиваются.

Приёмка:

- `orders_v2` остаётся сущностью сделки;
- `crm_pipelines`/`crm_pipeline_stages` остаются единственными CRM-воронками;
- новые действия используют существующие writers, например `crm_task_create`.

### 1. Первый вертикальный сценарий

Сценарий:

> После входа сделки в выбранную стадию один раз создать CRM-задачу.

Результат:

- версионируемое правило;
- опубликованная версия неизменяема;
- событие смены стадии ставит работу в очередь;
- worker создаёт задачу через канонический writer;
- повтор события не создаёт дубль;
- ошибка автоматизации не откатывает перемещение сделки;
- журнал показывает `pending/running/succeeded/failed/dead`.

Приёмка:

- правило создаётся из настроек существующей воронки;
- можно выбрать стадию, тип задачи, заголовок, срок и исполнителя;
- есть черновик, публикация, пауза и архив;
- DB-тест доказывает enqueue и идемпотентность;
- UI проходит production build.

### 2. Время и каналы

- [x] задержки и «всё ещё в стадии»;
- [x] журнал последних запусков в настройках воронки;
- [x] отдельный исход `skipped`, если сделка покинула стадию;
- [x] quiet hours и timezone;
- [x] Email как отдельное действие через существующий SMTP writer;
- [x] Telegram как отдельное действие;
- [x] fallback-ветка канала;
- [x] retry/backoff и ручной повтор;
- [x] восстановление уже созданной задачи после сбоя фиксации результата.

Расписание вычисляется в часовом поясе правила и учитывает переходы DST через
PostgreSQL `AT TIME ZONE`. Тихий период может пересекать полночь. Ручной повтор
доступен только admin/super_admin и не создаёт вторую задачу: worker использует
канонический `crm_tasks_automation_uniq` и восстанавливает существующий side
effect по `automation_rule_id + deal_id`.

Инвентаризация каналов:

- канонический Email writer — Edge Function `send-email`, журнал — `email_logs`;
- канонический Telegram writer — `telegram-send-notification`, журнал —
  `telegram_messages`;
- произвольный CRM-текст пока не подключается к Telegram: service-role контракт
  writer ограничивает допустимые `message_type`. Расширение должно сохранить
  whitelist, шаблоны, idempotency и зеркалирование, а не создавать второй sender.

Email-действие:

- выбирает существующий активный `email_templates`;
- сохраняет subject/body snapshot в опубликованной версии правила;
- берёт получателя из `orders_v2.customer_email`;
- вызывает канонический `send-email`, который выбирает существующий SMTP account;
- пишет контекст сделки, правила и job в `email_logs`;
- использует уникальный `automation_idempotency_key`, поэтому повтор worker не
  отправляет второе письмо после уже принятого SMTP результата;
- не использует Lovable transactional queue.

Telegram-действие:

- использует существующий `telegram-send-notification`;
- доступно service-role только как специальный тип `crm_pipeline_automation`;
- проверяет связку `running job → send_telegram rule → deal → user_id`;
- принимает только idempotency key формата `crm-pipeline:{job_id}`;
- сохраняет текст как snapshot опубликованной версии;
- зеркалит успешное сообщение в `telegram_messages` для Contact Center;
- сохраняет outbox, audit и `telegram_logs`, не создавая второго Telegram sender.

Fallback канала:

- доступен только для противоположной пары Email → Telegram или Telegram → Email;
- не срабатывает на временной ошибке: основной канал получает все пять попыток
  с backoff;
- резерв запускается только на последней попытке и использует тот же job-scoped
  idempotency key в отдельном каноническом writer;
- опубликованная версия хранит snapshot резервного шаблона и запрещает его
  изменение;
- Telegram fallback дополнительно проверяет `attempt_count >= 5`, связь
  job/rule/deal/user и `fallback_action_type` внутри канонического sender;
- журнал отмечает `fallback_used`, исходный канал и ошибку основного канала.

### 3. Условия и ветвления

- [x] AND/OR/NOT для белого списка полей сделки;
- [x] ветка `no` (условия не совпали → задача);
- [x] ветка `error` (окончательная ошибка → задача);
- ветки success/timeout;
- ожидание платежа, клика, ответа и изменения сделки;
- ограниченные циклы и общий TTL;
- визуальный граф и проверка перед публикацией.

Условия v1:

- один компактный AND/OR-блок до выполнения действия;
- до десяти предикатов, каждый может быть инвертирован через NOT;
- поля и операторы ограничены серверным whitelist, произвольный SQL/JS запрещён;
- числовые сравнения принимают только JSON number;
- несовпадение завершает job исходом `skipped` с причиной
  `conditions_not_met`, не расходует retry и не запускает fallback;
- конфигурация валидируется CHECK constraint и входит в неизменяемый snapshot
  опубликованной версии.

Ветка `no` v1:

- доступна только если у правила есть условия;
- создаёт одну каноническую CRM-задачу вместо основного действия;
- сохраняет `no_branch_task_id` в результате job и оставляет исход `skipped`;
- использует отдельный `pipeline_automation_rule_id` в `crm_tasks`, поэтому не
  пересекается с legacy offer-level automation rules;
- ключ `(pipeline_automation_rule_id, deal_id)` обеспечивает идемпотентность
  follow-up задачи.

Ветка `error` v1:

- запускается только на пятой, окончательной ошибке job;
- не запускается, если fallback Email/Telegram успешно завершил исходную job;
- создаёт одну каноническую CRM-задачу и сохраняет её id в dead-letter job;
- сохраняет основной error в metadata задачи, чтобы сотрудник видел причину;
- конфигурация ветки является неизменяемой после публикации.

### Каталог триггеров и календарных правил

Уже исполняется:

- `deal_entered_stage` — сделка вошла в выбранную стадию.
- `after_event` — через выбранный период после входа сделки в выбранную стадию.
- `at_datetime` — один раз в выбранные локальные дату и время для сделок,
  которые в этот момент находятся в выбранной стадии.

Уже исполняемые правила времени после событий:

- период в минутах, часах, днях или неделях, включая перенос из quiet hours;
- часовой пояс правила и DST-корректный расчёт PostgreSQL;
- проверка, что сделка всё ещё находится в стадии перед запуском.

Запланированный каталог (в меню отмечается `скоро`, пока нет полного DB/event
contract):

- движение: создание сделки, выход из стадии;
- поля: изменение ответственного, суммы, продукта, тарифа и других whitelist-полей;
- платежи: получена оплата, просрочка;
- коммуникации: открытие/клик Email, ответ Telegram;
- календарь: дни недели, день месяца, первый/последний/N-й рабочий день месяца;
- система: ручной запуск и защищённый API.

Для календарной конфигурации переиспользуются `DatePicker`, `DateTimePicker`,
`Calendar`, `Popover` и `Tooltip` из текущего дизайн-системы. Отдельный
производственный календарь праздников пока отсутствует, поэтому trigger
`business_day` нельзя включать до появления утверждённого справочника рабочих
дней по юрисдикции и часовому поясу.

`at_datetime` хранит локальные дату/время вместе с часовым поясом правила,
поэтому браузер сотрудника не меняет смысл настройки. При очередном тике
существующего CRM worker правило атомарно получает marker `scheduled_fired_at`,
создаёт идемпотентные job только для текущего состава стадии и далее использует
тот же журнал, retry, условия, quiet hours и канонические writers. Для live
rollout потребуется отдельная проверка service-role вызова worker по `pg_cron`:
в этом PR cron/секреты не создаются и production не меняется.

### 4. Универсальные сценарии

- `entity_type`: deal/contact/training_access/webinar_registration;

### 5. Аналитика и масштабирование

- статистика по версиям и узлам;
- цели, конверсия и A/B;
- шаблоны, папки, теги и медиабиблиотека;
- webhook/API actions;
- лимиты, rate limiting и операционные dashboard/alerts.

## Нефункциональные требования

- Идемпотентность на уровне БД.
- At-least-once доставка события без двойного side effect.
- Неизменяемые опубликованные версии.
- RLS на всех таблицах `public`; конфигурация — только admin/super_admin.
- Worker/RPC исполнения — только `service_role`.
- Секреты каналов никогда не передаются в браузер.
- Повторные попытки ограничены; после лимита job переходит в dead-letter.
- Архивирование вместо физического удаления опубликованной истории.
- Feature flag и обратимый rollout.

## Границы доказательств

Коммит и зелёная сборка доказывают только состояние GitHub-кода. Миграция,
Edge Function, cron, production UI и реальное создание задачи считаются
подтверждёнными только после отдельного применения и live smoke.
