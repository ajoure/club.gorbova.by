# Контекст ЦБ21 и консультации по клубу

Этот патч устраняет production-блокер PR467 и добавляет выбор других продуктов для консультации в существующих настройках контакт-центра. Смена разрешена владельцу при OFF/HUMAN_HOLD и проверке предыдущего значения; данные хранятся в `sales_campaigns.knowledge.consultation_product_ids`.

## Подтверждённая ошибка истории

Read-only проверка Lovable 8269: в тестовом Business-диалоге 8 сообщений; у одной неудачной исходящей отправки CRM `message_id=NULL`. PostgreSQL при DESC ставил её первой. Код останавливался с `history_boundary_unavailable` до вызова ИИ. Теперь граница выбирается только по присвоенным Telegram номерам, с NULLS LAST. Неотправленный черновик не становится состоявшейся репликой. Регрессия воспроизводит оба SQL-результата. Во внешнем catch синтетического сценария появились безопасные `stage/reason`, без текстов клиента и провайдера.

## Источники условий

Runtime обращается к существующему публичному `public-product` текущего managed-проекта по выбранным ID. Оттуда берутся действующие публичные тарифы, их видимые описания, состав, доступы и кнопки. Нового каталога, фиксированных цен или отдельного выдающего доступы механизма нет. Связанные продукты не добавляются в checkout ЦБ21.

Цена другого продукта называется только при совпадении публичной цены и действующего полного платежа без специального условия покупки. При расхождении цену не выбираем самостоятельно. Отсутствие источника не мешает читать ЦБ: для недоступного продукта нет подтверждённых фактов, вопрос передаётся человеку. Содержимое уроков, закрытая база вопросов, отзывы с персональными данными и подписанные ссылки не загружаются.

Вопросы о клубе используют собственные факты `related_product`, а не цену или состав ЦБ. Сценарий ЦБ и этапы до цены сохраняются. Учебные решения не выдаются. При покупке другого продукта нужен человек; этот спринт автоматизирует оформление ЦБ21.

## Проверка и выпуск

- Синтетический `new_client` содержит **6 шагов**, включая выбор оформления без создания ссылки. `graduate` — 5. Ранее в запросах на deploy ошибочно указывались 5 шагов для нового клиента.
- Новый `club_consultation` проходит ту же диагностику и в шестом шаге спрашивает про FULL клуба. Ожидается ответ подтверждёнными фактами клуба.
- `preview_image` проверяет отсутствие выдуманного текста на пустой картинке; `preview_image_text` — распознавание 404 на фиксированной служебной картинке. Реальных сообщений, вложений, платежей и записей кэша эти проверки не создают.
- Managed-копия `20260912112527_21624fbd-6791-42e7-95f8-6ded9de89bd7.sql` совпала с исходным AI SQL105739; она заменена на проверяющий маркер. Нужно зарегистрировать оригинальную версию105739 как уже применённую после точной сверки stored SQL, без повторного DDL.
- Новая миграция `20260912112411_sales_consultation_products.sql`: только идемпотентная функция настройки и service-only grants. После ревизии/merge deploy двух функций: `sales-runtime-worker`, `sales-runtime-control`.
- Настройку клуба применить через тот же `sales_configure_knowledge_products`, что вызывает администратор: одна существующая кампания, существующий владелец, продукт Gorbova Club, ожидаемое исходное значение обязательно read-back. Не включать кампанию. После — синтетические сценарии и чтение условий клуба, затем Publish и ПК/mobile.

Полная синхронизация тарифов20→21 ждёт дат и решения по конференциям. 59 расшифровок и дополнительные карточки требуют отдельного подтверждения полноты/формулировок; этот патч не объявляет их все проверенными.
