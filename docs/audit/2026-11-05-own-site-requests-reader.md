# Собственные заявки с сайта в истории покупок

## Проблема и результат изменения

Авторизованная форма сайта сохраняет отправку и CRM-черновик, но вкладка
предзаписей читала только `course_preregistrations`. Поэтому существующее
обращение могло отсутствовать в клиентской истории. Изменение добавляет
отдельную проекцию **«Заявка с сайта»**, сохраняя прежние предзаписи на курсы.
Заявка не классифицируется как предзапись по названию продукта или нулю цены.

## Граница чтения

`get_my_site_requests()` не принимает аргументы и требует ненулевой `auth.uid()`
и роль `authenticated`, без обходов для администратора или service role.
Это `STABLE SECURITY DEFINER` с пустым `search_path` и полными именами объектов;
PUBLIC, anon и service_role не получают EXECUTE. Табличные grants и RLS не
меняются. Миграция применяет функцию и ACL одной атомарной командой DO.

Условия выдачи строки:

- Ровно один активный, неархивный, неслитый canonical profile текущего auth.
- Существующие processed `site_form_auth` с JSON boolean `auth_mode=true` и
  серверными actor/product/tariff, совпадающими с профилем и заказом.
- Неудалённый order с тем же профилем; nonnull user_id не противоречит actor.
- Совпадают исходные page/workspace, source и product/tariff; нулевой UUID
  workspace допустим, если это точное сохранённое значение.
- Указанный в order origin сам проходит все проверки. Поздняя авторизованная
  отправка не легализует старый legacy/foreign origin.

Одна строка на существующий order, с самой ранней проверенной отправкой.
Нет скрытого LIMIT, отбрасывающего часть истории. Проекционный дубль против
курсовой предзаписи снимается только по точной ссылке order→course, backlink,
одинаковому владельцу и product/tariff. Одного course.meta недостаточно:
исторический публичный INSERT позволяет передавать эти метаданные.

Возвращаются только id/kind/source_id/submitted_at/product_name/tariff_name/status.
Ответ не содержит контактов, form_data, notes, metadata или платёжных полей.
`received` описывает получение исходного обращения; статус финансовой сделки
не превращается в обещание места, оплаты или доступа.

## Интерфейс и границы scope

Вкладка «Заявки» содержит два различимых списка. Длинное название заявки
переносится, дата сохраняется. Ошибки двух источников показаны отдельно от
успешного пустого результата; доступна только повторная загрузка чтения.
Новых действий создания, оплаты, отмены или выдачи права нет.

Writers, существующие данные, user_id, даты, оплаты, права, приглашения,
уведомления и правила истёкшего доступа не изменяются. Неактивный исторический
каталог не становится активным правом и сам по себе не стирает обращение.

## Проверки

Реальные SQL-контракты выполняет отдельный workflow
`site-requests-reader.yml` на официальном `postgres:17`. Он применяет именно
managed-миграцию к синтетической схеме, ролям и данным. В тестах нет клиентских
идентификаторов, production-соединений или ключей. Harness принимает только
явно включённую тестовую БД `site_requests_reader_test` на loopback.

Покрыты ACL, NULL uid/role, foreign user, неоднозначный/архивный/merged профиль,
конфликт владельца, legacy/необработанные/повреждённые метаданные, origin
laundering, page/workspace/product/tariff/delete, реальные повторения и разные
заказы, earliest date, доверенный и недоверенный course dedup. Прямое чтение
исходных authNULL orders и form submissions обычным клиентом остаётся закрыто.
Проверяется точная форма ответа и отсутствие DML после повторных чтений.

Фактические результаты конкретного head CI прикладываются к PR и приватному
checkpoint. Наличие этого документа само по себе не утверждает PASS workflow
или применение миграции в production.

После разрешённого выпуска нужны реальные обезличенные снимки опубликованной
страницы на ПК и телефоне: исходная заявка с датой, прежняя отдельная
предзапись, читаемый текст и отсутствие изменений прав. Новую заявку для
проверки не подавать. Merge, managed apply и Publish выполняет координатор.
