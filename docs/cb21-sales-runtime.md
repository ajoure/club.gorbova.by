# Автопродажи ЦБ21: первый тест в личном Telegram

Входящие Business-сообщения раньше только сохранялись в контакт-центре. Этот
спринт подключает постоянную очередь, ограниченный выбор проверенных реплик,
отправку через существующее Business-подключение и управление разговором.

Первый запуск разрешён только для одного подтверждённого диалога Сергея.
`owner_test` — явное исключение для теста без анкеты, а не фиктивная предзапись.
Режим клиентской кампании отсутствует в допустимых значениях таблицы; перед
массовым запуском требуется согласование текстов и реальной связи с анкетой.

## Поведение

- Только новое входящее `Хочу программу курса ЦБ`, с нормализацией регистра и
  пробелов. Исторический импорт, редактирование, echo, другой пользователь,
  другой бот или Business-аккаунт не активируют разговор.
- Случайная задержка 60–180 секунд. Новое сообщение отменяет старый проект
  ответа и создаёт новый срок. Планировщик проверяет очередь каждые 10 секунд;
  к выбранному интервалу добавляются этот такт и время подготовки ответа.
- Модель выбирает ID фактов и максимум одного вопроса; клиентский текст
  собирается сервером из банка. Полные транскрипты, учебные решения,
  персональные платёжные данные и несвязанные уведомления бота не передаются.
- После ответа — `WAIT_CUSTOMER`. Нет автоматических напоминаний.
- Пауза отменяет ожидающий и подготовленный ответ. Если отправка уже передана
  Telegram, отозвать её нельзя; интерфейс показывает это и блокирует следующие.
- Продолжение сохраняет этап и перечитывает историю. Если ответил человек —
  ждать клиента; если есть новое неотвеченное входящее — один ответ с задержкой.
- Неизвестная доставка блокирует повтор и автоматическое продолжение.
- Сложный вопрос, ошибка подготовки, просьба позвать человека — точное
  поручение Сергею и внутреннее уведомление. В клиентский диалог ничего не
  отправляется. Отказ от общения переводит разговор в STOPPED.
- На прямой вопрос об автоматизации помощник отвечает честно.

## Источники

`scripts/sales-knowledge/cb21-owner-test-pack.json` содержит 22 описания тем,
связанных с ЦБ21: 9 после полного тематического прочтения и 13 после проверки
контекстов. Это редакторский пакет для теста с владельцем, не утверждённый
клиентский релиз. Исходные расшифровки остаются закрытыми в существующем корпусе.
Runtime проверяет их ревизии и SHA без чтения текста уроков. Программа, текущие
даты, стоимость полной оплаты, длительность доступа и состав тарифов читаются
из текущих таблиц продукта. Исторические цены не используются.

Нестандартная рассрочка, скидка и персональная ссылка на оплату передаются
оператору через существующий механизм поручения. Платёжные API не вызываются
для теста разговора. Отзывы без согласованного текста не добавляются.

## Публикация через Lovable

После GitHub checks и merge:

1. Сверить точный SHA; выполнить только две миграции этого PR в указанном порядке.
   Сначала проверить pg_cron >= 1.5, Vault/pg_net и канонический Cloud-проект.
2. Deploy только `sales-runtime-control`, `sales-runtime-worker`,
   `telegram-admin-chat`, `telegram-webhook`. Никаких новых файлов/коммитов в Lovable.
3. Создать одну выключенную кампанию `cb21-owner-test`, используя подтверждённые
   message UUID → user UUID, bot UUID и Business row UUID. Ответственный — тот
   же подтверждённый Сергей с `communication:manage`. Загрузить JSON пакета
   дословно, `knowledge_version` = SHA256 файла, `policy_version=cb21-v1`.
   Проверить product, flow, root, 22 источника; не менять обычные AI settings.
4. Создать единственную строку разговора в OFF. Проверить отсутствие jobs/outbox.
5. Защищённые health и preview: health не вызывает модель, preview использует
   существующий gateway и возвращает только проект ответа без отправки/очереди.
   Секрет читать только сервером из Vault, не выводить в ответ/логи/команду cron.
6. Без исходящих сообщений проверить pause/resume в OFF и настройки 60–180;
   затем включить тест через `sales_control`. Прочитать enabled_at, scope,
   состояние OFF, jobs=0, отсутствие исходящих. Старый кодовый запрос не переигрывать.
7. Publish после PASS. Проверить опубликованный контрол на ПК и мобильном
   viewport, сохранить два скриншота области контролов без персональных данных.
8. Только после этого пригласить Сергея отправить новую кодовую фразу. Проверить
   её ID → один job → случайный due_at → один Telegram message ID → WAIT_CUSTOMER.
   Следующий этап приёмки — пауза, ручной ответ, продолжение и handoff в этом
   же тестовом диалоге.

## Проверки

PGlite исполняет реальную миграцию: область активации, старые события,
случайный срок, объединение сообщений, атомарный claim, ручной ответ,
WAIT_CUSTOMER, pause/resume, неизвестная доставка, точное поручение, смена
истории/политики, новое входящее во время отправки, истечение генерации, RLS.
Тесты интерфейса проверяют область команды и запрет продолжения при неизвестной
доставке. Полный существующий пакет контрактов и сборка обязательны.
