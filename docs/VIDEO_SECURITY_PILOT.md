# Защита видео: подготовка и пилот без регрессии

Дата: 2026-10-29. Исходный main: `a107a84875a0c209c7e28c6130669d13d01867ce`.
Пользователь согласовал подготовку и изолированный пилот, отдельно потребовал
сохранить паузу, перемотку записей и продолжение с места остановки. Время
изменения боевых видео согласуется отдельно после приёмки. Текущий эфир исключён.

## Статус и границы этого PR

**DRAFT / NO-GO для production. Полное исправление ещё не реализовано.**

Подготовлены два пилотных endpoint, проверка настоящей подписи JWT, миграция
серверной проверки сессии, отдельная страница `/pilot/video-drm` и контроллер
обновления токена без замены iframe. Без полного отдельного конфига и двух
независимых секретов endpoint отвечают 404. Миграция пока не применена, функции
не развёрнуты, конфиг и секреты не установлены; Publish не выполнялся.

Пилотный ACL — явный серверный список контролируемых тестовых субъектов и
синтетических media UUID. Это НЕ подключение реальных lesson/live ACL и НЕ
приёмка всех ролей. Production consumers не подключаются к пилоту. В существующем
SDK-хуке изменены только диагностические сообщения, чтобы не печатать URL и
SDK-исключения с токеном. Управление существующим воспроизведением не изменено.

В Kinescope отдельно создан `Codex DRM Pilot 2026-10-29` с включённым DRM,
встраивание пока «Нигде». Загружен один синтетический пятиминутный ролик, без
материалов клиентов. Callback ещё не настроен, защищённое воспроизведение не
проверено. Зелёные unit-тесты не означают защищённое видео в production.

## Реализация изолированного пилота и оставшиеся условия включения

- `video-pilot-token`: проверяет подпись Supabase JWT через `getClaims`, issuer,
  audience, роль authenticated, sub/session_id/exp; анонимная Auth-сессия запрещена.
  Media выбирается по серверному mapping, клиент не выбирает произвольный UUID.
- `video-pilot-drm-callback`: Basic auth провайдера, проверка HS256 JWT библиотекой
  jose 6.2.3, issuer/audience/typ/subject/session/media/context/сроки, затем живая
  серверная проверка при каждом запросе лицензии. Повторные лицензии разрешены.
  Оба handler ограничивают тело 16 KiB и весь запрос 3,5 секунды. Ошибки не
  раскрывают исключения или токены, ответы no-store. Открытого fallback нет.
- `video_pilot_session_is_live`: только service_role; PUBLIC/anon/authenticated
  EXECUTE отозван. Проверяет пару user/session, auth-ban/deletion, активный не
  архивный/не слитый профиль, not_after, настройки timebox/inactivity и single
  session. `search_path=pg_catalog`, таблицы квалифицированы. Это SELECT без
  изменения пользователей, сессий и учебных прав.
- `VIDEO_DRM_PILOT_CONFIG`: enabled, sessionPolicyVerified, subjects (1–5 UUID),
  media (1–4 записи key/id/type/playerId), origins (1–4 точных HTTPS origin),
  ttlSeconds (30–300), sessionIdleSeconds/sessionMaxAgeSeconds и
  singleSessionPerUser. Два срока — положительные секунды либо **явный** null
  только если соответствующее ограничение отключено в проверенной Auth policy.
  Отсутствующие поля запрещены. Наличие not_after=null у сессий НЕ доказывает,
  что настройки Auth отключены. До проверки реальных настроек enabled=false.
- `VIDEO_DRM_PILOT_SIGNING_KEY` и `VIDEO_DRM_PILOT_PROVIDER_PASSWORD`: разные
  случайные значения по 32 байта (64 hex), только серверные secrets. Имя Basic
  пользователя `pilot-provider`. Kinescope API key этим endpoint не нужен.
- Страница пилота доступна через штатный вход, без ссылки в навигации. Проверка
  допуска всегда серверная. Использовать только preview и его точный origin,
  не добавлять production origin. Токен передаётся через playlist DRM options,
  не в URL. Смена токена вызывает только `setPlaylistItemOptions`.
- Диагностика SDK (позиция/пауза/скорость/качество) ограничена 300 мс на
  наблюдение. Ошибка или зависание getter до первого Play не блокирует обновление
  токена; в диагностике показывается отсутствие данных, не выдуманный PASS.
- При ошибке/истечении доступа контроллер ставит паузу и предлагает повторить
  проверку, не включает видео автоматически. Resume VOD хранит последнее время
  по паре user/asset, не максимум, и не наследуется другим пользователем или
  другим asset. Для live сохранённая позиция не применяется. Субтитры/качество
  и поведение после фонового режима требуют отдельного runtime-proof.

До merge/deploy необходимо получить точные UUID пилотных объектов, сверить
Auth policy и deployed schema (включая auth.users/profiles), закончить CI,
проверить callback strict=true и подготовить точный перечень применения.
Развёртывание — только Lovable с точным merged SHA и только двух названных
функций/одной названной миграции; сначала с выключенным конфигом. Боевой Publish
и подключение реальных consumers запрещены до отдельной приёмки и согласования.

## Подтверждённые исходные проблемы

- Гостевой просмотр двух существующих Kinescope player URL был воспроизведён
  в отдельном браузерном сеансе, включая видео из платного урока. Ссылки и
  персональные данные в репозиторий не включаются.
- В просмотренных настройках всех 24 проектов Kinescope шифрование выключено.
  Это инвентаризация настроек проектов, **не** всех индивидуальных overrides.
- `VideoBlock` при ошибке SDK использует прямой iframe и предлагает открыть
  отдельную вкладку. Legacy library, квест и live имеют другие прямые iframe.
- Скрытая кнопка скачивания не проверяет права при выдаче видеоданных.
- В hook нет платформенного сохранения позиции для обычной записи. Существующий
  `activeTimecode` — команда перехода по таймкоду, а не доказательство resume.
  SDK может сохранять позицию локально; это надо проверить на браузерах отдельно.

Браузерная baseline-проверка 2026-10-29: существующая запись, отдельное созданное
окно Chrome incognito, без входа в платформу. Play и Pause работают; на паузе
seek 00:11 → 00:16 → 00:11; затем seek 02:01, Play, Pause в 02:16. После reload
и Play через несколько секунд наблюдалось 02:28, то есть плеер продолжил около
предыдущей позиции, а не с начала. Это подтверждает локальное resume одной
незащищённой записи в том же browser storage. Точность ±2 секунды, новый браузер,
другой пользователь и защищённое воспроизведение этим не доказаны. Окно закрыто,
видео не скачивалось. Speed, subtitles, settings, PiP, fullscreen видны в UI,
но их работа в этом smoke не проверялась.

## Серверный доступ

1. Серверная карта content/block/lesson/live → provider UUID + media type.
   Короткий player slug не равен UUID callback. Не принимать mapping от клиента.
   Один asset может использоваться в нескольких разрешённых контекстах;
   проверка ведётся для конкретного контекста, не только случайного первого урока.
2. Для уроков повторно использовать `user_has_training_lesson_access`, актуальные
   release guards, наследование, исторические покупки и CB2-ограничения. Не
   переписывать это через один флаг «есть подписка». Сверить deployed определения
   с migrations перед подключением service-role.
3. Для live повторно использовать `verifyLiveBearerClaims`, `live_access_proofs`,
   `evaluateLiveAccessRule` и фазу комнаты. Для автовеба — существующую привязку
   viewer/session и исходное право на событие. Права сотрудника ограничены его
   разделами; слово admin на клиенте не является разрешением.
4. Provider callback не содержит Supabase-сессии посетителя: `auth.uid()` там
   не определяет зрителя. Проверенный subject/session извлекаются из разрешения;
   сервер явно проверяет их и контекст. Нельзя подменять это service-role bypass.
5. Разрешение ограничить audience/issuer, алгоритмом, сроком, media UUID/type,
   контекстом и сессией. Подпись проверяется до полей. Повторная проверка ACL и
   отзыва сессии при каждой выдаче лицензии; неизвестное/ошибка → запрет.
6. Callback требует отдельную аутентификацию провайдера, ограниченный размер тела,
   POST JSON, rate limit, timeout меньше 5 секунд и всегда 403 при отказе.
   Ответы выдачи разрешений — no-store. Ни JWT платформы, ни service key не
   передавать в плеер. Никаких токенов/полных URL/PII в диагностике.

## Ограничение защиты и блокер совместимости

**A. Принятый остаточный риск: полная ссылка может быть передана.** Документированный callback
передаёт token, id, type, IPv4 /24 и User-Agent. Второй браузер с теми же полями
неотличим от первого для такого backend. Локальный тест демонстрирует это:
оба запроса разрешены при ещё действующих правах владельца токена. Это модель
контракта, не утверждение о проверенном поведении live DRM провайдера.

Одноразовый токен не подходит: легитимный старт может потребовать две лицензии,
а seek, возобновление и live rotation — новые запросы. Ограничение одной сессией
без device proof может впустить чужого первым и выгнать покупателя. Доменный
allowlist, водяной знак, IP/UA и короткий TTL — дополнительные меры, не proof.

**B. Бесшовное обновление и resume надо доказать.** Срок токена не должен ломать
длинный эфир, долгую паузу, seek или возврат в приложение. Нужен штатный механизм
обновления/привязки лицензии без remount и проверка после истечения TTL. Если
provider не поддерживает нужный контракт, остановить интеграцию и согласовать
альтернативный плеер/лицензионный шлюз. Не вводить временный открытый fallback.

## Изолированный онлайн-пилот с согласованным остаточным риском

1. Создать отдельный Kinescope **проект** с синтетическим VOD и отдельным тестовым
   live; ни одного платного или текущего live asset. Настраивать project override,
   не workspace default. Перед действием записать точные ID и настройки.
2. Один тестовый backend/preview с явным allowlist этих UUID, отдельными secret
   names и существующими тестовыми учётными записями. Нет переноса пользовательских
   данных или покупки/создания пользователей ради smoke.
3. Получить DRM-ready status VOD; live создавать `protected:true`. Включить
   `strict:true`, точные разрешённые домены пилота, запрет прямого просмотра и
   источников/originals по подтверждённым provider controls. Приватная ссылка не
   должна обходить правила. Не полагаться только на скрытие кнопки Download.
4. Временные endpoint/миграции сначала через GitHub PR/CI; для Lovable Cloud —
   plan-only, ревизия Codex, exact SHA execute только названного пилота. Не
   встраивать код в боевые consumers до прохождения пилота.
5. Выполнить матрицу ниже. Хранить минимальные пруфы без URL-токенов и PII.
   Screenshot плеера + URL платформы + SHA + viewport; DRM callback журнал
   только outcome/reason/test-case, а не тело или подпись.

## Пакет внедрения после успешного пилота

- Полная инвентаризация per-file overrides, платного/публичного контента, аудио,
  вложений, playlist, дублей и старых live. Dry-run: точные ID, counts, ACL,
  encryption-ready, исключённые текущие эфиры, несовпадения → STOP.
- Подключить защиту ко всем consumers из таблицы, сохранить controls и стабильный
  lifecycle. В защищённом режиме ошибки не ведут к открытому iframe/новой вкладке.
- Если штатное resume не переживает защиту, добавить отдельное хранилище позиции
  пользователя/content/asset, не затирая существующие ответы/lesson progress.
  Сохранение по timeupdate с throttling и при pause/pagehide; восстановление после
  ready без неожиданного autoplay; end/replay и конфликт нескольких вкладок
  проверять отдельно. Это требуется до выпуска, а не после жалоб.
- При загрузке/публикации приватного видео проверять DRM, mapping и ACL; неполный
  контракт блокирует публикацию. Публичное промо требует явной классификации.
- Согласовать окно после текущего эфира, применить небольшую группу, read-back,
  runtime, затем следующие batches. Publish только после проверки backend/CI.
- Откат: вернуть последнюю рабочую **защищённую** конфигурацию. При отсутствии
  такой версии остановить rollout; не отключать auth и не открывать источники.
  DRM отключается через поддержку, поэтому включать его на боевом проекте как
  «быстрый обратимый эксперимент» нельзя.

## Ревизия Lovable и уточнения Codex

Read-only ревизия Lovable получена 2026-10-29 на исходном SHA; изменения в Cloud
не выполнялись. Направление принято с обязательными уточнениями:

- `user_lesson_progress`/completion не доказывают resume обычного видео.
- В callback нет viewer `auth.uid()`; использовать проверенный permit subject.
- `protected:true` относится к live; VOD включается через проектное DRM и readiness,
  не выдуманное универсальное поле `drm:true`.
- Исходное требование anti-replay уточнено пользователем 29.10.2026: риск
  передачи действующего токена принят для пилота. Долгий просмотр без регрессии
  остаётся обязательным. Concurrent-stream limit не доказывает device binding.
- Блокировка применяется на стороне provider. Удаление ссылок из HTML само по
  себе не закрывает видеоданные; старые открытые пути тоже проверяются.

криптографической привязки к устройству, браузерной сессии или license challenge.
Полный URL с действующим токеном остаётся bearer credential. Это подтверждает
блокер A; предлагаемая резервация `jti` не решает его, поскольку в callback нет
достоверного идентификатора нового зрителя. Нельзя принимать IP/UA за такой
идентификатор или ломать повторные лицензии одноразовым токеном.

Для обновления токена поддержка указала метод
`player.setPlaylistItemOptions({ drm: { auth: { token: freshJwt } } })`.
Метод и поле `drm.auth.token` независимо сверены с официальной документацией
«Управление плеером» (обновлена 07.10.2026). Это уточняет путь пилота по блокеру B,
но не доказывает сохранение позиции, качества, субтитров, паузы и следующей
лицензии. `setOptions` документирует только watermark; менять query URL нельзя.

Поддержка не гарантировала срок уже выданной лицензии, немедленный отзыв либо
полную DRM-совместимость PiP/Cast/AirPlay. Отказ callback действует на следующую
выдачу лицензии. Все эти пункты остаются обязательными онлайн-проверками.
Настройки workspace, проектов, видео и эфиров при обращении не менялись.

29.10.2026 пользователь выбрал: сначала пилот DRM, короткие токены и проверка
прав, принимая остаточный риск передачи действующего токена. Блокер A теперь
является явно принятым ограничением пилота, а не заявлением о непередаваемости.
Тест пересылки действующего токена должен зафиксировать фактическое поведение;
его успешное воспроизведение нельзя назвать PASS строгой защиты. Старые URL
без токена, истечение токена, отзыв сессии и отсутствие прав по-прежнему должны
запрещать следующую выдачу лицензии. Блокер B и вся матрица функций сохраняются.
Разрешение касается изолированного пилота, не внедрения на боевых видео.
