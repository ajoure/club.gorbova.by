# Проверка полного оплаченного периода перед завершением очереди

Продолжение backend-патча PR #404. Production preflight обнаружил, что
наличие ещё активного доступа не доказывает выдачу полного оплаченного периода.
Код меняется отдельно от корректировки конкретных production-записей.

## Изменения и границы

- Перед lease/CAS уже выполненная выдача проверяется по срокам обеих сущностей:
  подписки и entitlement. Недостаточное окно даёт
  `recovery_paid_access_window_short`, без записи, grant или закрытия очереди.
- Нижняя граница берётся из сохранённого окна этого платежа либо подтверждённой
  даты платежа и явной настройки календарного месяца. Для queue
  completion применяется точная граница, без допуска на недовыданные часы.
- Для существующих платежей по фиксированным/учебным тарифам без такого правила
  новый минимум не придумывается: очередной платёж рассрочки не означает покупку
  всей длительности курса заново. Их прежняя проверка не меняется.
- После реального grant проверяется тот же минимум, в том числе для уже
  существующего платежа. Успешный HTTP-ответ сам по себе не завершает очередь.
- Сохранённое окно принадлежит только заказу с UID текущего платежа. Новый REBILL
  не наследует окно предыдущего восстановленного цикла; повтор текущего цикла
  использует сохранённый конец, даже если позже изменили настройку тарифа.
- Повреждённое сохранённое окно, включая нулевую длительность, блокируется
  до lease/CAS и бизнес-записей.
- Подписки, платежи, provider state, сроки списаний и уведомления этот патч
  сам по себе не корректирует. Слишком короткий оплаченный период требует
  отдельного exact-плана с подтверждённой предыдущей границей, без NOW.

## Проверка

На базе #404 пять новых регрессионных случаев воспроизвели ложный успех:
короткая подписка, короткий entitlement, оба сразу, повтор completed-строки,
успешный downstream-ответ с недостаточным результатом. После исправления
проверяются также точная граница, повтор после частичной выдачи, смена тарифа
и переход к следующему платёжному циклу.

Managed rollout остаётся последовательным: зелёный отдельный PR → exact
merged SHA → перечисленные workers из документа #404 → exact dry-run и
read-back → Publish только после закрытия критических findings. Код и
успешные тесты не являются доказательством production-исправления.
