# Проверка системы и права чтения — 21.10.2026

Область: RateLimit в `system-health-full-check`, 22 таблицы из quick scan,
дополнительно `fields`, `document_token_registry` и UPDATE `telegram-media`.
Источник production — существующий Lovable Cloud. Код — GitHub.

## Подтверждённые причины

- В одной цепочке было 172 OPTIONS. После 30 вызовов hosted runtime возвращал
  `RateLimitError`. Это не лимит платёжного/почтового провайдера.
- `ERROR` и `CORS_ERROR` ошибочно входили в healthy, транспортные ошибки — в
  deployed. Ответ `204` рассылки не входил в старый список expected statuses.
- 22 широкие SELECT-политики, ещё два чтения без проверки области; лишние
  TRUNCATE/REFERENCES/TRIGGER/MAINTAIN у клиентских ролей. RLS не защищает
  TRUNCATE. Наличие ACL не означает существование REST-метода TRUNCATE.
- У UPDATE Telegram-медиа WITH CHECK проверял только бакет.

## Итоговый контракт

Один вызов проверяет не более 20 функций, параллельно не более четырёх.
На RateLimit/429 новые порции в этом вызове не запускаются, retry-after
сохраняется и соблюдается. Только OPTIONS, без бизнес-POST и изменения trace.
Преемник — неизменяемый отчёт, прочитанный сервером по ID: браузер не передаёт
результаты. Две цепочки не перезаписывают общий курсор. Digest реестра и TTL
15 минут исключают смешение реестров и устаревших результатов.

Ручной запуск проходит все порции с `notify:false`. Существующее задание29
получает минутное расписание; его запрос и авторизация не читаются и не меняются.
Функция начинает одну дневную цепочку после прежней границы 05:00 UTC, затем
продолжает её минутными вызовами (обычно девять порций). В простое один уже
авторизованный tick возвращает 200 без проб, отчётов, аудита и уведомлений.
Новых заданий, таблиц блокировок, RPC, credentials и публичных точек входа нет.

Дубли одного старта/преемника получают одинаковый PK существующего отчёта:
вставка атомарно выбирает единственный результат, остальные возвращают replay
до аудита и уведомления. При гонке возможны дубли безопасных OPTIONS, но не
повторные сохранения/уведомления. Последовательный повтор в ту же минуту idle.
Дата цепочки — день старта, включая пересечение полуночи. Свежая цепочка может
продолжаться до05:00; новый дневной запуск — после05:00. Истёкшая в тот же день
цепочка остаётся явно неполной до ручного запуска либо следующего дня: нет
бесконечных рестартов и ложного зелёного статуса. TTL и retry-after соблюдаются.

Инварианты проверяются только в конце; известные проблемы сохраняются до
свежего результата. После каждой порции сервер сверяет последние30 отчётов:
старый predecessor не перекрывает более новую бизнес-проверку другой цепочки.
Подтверждённый P0 NOT_DEPLOYED хранится до более нового успешного OPTIONS,
включая проверку другой цепочки. Завершённый replay ничего не записывает.

UNKNOWN, RATE_LIMITED, TIMEOUT, ERROR, CORS_ERROR не healthy. Неполный отчёт
показывается как неполный, а ошибки завершённой проверки — отдельной карточкой.
OPTIONS подтверждает только доступность/CORS, не выполнение бизнес-сценария.

Дополнительный read-only preflight обнаружил девять старых enabled-записей
без исходников в GitHub. Managed tools не умеют читать их развёрнутый код.
Чтобы не запускать неизвестный старый обработчик оплаты/импорта, scanner
сверяет source-derived manifest обработчиков OPTIONS. TypeScript AST требует
безусловный ранний `return new Response(...)` до бизнес-кода: комментарий,
строка, поздний guard, вызов бизнес-функции в аргументе и неизвестный wrapper
не принимаются. Локальный handler-идентификатор разрешается по объявлению.
Файл создаётся
`node scripts/health-preflight-manifest.mjs`, CI проверяет его актуальность.
Отсутствующий контракт даёт UNKNOWN/probe_skipped, без HTTP-запроса;
это не считается успешной проверкой или доказательством deployment.
Финальная порция может завершить обработку реестра, но UI честно исключает
пропуски из числа выполненных проб. Реестр не отключаем и старые функции
не удаляем. Непроверенные исходники — явно обозначенный follow-up.
Digest manifest включён в digest сканирования, поэтому смена контрактов
не смешивает результаты разных версий.

| Данные | Чтение после исправления |
| --- | --- |
| Продукты, тарифы, цены, свойства | Публичный активный каталог; своя историческая покупка; сотрудники по разделам |
| Доменные привязки | Опубликованные страницы; гостю пять существующих полей маршрутизации (включая id) |
| Политики конфиденциальности | Выбранная текущая версия и история; прочие будущие — уполномоченным сотрудникам |
| Роли и разрешения | Свои назначения и уполномоченные сотрудники; bootstrap сохранён |
| CRM | Сотрудники с соответствующим доступом |
| Вопросы базы знаний | Канонический resolver доступа к уроку, без рекурсивного JOIN |
| Правила и связи обучения | Активные/видимые метаданные, свои потоки, сотрудники |
| Меню, юридические справочники, реестр плейсхолдеров | Активные записи, которые нужны клиентским формам; архив — сотрудникам |
| `fields` | Настройка контактов/интеграций по RBAC |
| Telegram-медиа | Существующая общая область сотрудников; одинаковый USING/WITH CHECK |

Покупки, доступы и пользовательские данные не изменяются. У service_role
ничего не отзывается. Отозваны лишние разрушительные/DDL-права клиентских
ролей и анонимная запись. Новые SECURITY DEFINER-функции не создаются.

## Проверка и порядок применения

1. CI: полный Vitest/build/Edge typecheck и PostgreSQL fixture-тесты.
2. Lovable — точный merged SHA; deploy только `system-health-full-check`.
3. Подтвердить runtime release `health-bounded-preflight-2026-10-21-v2`
   безопасной первой порцией `source:manual,notify:false`. Не включать новое
   расписание до этого: старая функция не знает режим продолжения.
4. Read-only preflight: fingerprint68 политик
   `f6b34c79c1c4e5f872b45244eecc947e`, 24 RLS-таблицы, два ожидаемых cron-задания,
   метаданные job29/job28 (id/name/active/schedule), ровно пять существующих SELECT column ACL
   anon для site_domain_bindings: id,site_page_id,domain,is_home,is_primary.
   Исходная оценка 0 ACL уточнена финальным preflight: table ACL и column ACL
   различаются. Каноническая область пяти полей сохраняется; любые другие
   column ACL блокируют миграцию до первого REVOKE.
   Service-role ACL сравнивается с исходным fixture: все24 имеют ровно
   service_role=arwdDxtm/postgres. Canonical SHA256 sorted [table,ACL-array]
   через JSON.stringify: eafc3b74bd6e23ea29c90624ca3277993d14ff78285c25a2890ae66b08170734.
   Cron request configuration, headers и секреты не читаются.
5. Применить по порядку канонические файлы:
   `20261021084810_health_least_privilege.sql`, затем
   `20261021084811_health_bounded_scan_scheduler.sql`.
   Допустим один managed-вызов с их дословной конкатенацией в этом порядке.
6. Read-back: fingerprint74 политик
   `9533ab393040dfe65fdfbfcc30a79cc1`, 0 лишних клиентских привилегий,
   неизменные service grants, RLS24/24, ожидаемые routing columns.
   Проверить гостевой каталог/страницы и кабинет/RBAC существующей сессии.
7. Cron: остаются ровно два прежних задания. Job29 меняет только schedule
   на * * * * *; job28 остаётся 0 * * * *. Идентичность/active/расписания
   проверяются до изменения; остальные расхождения STOP. В самом SQL нет
   обращений к request configuration или защищённым объектам. Успешный реальный
   idle-tick проверяется по безопасным логам releaseV2/HTTP200 и job29 status.
8. Довести одну ручную цепочку до полного покрытия, без рассылок/платежей/
   контактов. Прочитать узкую сводку сохранённого результата, проверить replay
   и idle-tick. Выполнить существующий безопасный release-health.
9. Security scan без ignore/autofix, затем Publish и скриншоты production
   desktop/mobile с URL, точным SHA/версией и viewport.

Managed tool может автоматически записать Drizzle-receipt. Это не разрешение
Lovable писать код: при новом SHA остановиться, проверить, что SQL дословно
совпадает с двумя каноническими файлами, изменены только receipt/journal,
дождаться GitHub checks и продолжить с проверенным SHA.

При расхождении политики/прав/расписания/rowcount или новом критическом
факте — STOP до исправления. Не откатывать автоматически к широким политикам
и TRUNCATE, не заменять безопасную проверку реальным платежом или отправкой.

## Причина замены неприменённого планировщика

Первоначальный вариант с переносом существующего ключа в Vault отклонён
managed capability: Agent access to secrets is not allowed. Повторов или
обхода ограничений нет. По read-only metadata обе миграции не применены:
68 политик/f6b..., job29=0 5 * * *, job28=0 * * * *, новых jobs/receipts нет.
Поэтому до применения исправлен только pending scheduler-файл. Новый вариант
вообще не требует доступа к секретам. RLS-файл остаётся дословно прежним.
