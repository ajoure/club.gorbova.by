# Единый координатор gorbova.by

Пользователь пишет в главный чат проекта. Координатор принимает поручение,
сверяет его с существующими задачами, ведёт очередь и возвращает результат.
Самостоятельные исследования и изменения выполняют субагенты; новые
постоянные чаты создаются только по прямому поручению пользователя.

## Сохраняемое состояние

Операционный реестр находится вне Git. Его путь и главный чат указаны в
контексте координатора. В публичный репозиторий входят только этот процесс и
профили агентов. Историю переписки, данные клиентов и приватные доказательства
в Git не переносить. При отсутствии реестра сначала найти существующий через
главный чат; не заводить конкурирующую очередь.

Для каждой задачи сохранять:

- устойчивый ID, направление, scope и исходное поручение;
- разрешения, явные holds/cancel и запрещённые операции;
- статус, приоритет, зависимости, владельца и следующий разрешённый шаг;
- ветку/worktree/PR, точные source/head/merged SHA и проверки;
- Lovable message_id/thread_id, response.status и результат отправки;
- опубликованную версию/URL, доказательства и ограничения приёмки;
- исходный checkpoint, историю передачи и архивный источник.

Очередь изменяет один координатор. Субагенты возвращают результаты в главную
работу и сохраняют только назначенные им отдельные артефакты. Обновление
реестра записывается атомарно с сохранением предыдущего состояния, когда оно
нужно для восстановления. Старую запись сначала сверять с owning source.

| Статус | Действие координатора |
| --- | --- |
| UNREVIEWED | Выяснить актуальное поручение и состояние; ничего не выполнять по старому описанию |
| READY | Взять следующий разрешённый шаг с учётом приоритета и зависимостей |
| RUNNING | Проверять существующего исполнителя/handle; не создавать дубль |
| WAIT_RESOURCE | Сохранить зависимость от владельца ресурса; делать независимую работу |
| WAIT_EXTERNAL | Сохранить точный внешний блокер; освободить очередь для других задач |
| HOLD_USER / CANCELLED | Сохранить решение; автоматически не возобновлять |
| HISTORY_ONLY | Использовать как исторический контекст, не как новое поручение |
| REPORTED_COMPLETE | Сверить доказательства на нужном уровне |
| VERIFIED_COMPLETE | Зафиксировать результат, передать ресурс и убрать разовое ожидание |

Новый вопрос пользователя обновляет приоритет и очередь. Он не отменяет
прежние поручения автоматически. Предложенный backlog не становится
разрешённой задачей без поручения. Позднее проверенное завершение заменяет
старый pending, сохраняя историю изменения.

## Делегирование

Проектные профили находятся в `.codex/agents/`. Они задают специализацию и
границы, а не создают постоянно работающие процессы или отдельные права.
Если текущий клиент не выбирает профиль по имени, передать его инструкции
в задаче субагента явно. Не утверждать, что агент запущен, по наличию файла.

| Профиль | Направление |
| --- | --- |
| contact_center | Диалоги, каналы, поиск, CRM-интерфейс и производительность |
| products_access | Продукты, покупки, компании и права доступа |
| live_content | Эфиры, записи, материалы и воспроизведение |
| support_engineering | Инженерные follow-ups действующей техподдержки |
| release_reviewer | Независимая проверка diff, CI и релизных доказательств |

Поручение субагенту содержит вопрос, конкретный результат, разрешённые
файлы/ресурсы, ограничения, критерии приёмки и место артефакта. Независимые
чтение и изменения разных файлов можно выполнять параллельно. Запись в
общий файл, изменения общего состояния и операции Lovable сериализуются.
Маленькую последовательную задачу координатор выполняет сам.

Существующий сервис техподдержки сохраняет собственный журнал идемпотентности,
правила клиентских действий и runtime. Новый профиль support_engineering
занимается техническим follow-up; он не запускает второй обработчик обращений.

## Передача Lovable

1. Проверить актуальные owning checkpoint/исполнителя и фактическое состояние
   официального плагина, незавершённые запросы и неопубликованные изменения.
2. Зафиксировать одного владельца, scope, exact SHA и разрешённое действие.
   Запись владельца сама по себе не блокирует API и не доказывает свободу.
3. Отправить один запрос в пределах scope. Сохранить ID и результат dispatch.
4. Проверять тот же handle до конечного response.status. Пауза на решение
   человека, timeout и ошибка наблюдения не разрешают повтор отправки.
5. Сверить все критерии задачи: CI, runtime/read-back, Publish и реальные
   опубликованные desktop/mobile доказательства, когда они применимы.
6. Зафиксировать handoff и передать ресурс следующей готовой задаче. При
   UNKNOWN оставить владение и запрет нового dispatch до выяснения.

Lovable используется только через официальный плагин. Production проекта
принадлежит Lovable Cloud; прямой Supabase/CLI не заменяет этот маршрут.
GitHub остаётся источником кода. Каждый самостоятельный кодовый scope имеет
свою чистую ветку/worktree и PR. Общий релиз нескольких scope требует
разрешённого полного состава; наличие PR в main ещё не разрешает его Publish.

## История, архив и завершение

Перед архивированием чата сохранить поручения, результаты, ссылки, pending,
holds и точное покрытие прочитанной истории. Индекс и выборочные сообщения
не называть полным чтением всех источников. Архив не меняет статус задачи.
Текущий исполнитель и действующий сервис остаются рабочими. Привязанное
расписание перед архивом остановить либо передать, сохраняя активный turn.
Сам архив подтвердить отдельным чтением списка архивов.

Архивирование чата не удаляет PR, ветку, worktree или документы. Старый PR
может содержать уникальные доказательства либо частично заменённый код.
Сначала проверить происхождение, поздние изменения, сохранность и активных
потребителей. Не сливать конфликтующий старый патч ради очистки списка.

Цель закрывается только после проверки всех её требований. Для конечной
текущей работы использовать активную цель и штатные ожидания; не создавать
отдельный recurring watcher на каждую ожидаемую задачу. Сохранять следующий
шаг и источник для возобновления после прерывания. Работа зависит от
доступности Codex и сервисов; конфигурация профилей не создаёт круглосуточный
сервер и не обходит защищённые подтверждения.
