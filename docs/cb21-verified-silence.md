# Проверенная цифровая тишина в длинной расшифровке

Статус: разработка; production не изменён.

Для первого окна длинного практикума dry-run обнаружил полностью нулевой
PCM. Такое окно нельзя отправлять в STT: модель может выдумать речь.
Нельзя и пропустить его в проверке полноты итоговой расшифровки.

## Проверка аудио

`verifyDigitalSilence` сверяет свежий захват с утверждённым манифестом:
границы, размер, SHA256 и флаг цифровой тишины. Затем побайтно сравнивает
полный WAV с каноническим PCM s16le 16000 Hz mono, содержащим только нули.
Тихая речь, шум, изменённый заголовок и даже один ненулевой отсчёт не проходят.
Проверка не использует ИИ и не делает сетевых запросов.

## Предлагаемый managed путь для ревизии

1. Повторно проверить владельца, provider revision, выбранные активные уроки,
   source/job и утверждённый SHA исходного манифеста. Не создавать новый job.
2. Повторно захватить только явно перечисленные silent-окна и проверить WAV.
3. Новый service-only invoker RPC блокирует job/source/part, проверяет владельца,
   ревизию и границы. Принимает только pending с attempts=0; uncertain,
   processing, cancelled и review_required не переводит в ready.
4. Сохранить типизированное evidence цифровой тишины и явно редакционную
   отметку с границами времени, а не приписывать её словам преподавателя.
   attempts остаётся 0, STT не вызывается. Обычные части не изменяются.
5. Повторное выполнение допускается только при полном совпадении evidence,
   аудио-хеша и отметки; изменение исходника останавливает выполнение.
6. Итог собирается существующим finalize только после готовности всех частей.
   Результат остаётся paid_private/unreviewed; включения кампании и клиентских
   сообщений нет. Отдельно проверить read-back, повтор finalize и отсутствие
   новых источников, заданий, связей и платных вызовов.

До реализации RPC нужна plan-only ревизия Lovable. До managed применения —
GitHub checks и ревизия точного SHA. Нельзя заменять этот путь ручным UPDATE.
