# Receipt sync: purchase identity boundary

Opening a contact refreshes provider subscription details. Previously that
observer could upsert the last receipt onto the subscription's original order,
autolink local subscriptions and propagate access. The UID fallback importer
could also overwrite an existing receipt and mark its queue item processed.
Status/metadata enrichment in two other importers bypassed the same boundary.

The snapshot now updates only the provider diagnostic cache, with a version CAS.
It does not link subscriptions, change billing dates, or write orders, payments,
entitlements or Telegram access. A complete unseen successful transaction enters
the existing canonical recovery queue; recovery independently fetches provider
proof and owns period materialization. Queue insertion does not mean fulfillment.

All four observers/importers preserve proven canonical and reconstructed
historical receipt identity. Partial markers, lookup errors and inconsistent
proof stop processing. Unknown successful transaction types cannot fall through
to a legacy INSERT with a fabricated default payment type. A partial provider
summary (for example, missing transaction type) is held; its snapshot remains in
the HTTP response, but neither cache nor financial/access writes are claimed.
Legacy enrichment re-reads intent and uses payment ID, provider UID, order link
and updated_at as a CAS; unrelated metadata is merged rather than replaced.

## Managed release

After CI and the reviewed merged SHA, deploy exactly:

- `bepaid-get-subscription-details`
- `bepaid-fetch-transactions`
- `admin-bepaid-full-reconcile`
- `bepaid-uid-resync`
- `system-health-full-check` (generated dependency digest only)

No migration, historical data repair, queue reset, provider charge/cancellation,
grant, message, schedule change or frontend Publish belongs to this release.
The previously deployed receipt guard and shared canonical engine are unchanged.
Package-local mirrors are generated by
`scripts/payments/sync-historical-receipt-guards.mjs --write` and checked in CI.

## Verification

Local tests execute the actual snapshot HTTP entrypoint and import boundaries
with isolated stateful database/provider fixtures. They cover immutable receipt
identity, dates/currency/status/refunds, missing/duplicate proof, cache-only
observation, canonical queue handoff, existing queue leases/holds, unique races,
metadata and version CAS races, authorization, and failure responses. Canonical
recovery and historical guard regressions remain part of the validation set.

Production verification must use the managed deployment result and safe OPTIONS
probes. Do not invoke full reconciliation, snapshot auto-refresh, actual payment
replay, grants or cancellation as smoke tests. Independently readable deployment
version evidence must be reported separately if unavailable. Historical repair
remains on hold until writer deployment and its separate trigger/side-effect
preflight are proved. Backend changes do not need artificial UI screenshots.
