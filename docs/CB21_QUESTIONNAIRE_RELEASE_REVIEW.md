# Ревизия предзаписи ЦБ21 перед публикацией

09.10.2026. Это журнал проверки и условий выката, а не подтверждение deployment/Publish.

## Проверенные источники

Lovable plan-only ревизия скачала и прочитала 29 перечисленных критических файлов PR611 на ee80badcc по публичным raw-адресам. Проверены семь миграций, запись анкеты, OTP, приватная UTM-атрибуция, привязка бота, webhook, рассылки и основные клиентские компоненты. Runtime не проверялся; этот аудит не покрывает автоматически все файлы репозитория.

В живой базе объектов PR611 пока нет. Колонки профиля и Telegram-аудита, используемые проверкой genuine primary bot binding, существуют. Production trigger_kind пока допускает manual/lesson_event/scheduled_condition; миграция 062003 добавляет site_form_event с сохранением прежних значений. Шаблонов событий по исходной странице пока ноль.

Обе предоставленные общие ссылки в публичном Telegram-preview открывают X-files для бухгалтеров (560 подписчиков, support-бот в описании). Первая посимвольно совпадает с HTML страницы Спасибо; вторая ещё не настроена в рассылках. Публичный preview не доказывает expire_date/member_limit, точный channel ID, права бота и allowed_updates.

## Разбор замечаний

- C1: новые webhook paths требуют resolve_site_questionnaire_bonus_join. Все миграции установить до функций. При откате сначала вернуть прежние функции, затем откатывать managed конфигурацию; не удалять рабочую RPC из-под нового webhook.
- C2: существующая коммерческая привязка бесплатного канала позволяет старым коммерческим cron/revoke/kick paths исключать участников. Guarded cutover после миграций, до активации клиентского пути: club channel_id/invite становятся NULL, paid chat остаётся прежним. Ожидаемые delta 1 club/1 reserved route; replay 0/0. Участники, подписки, деньги и telegram_access не меняются.
- B1: UUID и channel ID в configure_cb21_bonus_channel — guards разовой миграции конкретной конфигурации, а не runtime-настройки страницы. Сохраняем их для точного scope и счётчиков. Ссылки и название канала на странице управляются администратором через существующий редактор.
- B2: буквальное имя бота в QuestionnaireTelegramStep убрано. Серверный status возвращает username единственного active primary bot; клиент сверяет ответ start/deep_link с этим username. Проверка genuine primary bot binding при сохранении остаётся обязательной.
- B3: общие ссылки и пересылка разрешены. Если ссылка использует заявки, reserved route одобряет их без индивидуального Telegram ID gate. Параметры двух существующих приглашений всё ещё требуют read-back.
- M1: legacy repair устанавливает RPC; никаких автоматических исправлений при установке. Dry-run ожидает 2 истории/1 zero draft; execute отдельный managed шаг, бонусных/учебных прав ноль.
- M2: 072000 переопределяет очередь/eligibility рассылки; сохранять порядок миграций.
- M3: без approved template события не отправляются. Текст и тестовая личность запрошены у владельца; real client smoke не разрешён.

## Порядок managed выката

1. Точный merged SHA, зелёные checks и source hashes; установить миграции 055330, 062003, 064000, 071000, 072000, 080000, 083000 по порядку. Configure/repair не запускать автоматически. Подтвердить owner SELECT на auth.users для SECURITY DEFINER и фактические grants.
2. Проверить фактический target канала/ссылок и права бота. Dry-run и guarded cutover 1/1, read-back неизменных paid chat/участников/подписок. Legacy repair dry-run 2/1, затем bounded execute и replay 0.
3. Deploy site-questionnaire-visit, request-inline-otp, verify-inline-otp, site-form-submit, process-scheduled-broadcasts, telegram-webhook. Изменение shared runtime требует также синхронизации всех четырёх CB21 attested функций, точный список/hash определить по manifest; список из шести выше не заменяет этот gate.
4. В существующей странице включить questionnaire_first, сохранить product/tariff/pipeline/fields, перейти на существующую Спасибо. Заменить обещание урока двумя управляемыми CTA без изменения существующего Business URL. Настроить approved notification templates только после согласования текста; отдельная ссылка для рассылок.
5. Согласованный E2E: новый и существующий аккаунт, OTP/retry, bot Start/return, одна анкета/история/сделка, источники/UTM, обе CTA; никаких учебных прав. Проверить actual outgoing records, сообщения и опубликованные ПК/мобильные screenshots с URL/SHA/viewport. Только после всех PASS — утверждать завершение.

## Незавершённое

После merge PR611 (50b1cb638969866589db45da61aa3ee07a518fe0) checks завершились SUCCESS. Lovable синхронизировал этот SHA; хеши семи исходных SQL совпали. Владелец отдельно разрешил неизбежные служебные файлы drizzle и автоматический коммит штатного инструмента. Первая попытка применения завершилась до SQL: `lov_database--migration` требует отсутствующий `drizzle-kit`. Read-back подтвердил 0 новых функций/индексов и прежние 2 записи журнала; миграции 2–7 не запускались.

Технический prerequisite возвращает в devDependencies точные версии ранее использованного toolchain: drizzle-kit 0.31.11, drizzle-orm 0.45.4, postgres 3.4.9, с обоими lockfiles. Версии существующих пакетов сохранены. Проверены `npm ci --ignore-scripts`, production build и offline `drizzle-kit generate --custom` в отдельной временной папке без подключения к базе. Сравнение npm audit до/после не выявило новых advisory packages; прежние 70 findings вне этого prerequisite не исправлялись. После GitHub checks/merge — синхронизировать новый SHA, заново сверить семь SQL и повторить managed install. Эти зависимости нужны штатному механизму, их нельзя удалять при уборке его служебных артефактов.

Через существующую кнопку «Проверить права» в настройках клуба проверен `telegram-bot-actions/check_chat_rights`: support-бот является администратором и может приглашать в канал -1002091043395. Платный чат проверен отдельно и также доступен боту. Настройки клуба этой диагностикой не менялись. Сроки/лимиты двух приглашений она не проверяет.

Production deployment и Publish не выполнялись. Параметры Telegram приглашений/бота, подтверждение прав owner, конфигурация шаблонов и полный реальный E2E остаются непроверенными. Sales automation сейчас owner_test; автоматически отвечать обычным клиентам она не начнёт. Нужно завершить отдельный scoped сценарий через существующее управление кампаниями, сохранив чужие owner tests и глобальные настройки; сообщение клиента по существующей Business ссылке уже направляется в контакт-центр.
