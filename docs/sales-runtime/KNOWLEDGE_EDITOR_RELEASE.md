# Редактируемая база знаний продавца

Раньше настройки бота позволяли выбрать продукты консультации, но краткие описания уроков менялись только прямым SQL. Новый редактор в существующем диалоге контакт-центра позволяет владельцу проверить источники, отредактировать описание и сохранить версию. Сырые учебные расшифровки в модель и редактор не передаются.

## Контракт

- Вход: существующий `sales-runtime-control`; actor берётся из проверенного JWT. Чтение и запись требуют `super_admin` и `communication:manage`.
- Сохранение возможно только при OFF / HUMAN_HOLD и отсутствии отправки с неизвестным результатом. Предварительная проверка ничего не записывает.
- Сохранение сверяет прежнюю версию, хэш прежнего массива и хэш ровно проверенного нового массива. Изменение текста или источника аннулирует подтверждение. Повтор идентичного пакета не создаёт версию.
- Версии сохраняются в `sales_knowledge_versions`; возврат прежней версии создаёт новый черновик с повторной проверкой источников. Очередь отменяется атомарно; аудит содержит только счётчики и хэши.
- Проверяется актуальный источник, версия и хэш транскрипта, привязка к видео, timestamp блока, отсутствие неразрешённых пропусков. Качество полного транскрипта не повышается автоматически.
- Историческое видео может быть переиспользовано в ЦБ21 только при точном совпадении video reference и проверенной цепочке целевого блока. Покрытие программы проверяет Edge через существующий `loadPublicTariffAccess` / `resolveTrainingContentFilters`; runtime повторно ограничивает факты правилами доступных клиенту тарифов.
- `is_active` урока означает текущую видимость, а не состав будущего курса. Закрытый урок не исключается автоматически из продаваемой программы.
- Исторические описания без связи с ЦБ21 идут только как фон для понимания. Они не становятся выбираемыми фактами ответа и не обещают комплектацию курса.
- Импорт JSON создаёт только черновик, сохраняет ревизии и хэши проверенного пакета. Проверка и подтверждение обязательны. Цены и доступы остаются в канонических настройках продукта.

## Установка через Lovable Cloud

После merge точного GitHub SHA и зелёных checks:

1. Сверить SHA, чистое дерево, canonical project и состояние OFF/HUMAN_HOLD. Зафиксировать агрегаты knowledge facts, versions, jobs, events, outbox и checkout operations.
2. Применить только существующий файл `supabase/migrations/20260912162000_sales_knowledge_editor.sql` через managed migration. Не создавать код, коммиты, новые SQL-решения или записи фактов. При drift/missing dependency остановиться.
3. Развернуть только `sales-runtime-control` и `sales-runtime-worker` с этого SHA.
4. Проверить схему, RLS/grants и read-only owner snapshot / preview текущих фактов. Worker `health` должен вернуть `knowledge_editor_revision=v1`; `preview_context` — только агрегаты, без модели и отправок. Ни одного изменения кампании, сообщений, уведомлений, оплат, доступов и транскриптов.
5. После PASS опубликовать точный SHA. Проверить опубликованный редактор на ПК и мобильном viewport: открытие, карточки, разворачивание, чтение источника, проверка черновика; сохранение и включение не использовать как smoke.

Импорт нового пакета знаний — отдельный последующий шаг через этот редактор с точными счётчиками. Конференция 4 с неразрешёнными пропусками в пакет не входит. Новая версия не означает одобрение клиентского запуска: `client_release_approved=false` и OFF сохраняются. Сквозной тест — только на новом сообщении владельца после согласования правил.

## Проверки

- PGlite: 8 сценариев preview/apply, CAS, RLS, stale source, отмена очереди, no-op и rollback.
- Deno API: каталог без учебных текстов/URL; запрет доступа не-владельцу и записи неподтверждённого модуля.
- UI: редактирование, инвалидирование подтверждения, импорт без подмены хэша, чтение без права записи.
- Существующие сценарии диалога и runtime; типы браузера/Edge; production build. Результаты CI и опубликованные доказательства фиксируются отдельно после выполнения.
