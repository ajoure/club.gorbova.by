# Скрытие двух оставшихся опубликованными QA-эфиров

## Проблема и границы

На production Lovable Cloud 22.10.2026 две июльские QA-фикстуры оставались
опубликованными. `live-events-list` честно отдавал их по действующим правилам
доступа. `qa-live-setup` повторно публиковал обе записи при каждом setup.
Отдельного признака тестового события нет; исправление ограничено ровно двумя
известными UUID/slug, без эвристик по названию и без нового фильтра клиентов.

- `6ea22dad-2c60-48a3-986f-aa04efd0eab6` / `qa-live-open`
- `4ad98360-41d5-40c2-9d3c-946d314e5875` / `qa-live-locked`

Правка helper меняет только два значения `is_published` на false. Его не
запускать: POST создаёт/сбрасывает пользователей. Миграция атомарно блокирует
обе строки, проверяет точный июльский снимок и меняет только публикацию.
Триггер обновит `updated_at`. Повтор при двух уже скрытых строках ничего не
пишет; частичный результат, другая идентичность или устаревший снимок — стоп.
Статусы, содержимое, видео, расписание, правила доступа и записи сохраняются.

Старый клиентский end-to-end QA через эти ссылки перестанет работать:
`live-resolve` блокирует неопубликованные события до auth/admin-проверки.
Админредактор читает таблицу под admin-RLS, обе записи остаются редактируемыми.
Новые проверки следует готовить отдельно, а не публиковать эти фикстуры.

Сентябрьский клубный эфир и отсутствующие записи вне scope: отмена не
подтверждена системой, отсутствующее видео нельзя восстановить кодом.
Также вне scope — обучение, оплаты, доступы, клиентские сообщения, роли,
удаление QA-пользователей, секреты, общий Publish и другие functions.

## Проверки и план применения

База: `811c51bf468ff9f983680853d89ca720be5dbeb4`.

1. Локально: PGlite на синтетической БД выполняет настоящий SQL, проверяет
   идемпотентность, сохранение других полей/событий и атомарный отказ при
   изменённом снимке. Проверка Edge contracts/health manifest и bundle helper.
2. CI и одна консолидированная Lovable plan-only ревизия diff до merge.
3. Перед execute: exact merged SHA/tree/blobs, чистый Cloud source; по двум
   событиям прежние даты/закрытое состояние/нулевые sessions и autoweb runs,
   отсутствие видео. Проверить текущие ACL и триггеры. Несовпадение — стоп.
   Снять read-only снимок остальных live_events и правил для сравнения;
   никакие клиентские данные не нужны.
4. Deploy **только** `qa-live-setup` с безопасным unpublished default,
   не вызывать POST/setup/cleanup. OPTIONS не затрагивает пользователей.
5. Через Lovable применить ровно одну миграцию
   `20261022160000_unpublish_stale_qa_live_events.sql`. Нативное зеркало:
   `drizzle/migrations/0019_unpublish_stale_qa_live_events.sql`, байтово равно.
   Это один apply, не два. Ожидается ровно 2 обновления (либо доказанный
   already-applied с 0), при ошибке выяснить результат до повтора.
6. Read-back: обе публикации false; остальные поля, ACL и события прежние,
   кроме двух `updated_at`. Обе записи есть в админредакторе. Safe native
   authenticated GET `live-events-list` не содержит QA. Прямой resolve не
   нужен для smoke: его исходный guard неизменён, вызов создаёт audit-запись.
7. Опубликованный `https://gorbova.by/live`: отдельно ПК и mobile screenshot,
   отсутствие двух QA-карточек, реальные события доступны, нет переполнения.
   Не входить в комнаты и не создавать просмотры/участников ради проверки.
   Frontend не меняется, повторный Publish не нужен.

Обратное действие только отдельным reviewed изменением, по фактам. Автоматически
возвращать тестовые события в клиентский каталог не следует.
