# Хранение CAS-исправления данных отдельно от миграций схемы

## Проблема и результат

PR 653 поместил один DML-скрипт в два каталога миграций, включая файл
Drizzle `0019`, отсутствующий в `_journal.json`. Штатный генератор Lovable
попытался создать следующий номер `0019` и перезаписал этот файл заготовкой.
Инструмент сообщил, что SQL не запускался; source восстановлен. Успех
генерации миграции нельзя считать применением исправления данных.

Единственный канонический скрипт теперь находится в
`docs/operations/2026-10-22-qa-live-catalogue-data-repair.sql`.
Его байты сохранены: Git blob `ba4e31a06eda14a54fed3b10e73a6214af4e441e`,
SHA256 `eba92d0a5b7f78a65a48959ea093c4c8be761554ad9cbb7771534bb5cf1bec83`.
Два неприменённых schema-артефакта удалены из соответствующих каталогов.
Журнал Drizzle и snapshots не меняются, applied-метка не подделывается.

Это исправление размещения артефакта и регламента. Код Edge Functions,
запрос CAS, правила доступа, схемы, контракты и UI не изменяются.
Ранее выполненный deploy `qa-live-setup` повторять не нужно.

## Применение и проверка

Действие с данными разрешено только отдельной явной задачей в каноническом
Lovable Cloud после exact-SHA/hash/preflight. Не использовать внешний
production SQL/CLI/MCP, generator или второй зеркальный apply. При
неподдерживаемом синтаксисе/неясном результате остановиться и проверить
данные, не переписывать SQL и не повторять вслепую.

CAS проверяет две точные идентичности и снимок, атомарно меняет только
публикацию; повтор уже завершённого исправления не меняет timestamps.
До/после дополнительно сравнить остальные события, ACL и все 132 истёкшие
строки присутствия; действующих сессий должно быть 0. Старые строки не
удалять. Для фактического скрытия обязательны read-back и опубликованные
ПК/mobile снимки. Этот PR сам по себе не доказывает изменение production.

Проверки: прежние семь PGlite-сценариев выполняют тот же настоящий SQL из
нового пути; сверка байтов и diff. Дополнительный deploy/Publish не нужен.
