# Служебная поддержка: граница канала и явное решение

## Проблема

Общий Telegram-компонент объединяет историю отправителей. Выбор бота меняет
отправителя, но не исключает личный Telegram. После промежуточного ответа UI
автоматически закрывает входящие. Кнопка прочтения общего списка использовала
устаревший ключ кэша и могла передавать старую границу.

## Изменение

Отдельный режим `/admin/communication?tab=inbox&support_mode=1` использует
серверный allowlist служебных ботов (`support_enabled`, по умолчанию false),
точный bot_id, transport=bot и оба Business ID NULL во всех чтениях и действиях.
Личный Telegram, его назначения, продажи и паузы не обрабатываются.
Общая лента остаётся отдельным режимом оператора.

История, черновики, запросы списка и сообщения разделены по клиенту и боту.
В этом режиме нет общей Realtime-подписки, звуковых превью других каналов,
списка Business-отправителей или контролов продаж; используется scoped polling.
Просмотр и промежуточный ответ не снимают unanswered. Явные действия решения,
повторного открытия и назначения проверяют UUID последнего наблюдённого
входящего под общей блокировкой с INSERT. Более новое входящее блокирует старое
решение. Входящее после commit остаётся требующим ответа.

Существующая `telegram-admin-chat` проверяет allowlist, точного получателя,
последнее наблюдённое входящее, владельца назначения и принадлежность message IDs
до вызова Telegram. Support-режим не допускает fallback-отправителя, Business,
user-wide worker, редактирования и удаления. Доступно чтение уже подготовленных
вложений; повторная обработка pending-вложений требует отдельной диагностики.
Реакция записывается отдельным scoped RPC; её сохранение и доставка в Telegram
показываются раздельно. Повтор verified/uncertain действий контролирует журнал
автоматизации, как и раньше.

Веб-режим `support_mode=1&channel=web` допускает только тикеты без Telegram-моста,
Telegram recipient и истории синхронизации. Неясные/смешанные тикеты исключены
до чтения. Промежуточный ответ сохраняет unread; закрытие — отдельное действие
после отметки решения. Новое клиентское сообщение снова открывает вопрос.
Веб-режим не отправляет и не синхронизирует сообщения/реакции в Telegram.
Назначение с проверяемым Telegram-уведомлением предусмотрено для служебных
ботов через существующую таблицу и функцию уведомления; отдельная доставка
уведомления о назначении чистого web-тикета этим патчем не добавляется.

## Проверки

- Полный Vitest: 356 файлов / 2303 теста PASS до финальных узких правок;
  после них выполняются профильные проверки и обязательный CI.
- TypeScript и production build локально PASS; результат сборки не равен Publish.
- PGlite: смешанные bot/Business, неверно помеченный transport, два бота,
  microseconds/UUID boundary, stale CAS, идемпотентные assignment/reaction,
  роли, неизвестный/выключенный канал, web bridge exclusion, промежуточный ответ,
  закрытие и новое входящее.
- React integration: действительный компонент истории читает только scoped RPC,
  не создаёт общий Realtime и не вызывает resolve/mark-read после ответа.
- Real PostgreSQL concurrency добавлена в существующий обязательный CI:
  оба порядка INSERT/resolve; тест использует только отдельную synthetic DB.

## План применения — ещё не выполнен

1. PR/checks и консолидированная Lovable plan-only ревизия фактического diff.
2. После одобрения и merge: синхронизировать точный merged SHA.
3. Managed migration только `20261022113000_support_channel_boundary.sql`:
   preflight ровно 4 заданных активных служебных бота; bool default false;
   проверить DDL, grants, функции/триггеры, allowlist и ожидаемый rowcount.
4. Развернуть только `telegram-admin-chat` вместе с `supportScope.ts`.
   Никаких других functions, кода или коммитов из Lovable.
5. Read-only runtime: роли/allowlist, scoped metadata и отсутствующие Business
   rows в выдаче. Ни реальных сообщений, ни реакций, платежей, consent,
   назначений или изменений unread ради smoke.
6. Publish только после всех PASS. Проверить опубликованные URL и SHA,
   отдельные desktop/mobile screenshots без персональных данных. После этого
   обновить инструкцию heartbeat на новый безопасный маршрут.

Изменение пока не опубликовано. Не использовать новый маршрут как production
доказательство до managed deployment и runtime-проверки. Не повторять старое
uncertain mark-read и уже сохранённую реакцию.

## Откат

Вернуть frontend/function к предыдущему проверенному SHA, отключить вход в
support-режим. Additive DDL можно оставить неиспользуемым; не откатывать массово
флаги клиентов. Изменения конфигурации/триггеров — только через отдельный
reviewed Lovable plan, с точными ожидаемыми счётчиками и read-back.
