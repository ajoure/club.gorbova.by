# Исправление штатного переназначения служебного вопроса

При прежнем назначении другому сотруднику `SupportWorkspace` блокировал не
только ответ, но и «Передать менеджеру». Существующий `support_bot_assign_v1`
тоже отказывал при другом владельце. После прямого поручения владельца
техподдержка не могла продолжить технический вопрос в исходном саппорт-боте.

Сохраняются существующие функция и кнопка. У `support_bot_assign_v1` добавлена
перегрузка с обязательными CAS-параметрами; прежняя пятиаргументная сигнатура
и её отказ при чужом назначении не меняются. Оператор подтверждает текущего
и нового ответственного. Ответы, реакции и решение вопроса по-прежнему
блокируются до подтверждённого назначения текущему оператору.

## Контракт

- Только active/support_enabled бот, точные user/bot, transport=bot и оба
  Business-поля NULL. Личный Telegram и глобальный writer не используются.
- Права manage у вызывающего, view у получателя. Порядок блокировок:
  request → binding → bot/dialog; row locks следуют после advisory locks и
  используют NOWAIT с явным retry-отказом при чужой блокировке, без deadlock.
  Незавершённая/неоднозначная отправка блокирует изменение назначения.
- Снимок последнего входящего, привязки Telegram и ровно одного активного
  назначения. Opaque `assignment_version` содержит `xmin` строки и время
  наблюдения; новые изменения без обновления `updated_at` тоже видны.
  Снимок истекает через две минуты. Это краткий CAS-token, не долговременный
  идентификатор транзакции. [PostgreSQL system columns](https://www.postgresql.org/docs/current/ddl-system-columns.html).
- Старое назначение закрывается ровно одной строкой, новое создаётся ровно
  одной строкой; история и unread сохраняются. При нескольких активных
  назначениях — отказ, без массового исправления.
- ID новой записи равен request UUID; существующий audit_logs хранит
  receipt с непрямыми идентификаторами и SHA256 привязки/заметки, без текстов,
  платёжных ссылок и Telegram ID. Ровно тот же запрос возвращает created=false,
  даже после истечения снимка; другой payload с тем же ID отклоняется.
- UI хранит запрос при неясном исходе до явной проверки тем же nonce.
  Уведомление — прежний contact-center-assignment-notify, только created=true.
  Подтверждённое назначение и недоставленное уведомление различаются.

## Миграция и границы выпуска

Supabase CLI сгенерировал timestamp-файл, Drizzle `generate --custom` —
`0019_support_assignment_cas.sql`, journal entry и snapshot. Оба SQL-файла
байтово равны; это одна миграция, не два последовательных исполнения.
Snapshot схемы равен 0018, кроме id/prevId: таблицы, RLS, данные и поля не
меняются. Миграция заменяет только JSON reader и добавляет перегрузку writer;
DROP/CASCADE не нужны. Прежняя неприменённая QA-миграция 0019 удалена PR655;
это новый generated tag для реального изменения функций, не её повтор.

Production принадлежит Lovable Cloud. Применить только этот проверенный
pending managed migration после merge/exact-SHA проверки; не генерировать
дополнительный SQL, не повторять 0018/QA repair, не отмечать фиктивные receipts.
Backend-функции и реальные платежи не используются как smoke. Затем read-back
функций/прав/журнала, безопасные проверки, Publish только согласованного source
и отдельные снимки опубликованного управления на ПК/mobile без ПДн.

## Проверки

PGlite проверяет старую сигнатуру, изоляцию Business/других ботов, точные
rowcounts, повтор/конфликт nonce, истечение снимка, binding/incoming CAS,
неизвестный send-claim и сохранение unread. React проверяет подтверждение,
блокировку ответа до переназначения, прежний nonce после неясного RPC,
отдельный сбой уведомления и отмену/права. Обязательный CI дополнен реальными
PostgreSQL гонками операторов, входящих, профиля, конфигурации и прямых
UPDATE/DELETE с инверсией row/advisory locks. Результаты выпуска фиксируются
после фактических проверок; этот план не означает deployment.
